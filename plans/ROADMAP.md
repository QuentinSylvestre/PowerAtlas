## Automation & Workflows

> Every item here needs one capability PowerAtlas does not have: sending a prompt to an agent
> without a terminal. That is why `260725_KIRO_CLI_ACP_CLIENT_PROTOTYPE` was built, and the findings
> are recorded per item below, dated 2026-07-26 and measured on kiro-cli 2.14.2. Read them with the
> prototype's boundary in mind: it proved a **chat surface driven by a human watching it**, which is
> what its `-a` posture assumed. Three of the six — fire-and-forget dispatch, scheduled tasks and
> chained launches — are *unattended*, which is the absence of that human, so for those the prototype
> prices the work without deciding it. Where it established nothing, that is said rather than left
> blank.

- **Dispatch no-interactive tasks** — launch kiro-cli with `--no-interactive` and a prompt, fire-and-forget from the UI
  - **The mechanism this item names persists nothing, which changes what the feature would deliver.** Four variants were run: `--no-interactive` piped, `--no-interactive` in a real console window, and an interactive session with piped stdio quit gracefully via `/quit` (exit 0) all wrote **zero files**; only a fully interactive TTY session persisted. It is the console, not the flag. So a fire-and-forget `--no-interactive` dispatch leaves no session file, no transcript and no lock — nothing for the dashboard that motivates the item to show, and nothing for `status_classifier.py` to classify. Recorded in full under *Accepted limitations* in `plans/CLOSED_INVESTIGATIONS.md`.
  - **ACP is the dispatch path that does leave a trail**, and the trade is the mirror image. `session/new` writes `<sid>.json`, `.jsonl` and `.lock` at creation before any prompt, and the turn lands in the `.jsonl` the existing pipeline already reads — but every dispatch is then a permanent artifact in a store already holding ~13,300, and the prototype had to enumerate the store by `cwd` before and after each phase to keep its own count of what it had created honest.
  - *Unanswered — the thing that decides the item*: whether dispatch is safe with nobody watching. See the permission experiment under `## Session Control & Integration`.
- **Open session with specific prompt/skill** — generic prompt input, local/user skill execution with params
  - **The prompt half is built and measured.** Prompting over ACP works end to end with incremental chunks, tool-call rendering and an authoritative `stopReason`. Budget for latency rather than assuming it: a trivial 20-line answer took ~24 s wall clock and a tool-using turn runs to minutes, which is why the prototype needed a 600 s prompt ceiling distinct from its 90 s ceiling for ordinary requests.
  - **Skills work, and they work in full.** A skill invoked over ACP loads the whole `SKILL.md` body, not just the frontmatter description — verified with tools forbidden, reproducing a script path, four flag names and a five-row taxonomy that exist only in the body. The advertised catalogue matches `~\.kiro\skills\` exactly: 25 each, set difference empty in both directions.
  - **`with params` is the open half, and it is this item's own wording.** `/qsummarize-chat 1` honoured the body's output format but emitted 4 pairs rather than 1, and nothing distinguishes "the argument never reached `$ARGUMENTS`" from "the model ignored it". Any surface that passes parameters into a skill needs this settled first, and settling it costs one prompt.
- **Template prompts** — save reusable prompt templates per workspace (e.g., "/qdev {latest plan file}" as one-click)
  - **Nothing established about templating itself.** Storage, per-workspace scoping and the UI were all out of scope; the prototype hardcoded agent, model and effort and added no config keys, deliberately.
  - **The substitution question is inherited, not new**: this item's own example is a slash command carrying an argument, so it is blocked behind the same inconclusive `$ARGUMENTS` result as the item above — the template mechanism is worthless if the parameter never arrives.
- **Scheduled tasks** — cron-like recurring kiro-cli launches (e.g., "/qdream every Sunday 10am in agent-playbook")
  - **This is the item the prototype was scoped never to test**, and the gap is structural rather than incidental: `-a` was accepted for "a prototype driven by a human watching it", and a schedule is precisely the absence of that human.
  - **Three measured facts price it even so.** An unprompted `shell` command ran under `-a` and wrote into the real session store, overriding that session's own recorded `allowed_write_paths: []`, on a trigger nobody identified — so plan on an ungated command running on any turn, not the first. A held-open session costs ~254 MB and 5 processes, and the only lever that frees them is `_kiro.dev/session/terminate`, a kiro-private extension; there is no idle sweeper anywhere. And creation is ~5.4 s cold / ~2.5 s warm, so a scheduler either pays that per run or holds processes between runs and pays the memory instead.
  - *Blocked on*: the permission experiment under `## Session Control & Integration`. Of the six items here this is the one that should not be built on the prototype's evidence alone.
- **Chained launches** — "when session X exits, auto-launch session Y in folder Z" (pipeline mode)
  - **The trigger this item needs exists, and polling cannot see it.** `stopReason` on the completing `session/prompt` is an authoritative turn-end signal — measured at ~0.11 s after a cancel notification — where a transcript tail can only infer one from the shape of the last record.
  - **But it is a trigger only for sessions PowerAtlas itself drives.** A session live in a terminal is unreachable, because `kiro-cli chat`'s own ACP grandchild holds the lock, so "when session X exits" holds for X's that PowerAtlas launched or that have already exited — not for the terminal work the dashboard mostly watches.
  - **Stage health is not readable from the process.** `_kiro.dev/commands/execute` killed the agent with exit code 0 and no stderr, and the prototype's agent wrote 0 stderr bytes across whole sessions; separately, `-32603 "Internal error"` is this build's generic failure and was returned once for a `session/prompt` that then succeeded on immediate retry. A pipeline must judge liveness from the JSON-RPC channel and must not read a single error frame as a failed stage.
- **Plan-file shortcuts** — detect plan files in `plans/` and offer one-click "/qdev on this plan" buttons
  - **The invocation path is proven and it is cheap.** Slash commands are ordinary prompt text intercepted agent-side — `/tools` returned a canned answer in **1 ms**, impossible for a model round trip — so no proprietary RPC is involved and a standards-only client sees every skill.
  - **The parameter is the whole feature, and it is the unresolved part**: "/qdev on this plan" is exactly an argument-carrying invocation, blocked on the same `$ARGUMENTS` question as the two items above.
  - **Like *Open session with specific prompt/skill*, this one keeps its human.** A one-click button is a user gesture with the user present, so it sits inside the posture the prototype actually validated and is blocked on the parameter question rather than on the permission experiment. That makes it, with its two siblings above, the part of this section that survives a bad result from that experiment.

## Workspace Intelligence

- **Session status extensions** — the base shipped across three plans (live dots and status filter, semantic Active/Needs-input/Idle/Errored, toast notifications, blocked-on-approval vs asked-a-question). Still open: "stale /qdev never completed" heuristics, sound/chime notifications, and detecting fresh (non-resumed) in-terminal sessions
- **Plan progress overlay** — parse plan files to show phase completion status on workspace cards (e.g., "Phase 3/5")
- **Sub-agent pipeline visibility** — surface `/qreview` and `/qdev` fan-outs, which are currently invisible. kiro-cli's `subagent` tool is a DAG: *"Spawn and coordinate multiple AI agents in a pipeline… Each stage runs as a persistent session. Stages with no `depends_on` start immediately in parallel"*, with `loop_to` / `trigger` / `max_iterations` for review cycles. The TUI already exposes this behind ctrl+g; PowerAtlas shows nothing. Two independent data sources, worth treating as separate increments:
  - **Completed pipelines, from disk — available today, no integration.** Sub-agent stages persist as ordinary sessions carrying `parent_session_id`. There are **4,532** of them in the local store (vs 1,120 user-facing sessions), deliberately filtered out by the four `parent_session_id` guards in `data_kiro.py` — correct for the session list, but it means the raw material for a pipeline/history view already exists on disk. Grouping stages under their parent needs no ACP, no hooks and no new dependency. Titles are self-describing (e.g. *"You are a Maintainability reviewer reviewing a governance/skill-file c…"*).
  - **Live pipeline state, over ACP — the stated blocker is gone.** `_kiro.dev/subagent/list_update` pushes `{subagents, pendingStages}` as a fan-out runs — the DAG's current state, free once an ACP client exists. Observed firing 23 times across captured traffic, though always with empty arrays, since no probe session ever dispatched a fan-out. That client now exists: `260725_KIRO_CLI_ACP_CLIENT_PROTOTYPE` shipped a working kiro-cli ACP client on 2026-07-26, so this needs only a notification handler and a rendering surface on top of it. Two caveats keep it from being free. The prototype is **throwaway**, so this rides the rebuild rather than the original build decision; and it only ever sees fan-outs dispatched from sessions PowerAtlas itself drives — a fan-out running in the user's terminal is not reachable this way, which is what makes the disk-based increment above the one that covers real work.
  - *Confirmed*: `subagent` is advertised over ACP as a built-in tool and `chat.enableSubagent = true` globally. Since `kiro-cli chat` is a wrapper around `kiro-cli acp` (process tree measured 2026-07-25: `kiro-cli acp` ← `bun.exe` ← `kiro-cli chat -a`), every sub-agent ever dispatched from a terminal already ran through ACP — there is no TUI-only path. **Not directly observed**: a fan-out running inside an ACP probe session.
- **kiro-cli usage stats** — dashboard with session counts, durations, tool usage patterns over time

## Platform

- **[HIGH] Secret-aware handling for custom-launcher env vars** — launcher environment variables are stored, served and rendered in cleartext everywhere, and at least one real launcher holds production credentials. *Scoped 2026-07-25.*
  - *The concrete case*: `%LOCALAPPDATA%\power-atlas\config.toml` (lines 57-61 as of 2026-07-25) carries `AUTH_TOKEN_PRODUCTION`, `AUTH_TOKEN_STAGING` and `MQTT_CERT_PATH` under a `[custom_launchers.env]` block. Three other launchers have empty env blocks. The file is outside the repo, so this is not a git-leak risk — it is a local-exposure one.
  - **The exposure is wider than the config file, and this is the part that makes it high priority.** `/api/launchers` (`web.py`) returns every launcher **including its env dict**, and the `_launchers` bootstrap in `index.html` (`var _launchers={{launchers|tojson}}`) injects the same list into the page. `same_origin_guard` (`web.py`) gates **POST only** — its first line is `if request.method == "POST":` — so both `GET /` and `GET /api/launchers` are unauthenticated. **Any local process can read the production tokens with a single HTTP GET**, with no ACP client, no agent, and no user interaction. *Verified by code reading 2026-07-25; not executed against a live server.*
  - *Nothing masks them on the way through*: `launcher_modal.html:10` is a plain `<textarea>` ("Env (KEY=VAL per line)"), `editLauncher` (`index.html`) renders stored values straight back into it, and `launcher_create` (`web.py`) stores `body.get("env", {})` with no validation. Values reach the child at `launcher.py:403` (`proc_env = {**os.environ, **env}`), which is the intended behaviour and not the problem.
  - *Why now*: `save_config` (`config.py:271-290`) rewrites the whole file on any settings change, so the values are re-serialised constantly; and the ACP prototype (`260725_KIRO_CLI_ACP_CLIENT_PROTOTYPE`) introduces an agent running with `-a` that has filesystem access — a second, weaker path to the same data. That plan added a WebSocket token partly for this reason, but the token is itself served over the same unauthenticated `GET`, so it does not close this.
  - *Shapes worth considering, none chosen*: (a) reference-by-name indirection — store `AUTH_TOKEN_PRODUCTION = "@keyring:poweratlas/prod"` and resolve at launch from Windows Credential Manager / libsecret; (b) keep values local but stop serving them — omit `env` from `/api/launchers` and the `|tojson` payload, fetching it only when the edit modal opens; (c) minimum viable — mask in the UI and redact from any export or log. Note (b) alone fixes the GET exposure and is small; (a) is the durable answer.
  - *Adjacent, same root cause*: the `GET`-side gap is general. `same_origin_guard` protecting only POST means every read endpoint is open to any local process. Worth deciding whether that is acceptable independently of this item.

- **Launched sessions inherit PowerAtlas's own environment — on one of three launch paths only** — a session's environment silently depends on how the tray app was last started, and the three spawn paths disagree about whether it does. *Scoped 2026-07-28.*
  - *The symptom that surfaced it*: Claude Code launched from the PowerAtlas UI opens with `Transcript saving is off — inherited CLAUDE_CODE_CHILD_SESSION marker`; the same binary typed by hand into a terminal PowerAtlas opened in the same folder does not. `CLAUDE_CODE_CHILD_SESSION` is set by Claude Code on processes it spawns so a nested `claude` suppresses transcript saving.
  - **Verified — the discriminator is the `wt` command shape, measured 2026-07-28** on Windows Terminal 1.24.11911.0. Probe: exact-argv `subprocess.Popen` (the same call shape `launcher.py` uses) from a caller carrying `PA_PROBE_MARKER=set-by-caller` and `CLAUDE_CODE_CHILD_SESSION=1`. `wt --title … -p … -d … -- pwsh …` → the spawned shell sees **neither**. `wt new-tab --title … -d … -- pwsh …` → it sees **both**. `PA_PROBE_MARKER` existed nowhere but in the caller, so what arrives is the *caller's* environment block, not the Terminal's. Bare `wt` resolves through the app-execution-alias activation path, so the window is created by the app-model infrastructure with a fresh environment from the user registry; `new-tab` is routed into an existing Terminal instance, which forwards the invoking `wt.exe`'s environment to that tab's shell.
  - **The asymmetry is PowerAtlas's own, and nothing in the code names it.** `launch_session` (`launcher.py:172`) passes the configured template straight to `detect_terminal`; `launch_terminal` (`launcher.py:556`) and `launch_custom` (`launcher.py:419`) **discard** it whenever it contains a `{` placeholder and fall back to auto-detected bare `wt`. The Windows default template (`config.py:35`, live at `config.toml:19`) begins `wt new-tab`. So the provider path forwards the environment and the two others drop it, decided implicitly by which command shape each code path happens to build.
  - *The marker is the visible instance, not the extent*: `launch_session` calls `Popen` with no `env=`, so **everything** PowerAtlas holds reaches the session. The tray app is long-lived, so one start from inside an agent session poisons every launch until restart — currently reproducible because PowerAtlas is developed with Claude Code and gets restarted from tool calls (live instance at the time of scoping: PID 33732, `python -m power_atlas --foreground`, parent already exited — the shape of a launch from a tool call that then returned).
  - *Same disease as the interpreter split, on a different resource*: `interpreter.py`'s module docstring already diagnoses it — "four entry points independently choose an interpreter … and each inherits whichever environment invoked it. Left alone they drift apart." That module made the interpreter a property of the source tree instead of the invoking context. The environment has the identical shape and no equivalent fix.
  - *Shapes worth considering, none chosen*: (a) deny-list — strip `CLAUDECODE`, the `CLAUDE_CODE_*` session markers, the kiro equivalents and `POWER_ATLAS_VENV_REEXEC` before spawning; small, but a list that needs maintaining as agents add variables; (b) construct the child environment explicitly rather than inheriting it, which is the durable answer and also the one that makes the three launch paths agree; (c) accept it and document the workaround — restart PowerAtlas from a shell that is not inside an agent session, or from its autostart shortcut. Note that `launch_custom` deliberately merges `os.environ` at `launcher.py:403` for user-supplied launcher env vars, so (b) must keep that path's intended inheritance while fixing its default.
  - *Unverified — the one gap*: PowerAtlas's own environment block was never read directly. A PEB reader written for the purpose returned 0 variables, so its "no marker present" results are meaningless and are not relied on here; the conclusion that the tray process carries the marker is deduction from the observed banner plus the proven forwarding. Cheapest confirmation, if this is ever picked up: print `$env:CLAUDE_CODE_CHILD_SESSION` in a session launched from the UI. Also unmeasured: whether Terminal's forwarding behaviour is version-stable, and what the non-`wt` terminals in `_LINUX_TERMINALS` do.

- **Unify the `/search` and `partials_workspaces` render pipelines** — `search` and `partials_workspaces` (`web.py`) implement substantially the same filter-and-render pipeline in parallel. Unify them behind one shared helper — but diff the two functions first: they are not faithful copies, and a helper generalised from either one alone will silently change the other route's behaviour. *Scoped 2026-07-25.*
  - **The duplication has already shipped a defect, which is what moves this off the tidiness pile.** `51fc500` dropped the `latest_updated` parameter from `_workspace_status` and updated the `partials_workspaces` copy of the call; the `search` copy kept passing it, so `/search` with a status filter raised a 500 until the `260725_KIRO_CLI_ACP_CLIENT_PROTOTYPE` work fixed it. Nothing structural stops the next signature change repeating that.
  - *Static analysis will not catch the repeat*: `pyproject.toml` declares `ruff>=0.3` as a dev extra, there is no `[tool.ruff]` block and no `ruff.toml` anywhere in the repo, and ruff's default rule set does not check call arity. Tests are the only guard.
  - *Shape*: one shared filter-and-render helper both routes call, parameterised on the search prefilter and on whichever behavioural differences survive the keep-drop-unify decision the diff forces. Contained to `web.py`. Sequence it after the ACP routes land — that plan inserts into the same file.

- **kiro-cli v3 session support** — scan `~/.kiro/sessions/<workspace-hash>/sess_*/` alongside v2 `cli/` directory; handle new message format, subagent detection via `sub-executions/` dir
  - *Sized 2026-07-24*: **23 v3 sessions currently invisible** across 3 workspace-hash dirs. A read path already exists (the v3 branch of `_resolve_jsonl_path_uncached` in `status_classifier.py`); what is missing is discovery — `data_kiro.py` globs only `sessions\cli\*.json`. `kiro-cli chat --list-sessions -f json` confirms them as `"source":"v3"`. A further **11 "classic" sqlite conversations** have no file on disk at all. See `## Session Control & Integration` → [P2b].
  - **Priority downgraded 2026-07-24 — the v3 store is dormant, not live.** All 23 sessions fall between **2026-06-18 and 2026-07-16**, nothing in the 8 days since, and the window opens exactly at the `260618_KIRO_CLI_V3_PLAYBOOK_MIGRATION` work. Current kiro-cli 2.14.x writes `kiro-cli chat` sessions to the **v2** `sessions\cli\` layout even under `--v3`. So this item surfaces 23 historical sessions from a closed four-week experiment, not ongoing work — worth doing for completeness, not for coverage of live activity. Re-raise if the store starts growing again.

## Session Control & Integration

> Candidate paths to move PowerAtlas from read-only observation toward control, spiked over two rounds on 2026-07-24. Raw findings, wire logs, captured payloads and benchmark scripts are archived outside the repo at `Downloads\260724_PowerAtlas-spikes\` (`REPORT.md` for round 1, `REPORT-ROUND2.md` for round 2). Claims are marked *verified* (observed on this machine, with logs) or *unverified* (inferred from shipped code or docs, not executed). Pinned to Claude Code `2.1.219` and kiro-cli `2.14.0`/`2.14.1` — the kiro KAS bundle self-updated mid-spike, so code offsets rot.
>
> **The two correctness defects the spikes found (transcript-tail size, provider matching) and both row-level identity gaps shipped on 2026-07-24 as local fixes, with no integration work at all** (`a973715`, `ee998c2`, `8d97162`, `abc28db`). What remains below is genuine integration, ordered by value per day rather than by ambition.

- **Revisit the `None` → `"working"` fallback at the end of `_session_status` (`web.py`)** — an unclassifiable session currently displays as working, on the reasoning that a running process is working. That was unsafe when `None` was 77% of Claude Code sessions; the tail-size fix took it to 8%, so the fallback is now defensible — but an explicit unknown state may be the better answer. Small and self-contained, and the last surviving follow-up from the transcript-tail fix.

- **Baseline — measured 2026-07-24, at real scale** (84 workspaces, 1,709 sessions, 1.9 GB transcripts, 500-process table). *The sweep and classification figures were superseded by `plans/done/260725-1542_PARSE_AND_POLL_PERFORMANCE.md`, which also delivered the negative-lookup cache this block recommended. The process-scan findings below were untouched by that work and still stand.*
  - *Within the scan, `cmdline()` is ~96% of the cost*: `process_iter(["name"])` = 2.66 ms, adding `cmdline` = 57.8 ms. 213 of 502 processes are access-denied and still pay a failed syscall. ~0.1 ms per process, roughly linear in process-table size.
  - *Already solved, do not spend effort here*: workspace-level fresh-session detection is **11 ms**; session-end detection is **0 ms** at the scan layer (≤8 s end-to-end through the TTL and poll interval).

- **Push-based session status via hooks (Claude Code + kiro-cli)** — replace polling with agent-emitted events. **Status: roadmap item, not scheduled. Mechanism fully proven over two rounds.** Row-level identity, the original motivation, was solved without hooks on 2026-07-24, so what remains is latency (~300 ms against a 5 s poll) and events polling cannot see at all: permission prompts, idle nudges, sub-agent boundaries.
  - *Problem it solves*: `status_classifier.py` derives Working/Waiting/Errored by tailing JSONL transcripts behind a 5-second cache, so the dashboard is always up to one poll stale and sees only what the transcript records. Row-level liveness, the other half of the original gap, is now covered by the per-process sidecars, so hooks are no longer the only path to it.
  - *Verified — mechanism works end to end*: a project-level `.claude/settings.json` drove 28 real hook events into a FastAPI endpoint across 4 sessions; 7 hook types fired, zero delivery failures.
  - *Verified — `SessionStart` fires for fresh sessions*, carrying `source: "startup"` (vs `"resume"`), a `session_id` byte-identical to the JSONL name the `claude-code` branch of `_resolve_jsonl_path_uncached` (`status_classifier.py`) keys on, plus `transcript_path` and `cwd` outright — which removes the need for `_get_project_folder()`'s cwd-mangling. Confirmed three independent ways.
  - *Verified — Working vs Waiting is derivable from `hook_event_name` alone*, no transcript read. `Stop.last_assistant_message` even carries the final text. **Trap**: `SubagentStop` fires ~5s before the parent `Stop`; a rule that does not check `hook_event_name` (and `agent_id`, present on `SubagentStop`, absent on `Stop`) will flip a session to Waiting mid-work.
  - *Verified — the catalogue is far larger than documented*: 31 hook event types have schemas in the 2.1.219 binary. Only 8 were wired. The unwired set includes `PermissionRequest`, `PermissionDenied`, `StopFailure`, `PostToolUseFailure`, `TeammateIdle`.
  - *Verified — kiro-cli HAS hooks*, resolving the previous unknown. Not in `kiro-cli settings` (no hook keys) and not in the empty `~/.kiro/hooks/`, but **per-agent in the agent JSON** — both `agent_config.json.example` and the live `kiro_default.json` carry a top-level `"hooks": {}`. Five triggers, extracted from the binary: `agentSpawn`, `userPromptSubmit`, `preToolUse`, `postToolUse`, `stop`. Per-hook fields: `command`, `matcher?`, `timeout_ms?` (default 10s), `max_output_size?` (default 10240), `cache_ttl_seconds?`.
  - *Verified — kiro-cli `agentSpawn` DOES yield a session id, in the environment rather than the payload.* The JSON body carries only `hook_event_name`, `cwd`, `prompt`. But the hook subprocess environment contains `KIRO_SESSION_ID` (e.g. `ef360af4-9374-4931-8e4c-ba67c87e898f`), matching `kiro-cli chat --list-sessions -f json` exactly for that cwd — **the same identifier namespace `_PROVIDER_SPECS` (`presence.py`) already correlates on via `--resume-id`**. This resolves the load-bearing kiro-cli question affirmatively. `agentSpawn` fires ~1.17 s *before* `userPromptSubmit` and carries the prompt, so it is a genuine fresh-session signal.
  - *Caveat on that*: no transcript for that id was found at either path `status_classifier.py` knows (v2 `~/.kiro/sessions/cli/<id>.jsonl`, v3 `sess_<id>/messages.jsonl`). Its `"source":"classic"` points at the sqlite store (`data_kiro.py:16-25`), unopened. So the **id** is confirmed; transcript-path resolution for a classic-source session is undetermined.
  - *Verified — reactivity, measured in-band* (the tool printed `time.time_ns()`; the sink stamped arrival on the same clock): tool result → `PostToolUse` at sink is **266-321 ms**. Against the incumbent's ~2.5 s expected median staleness that is **~9× at the median, ~19× at worst case**. But decompose it: **~180 ms of that is the Python forwarder** (56 ms interpreter startup + 122 ms script) and only ~90 ms is Claude Code's own detect-and-spawn. kiro-cli is ~4× slower — `postToolUse` arrived **1,189 ms** after the tool's timestamp, with comparable forwarder cost, so ~900 ms is kiro-side.
  - *Verified — hooks BLOCK the session, serially. This is the dominant implementation constraint.* Identical 4-turn workload: no hooks 12,184 ms; 31 events wired with a fast forwarder **16,676 ms (+4.5 s, ~280 ms per event)**; a `sleep 5` hook **49,931 ms (+37.7 s)**; a `sleep 15` hook under `timeout: 10` **84,231 ms (+72.0 s)**. `duration_api_ms` stayed flat at 6.3-7.4 s across all four, proving the delta is pure hook blocking, not model latency. The configured `timeout` caps the damage but does **not** make hooks asynchronous. **A shipped implementation must not spawn a Python interpreter per tool call** — a compiled binary or fire-and-forget socket write is the single highest-leverage engineering item here.
  - *Verified — no delivery guarantee.* A session with three simultaneous failure modes (exit 1, unreachable endpoint, uncaught exception) completed `is_error: false` and *faster* than the clean baseline. Non-zero exit is logged at DEBUG only; nothing reaches the model or stderr. **Exactly one delivery attempt per event across all 205 records — no retries.** Good: a dead PowerAtlas endpoint degrades silently. Bad: a missed event is simply gone.
  - *Verified — `SessionEnd` does NOT fire on abnormal termination.* `taskkill /F /T` on a live session (21 events already delivered) produced zero further events, sink count unchanged 8 s later. **`presence.py` cannot be retired**; a hook-only model pins a hard-killed session at "Working" forever, and the process scan must *win* against stale hook state.
  - *Verified — delivery quality is otherwise good*: zero duplicates across 205 events; causally correct ordering in all 38 complete tool cycles; two simultaneous sessions in the same project interleaved with the correct `session_id` on every event and no cross-contamination.
  - *Verified — subagent attribution trap*: a subagent's own tool events carry the **parent** `session_id`. Only `SubagentStart`/`SubagentStop` carry `agent_id`/`agent_type`, so events between them cannot be attributed by `session_id` alone — the consumer must track the open-subagent window.
  - *Verified — 12 of 31 event types fire* (round 2 added `PostToolBatch`, `MessageDisplay`, `InstructionsLoaded`, `SubagentStart`, `CwdChanged`). **No event name is rejected by the settings schema — a typo is silently accepted and simply never fires.**
  - *Verified — `PermissionRequest` and `Notification` DO fire, but only with a real TTY.* Four headless approaches produced nothing (two with genuine `permission_denials` recorded); an interactive session produced both immediately. `PermissionRequest` carries `tool_name` and `tool_input` and lands **1.2 s after `PreToolUse`**; `Notification` follows ~6 s later with `notification_type: "permission_prompt"`, message `"Claude needs your permission"`. Since PowerAtlas watches sessions users run in real terminals, this is the *available* path, not a theoretical one.
  - *Verified — `Notification` has at least two types.* `permission_prompt` (above) and `idle_prompt` (`"Claude is waiting for your input"`), the latter firing **60.3 s after `Stop`** and **exactly once** across ~660 s of idling — a one-shot, not a heartbeat. Useful shape: `Stop` is the immediate turn-ended transition; `idle_prompt` is the "has been unattended a while" nudge that suits the toast-notification item under Workspace Intelligence.
  - *Verified — `PermissionDenied` never fires*, on either denial path, despite being in the binary schema.
  - *Verified — the two denial paths are distinguishable without it.* An **interactive rejection** yields `PreToolUse` → `PermissionRequest` → `Notification(permission_prompt)` → nothing (no `PostToolUse`, no `PostToolBatch`).   - *Limitations, verified*: hooks instrument **only sessions started after installation** — a settings file written mid-session is not picked up by the running session. kiro-cli config is **per agent**, so install means editing every `~/.kiro/agents/*.json` plus project-local ones, and silently misses agents added later. kiro-cli has **no `sessionEnd`, no notification and no permission trigger** at all.

A file-spool transport sidesteps both.
