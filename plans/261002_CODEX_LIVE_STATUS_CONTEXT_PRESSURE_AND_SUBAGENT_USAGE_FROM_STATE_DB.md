## Intent

### Problem statement & desired outcomes

The Codex provider shipped in `plans/done/261002-1113_CODEX_BUILT_IN_PROVIDER_SESSIONS_LIVE_DOT_AND_OVERVIEW.md`. Five gaps remain, and exploration measured each one on Codex 0.160.0 (Windows):

1. **The live dot is a guess.** A Codex row is live when `resume <uuid>` is on a process command line, or when a Codex process runs in its folder and its last activity is under 300 s old. An idle terminal session older than 300 s shows no dot. A desktop-held thread in the same folder as a terminal Codex can show one.
2. **No verdict and no notification for terminal Codex sessions.** Working/Waiting verdicts exist only for sessions that PowerAtlas's own ACP engine holds. Notifications fire only from that engine.
3. **Context pressure is kiro-cli only.** The Overview Usage block, the README and a node test all say so.
4. **The Usage page omits Codex sub-agent threads, and the omission is large.** In the current 14-day window, 26 sub-agent threads hold 24.2 M tokens against 37.0 M for the 4 top-level threads: about 40% of the Codex total. The archived plan assumed a lower bound of about 1.6% and an unknown size.
5. **Discovery reads only rollout files.** Codex's own state database (`state_5.sqlite`) holds data the rollouts do not, and it already matches the rollout scan.

Desired outcomes: a live dot that follows the thread's lock owner, a Working/Idle verdict and a turn-end toast for terminal Codex sessions, a Codex context-pressure estimate, an honest sub-agent token line, and a read-only state-database layer that fails open.

### Success criteria

- **SC-1 Live dot by lock owner.** A Codex row is live when a terminal process holds its writer lock. A terminal process is one whose command line has no helper subcommand (the existing `_CODEX_HELPER_SUBCOMMANDS` deny-list). The owner is looked up once when a lock appears and cached, and re-checked by process id and start time. When the lookup fails, or the platform is not Windows, the row uses today's rule. Verified live: an idle TUI older than 300 s shows a dot, a `codex exec` run behaves as measured, and a desktop-held or VS Code-held thread shows none (if one can be observed).
- **SC-2 Working/Idle verdict.** A terminal Codex row whose lock a terminal process holds shows Working or Idle from its last rollout record (`task_started` without `task_complete` is Working; `task_complete` is Idle). There is no Waiting state. A session whose process is gone shows neither. The rail dot and the Overview tile use the existing dot classes.
- **SC-3 Turn-end notification.** A toast fires once per new `task_complete` record of a lock-held terminal Codex session, through `notifications.py` and the existing `notifications.enabled` toggle. A session first seen mid-run records its starting offset without notifying, so old turns never fire.
- **SC-4 Context pressure.** The Overview Usage "Context pressure" block shows Codex as its own labelled estimate (peak of `last_token_usage.input_tokens` over `model_context_window` per day, sessions above 80%, top list). kiro-cli numbers are unchanged. `_USAGE_SCHEMA` is bumped.
- **SC-5 State-database layer.** A read-only reader opens `state_*.sqlite` with `mode=ro` (never `immutable=1`), in short-lived connections, normalises the `\\?\` path prefix, selects columns by name, and treats any `sqlite3` error or missing table as "no database". The spike's checks are re-run on the then-current Codex version before the layer ships: coverage equal to the rollout scan, recency within seconds, `tokens_used` equal to the rollout's final total, fail-open on a missing column.
- **SC-6 Sub-agent usage.** The Codex Tokens block gains a "Sub-agent threads" line (total only, split into `thread_spawn` and `guardian` review) for threads created in the window. The usage note says the total includes context inherited at spawn and comes from Codex's state database. With no database the page shows today's note. `claude_tokens` stays byte-identical.
- **SC-7 Documentation corrected.** README, `docs/KNOWLEDGE.md` (the 1.6% and "unknown size" statements are replaced by the measured figures and their method), the archived plan's decisions D4 and D5 are amended in a note, and the roadmap records the out-of-scope items with today's measurements.
- **SC-8 Cleanup.** The probe's throwaway Codex session (working folder ends `codexprobe_work`) is removed with the user's approval at the end.

### Scope boundaries & non-goals

In scope: the five gaps above, the state-database layer as optional enrichment, tests and documentation.

Out of scope, with the reason:
- **Driving Codex from `/acp`.** Codex has no ACP support of its own. An adapter exists: `@agentclientprotocol/codex-acp` 2.1.1 (Node, maintained under the ACP organisation, starts the Codex App Server, supports `session/new`, `session/load`, permission requests and four modes). Windows support and `session/list` are not stated. Not spiked. A future project would need a driver abstraction in `acp.py` and a permission model for Codex's approval policy and sandbox. Decided out of scope by the user (Q2).
- **App-server integration.** Dropped by the user (Q3). A standalone app-server saw a TUI's thread as `notLoaded`, and `thread/list` and `thread/read` return only metadata the rollouts already hold.
- **A Waiting verdict.** No approval record exists in any rollout, and the app-server cannot observe a terminal TUI's thread.
- **The state database as source of truth.** The scan stays authoritative (Q4).
- **A desktop/VS Code marker, a live context bar on tiles, notifications for other providers' terminal sessions.**
- **Windows-only behaviour is the target.** POSIX uses the existing fallback rule.

## 1) Current State

Labels: **read** = read in this repository (the next reader can confirm it by reading). **ran** = established by running something on 2026-10-02 against Codex 0.160.0 on Windows 11; it carries an expiry and must be re-run, which Phase 0 does. Line numbers are context only; every phase anchors edits by name.

**Liveness and the lock (read).**
- `data_codex.session_writer_locked` is a try-lock under Codex's `.coordination.lock`. It answers held or not, memoises 5 s, and **fails open to False for every failure**: an invalid id, a failed stat, a coordination lock busy through its retries with a cold cache, a probe-lock wait timeout and the `@_safe` neutral all read as "not held". A build without `.coordination.lock` also reads as not held. Its only consumer is `web._mark_resume_locked`. Lock files are 0 bytes.
- `web._session_is_live(snapshot, session, provider)` is the one liveness gate for the rail, the Overview tiles and the workspace panel. For Codex it returns True when `resume <uuid>` is on a process command line, or when a Codex process runs in the thread's folder and `data_codex.activity_epoch` is within `ACTIVITY_WINDOW` (300 s). `presence._PROVIDER_SPECS["codex"]` is argv-only, and `Snapshot.reported_status` is empty for Codex.
- `presence._match_provider` already drops any `codex.exe` whose command line carries a `_CODEX_HELPER_SUBCOMMANDS` token (34 tokens), so the snapshot's Codex processes are the terminal ones. **ran:** against `codex --help` on 0.160.0 every command is in the set except `resume` and `fork`, which are meant to be absent.
- `overview.live_sessions` builds tile candidates from held ACP sessions, ids on command lines and live process folders, then filters through `_session_is_live`. A Codex tile's `status` is always `""`. The workspace header's "active" flag uses `snapshot.live_cwds` (folder based).
- The row builders `_row_dict` and `_session_dict` in `web.py` set `status` for every row and gate only `live` and `provider` on `include_provider`; `/api/acp/sessions` is in `_REMOTE_ALLOWED_PATHS` and its docstring promises `status` is empty for sessions the ACP engine does not hold.

**Verdicts and notifications (read).**
- A Working/Waiting/Errored verdict exists only for sessions held by PowerAtlas's own ACP engine: `web._acp_status_for_held` hard-codes `kiro-cli-v3`, `_acp_availability` treats any id without a `sess_` prefix as "available", and the rail dot (`dashRailDotClass`) gives a verdict only when `availability` is `held`. The poll `dashRailRefreshStates` copies a row's `status` only when `availability` is `held`. Other live rows get the neutral `status-live` dot.
- `status_classifier._classify_from_path` returns None for Codex before reading (its tail reader uses a plain `open()`, which blocks Codex's rename and delete on Windows). Its cache is keyed on `st_mtime` alone, which Windows freezes for a held rollout.
- Notifications come only from `acp.py` through `web._notify_from_acp` and `notifications.notify_turn_end(label, stop_reason)`; the label comes from `web._notify_label(cwd, session_id)`. `notifications.py` documents that a poll-shaped notifier was removed on 2026-09-19 because it never ran, and `plans/done/260922-1140_ACP_TURN_END_AND_PERMISSION_NOTIFICATIONS.md` lists reviving it as a non-goal. Toast text reaches PowerShell through environment variables, never the script body.

**Usage and context (read).**
- `overview._parse_codex_usage` reads `info.total_token_usage` and `info.last_token_usage` and never `model_context_window`. Context pressure is parsed only for kiro-cli v3 and aggregated into `usage_summary()["context_pressure"]` with `CONTEXT_PRESSURE_PERCENT = 80.0`. `_new_day()` already carries a `context_peak` field. `_USAGE_SCHEMA` is 6 and is used only to reject a worker child on another format. `_usage_roots()` returns a 3-tuple that tests patch. `usage_summary` runs under `_usage_compute_lock` and applies the provider and hidden-workspace filters (`shown`, `is_hidden`) itself, outside the per-file memo.
- Codex sub-agent rollouts are excluded in three places (the store index verdict, `is_subagent_rollout`, `_parse_codex_usage`). The Codex Tokens block and `docs/KNOWLEDGE.md` say sub-agent threads are not counted and put the undercount at a lower bound of about 1.6 % of 852 M tokens.
- `acp.py` may import only `config`, `launcher._SESSION_ID_RE` and `permission_rows` (a test pins it); `acp.py` and `presence.py` may not import each other; `data_codex.py` must not import `overview`, `web` or `presence`; `presence.py` imports `.data` and `psutil`. Every Codex rollout read goes through `data_codex.open_shared`. No `sqlite3` import exists in `src/`.
- `data_codex._norm_cwd` treats any path starting with `\\` as a network or device path and only slash-normalises and case-folds it: it does not strip the `\\?\` prefix. `data._normalize_path` (used by the hidden-workspace tags) also keeps it.

**Measured on 2026-10-02 (ran; Codex 0.160.0; `docs/KNOWLEDGE.md` is pinned to 0.159.2).**
- *Lock owner (n=1 run):* an idle `codex resume` TUI took its thread's writer lock and a second lock for a helper thread. `psutil.open_files` (about 5 s) and the Windows Restart Manager through `ctypes` (about 1.2 s) both named the TUI as the holder of the lock file and the rollout. The lock file stayed on disk, unlocked, after the TUI ended. **Not observed:** a fresh `codex` TUI after its first prompt; a TUI that switches thread with `/new` or `/resume`; a lock held by the desktop app or the VS Code extension. `docs/KNOWLEDGE.md` records two older observations that an interactive TUI took no lock, made with a locked screen (the TUI never started); this run supersedes them only for the `resume` case. The desktop app's Codex processes are `codex.exe … app-server` with `ChatGPT.exe` as parent.
- *Rollout records (full scan of 92 top-level rollouts):* no approval, permission, elicitation or user-input record type exists. 82 end in `task_complete`, 2 in `turn_aborted`, 5 in a message.
- *Context (full scan, 13,957 `token_count` events):* `last_token_usage.input_tokens / model_context_window` has median 0.31, p99 0.80, max 0.93, none above 1.0; the window is 258,400 (13,951 events) or 272,000 (6). After 20 of 20 compactions that began at 0.2 of the window or more, the next reading was about 0.
- *State database `state_5.sqlite` (full scan of 644 rows):* WAL mode, 42 columns, 58 migrations. `mode=ro` honours the WAL; `immutable=1` ignored it and missed the newest row (n=2). 537 of 644 `cwd` values carry the `\\?\` prefix. The 93 unarchived non-sub-agent rows are exactly the 93 top-level rollouts. After stripping the prefix and normalising, 1 of 93 folders differed: the rollout stores an 8.3 short path and the database stores the long path. `updated_at_ms` matched the last rollout record within 5 s for 92 of 93. `tokens_used` equalled the final `total_tokens` for 86 of 86 top-level threads. `thread_spawn_edges` agreed with the `source` field for 297 of 297. A missing column or table raises `sqlite3.OperationalError`. Cold process: rollout scan 318 ms, DB query 8 ms (median of 5). A second, stale `state_5.sqlite` (737 KB, last written 2026-06-14) sits in a `sqlite` sub-folder of the Codex home, so the database's location has varied between Codex versions.
- *Sub-agent tokens (full scan):* in the 14-day window 4 top-level threads hold 37.0 M tokens and 26 sub-agent threads (8 `thread_spawn` children under 3 parents, 18 `guardian` reviews) hold 24.2 M (18.8 M `thread_spawn`, 5.4 M `guardian`): sub-agents are about 40 % of the Codex total, an estimate resting on 4 top-level threads. At a sub-agent's first `token_count` a median 7 % (p25 2 %, p75 22 %) of its final total is already present (500 rollouts); `docs/KNOWLEDGE.md` records a different measure of inheritance (pre-start cumulatives equal to the parent's in 47 % of `thread_spawn` cases), and Phase 0 reconciles the two before either is written into the documentation.
- *App-server (n=1 run):* a standalone `codex app-server` accepts requests with a `jsonrpc` field, reported the TUI's thread as `notLoaded` with an empty loaded list, and `thread/read` returns stored metadata only.
- *ACP:* Codex has no built-in ACP support (no `acp` command, no ACP feature flag among 154). An adapter, `@agentclientprotocol/codex-acp` 2.1.1 (Node, Apache-2.0, starts the Codex App Server), supports `session/new`, `session/load` and permission requests; its Windows support and `session/list` are not stated, and it was not run.

## 5) Implementation Phases

**Parallel phase annotation.** None is eligible: Phases 1 and 2 share `overview.py`, `index.html` and the Usage tests; Phases 3-5 form a dependency chain; every phase edits `tests/test_web.py`.

**Comment convention.** The shared source files already hold 349 comment lines that name a bare "Phase N" (in `web.py`, `templates/index.html` and the tests) and 92 that name the predecessor plan's phases. Any code comment written by this plan names its phase together with this plan's slug on the same line, never a bare "Phase N".

**Vertical phasing rule.** Each of Phases 1-5 is a vertical slice (data, aggregation or wiring, UI, tests). Phase 0 and Phase 6 are horizontal: Phase 0 is measurement that gates the design; Phase 6 is documentation and cleanup that depends on all slices.

**Public-repo hygiene check.** From Phase 0 on, the id of each throwaway session goes into a scratch ledger outside the repository at creation and is never printed.
