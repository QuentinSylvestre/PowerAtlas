# ACP v3 Spike — `/acp-v3` Prototype

> **Date**: 2026-08-19
> **Status**: Exploring
> **Scope**: Build a working `/acp-v3` prototype that drives kiro-cli v3 ACP sessions, covering full v2 feature parity plus v3-specific behaviors, as throwaway spike infrastructure.

---

## Intent

### Problem statement & desired outcomes

The `/acp` surface in PowerAtlas drives kiro-cli exclusively via the v2 ACP protocol (`kiro-cli acp -a`). kiro-cli v3 (`--agent-engine v3`) ships a materially different protocol: an auth handshake requiring the client to answer an inbound `_kiro/auth/getAccessToken` JSON-RPC request with a fresh OIDC token from `kiro-cli chat _ get-kas-token`; `sess_`-prefixed session IDs; no lock files; `_meta.kiro.modeId` for agent selection; and different notification method names (`session/update` subtypes vs `_kiro.dev/*`).

The desired outcome is a working `/acp-v3` page that covers every feature `/acp` currently covers — session creation, resume, prompting, streaming, tool call rendering, crew panels, steer/queue, diff recovery on reload, image paste, slash commands, session deletion — plus any surfaceable v3-specific behaviors discovered during the spike. The spike validates feasibility, measures every remaining protocol unknown, and produces a recommendation for the v3 liveness detection approach. The follow-on plan inherits no protocol unknowns.

### Success criteria

- SC-1: `_SupervisorV3` spawns `kiro-cli acp --agent-engine v3`, completes the `_kiro/auth/getAccessToken` handshake, and creates a session via `session/new` with `modeId=kiro_default`.
- SC-2: At least one full `session/prompt` round-trip completes — agent streams tokens, tool calls render, turn ends cleanly.
- SC-3: Diff recovery works on reload for a session containing `fs_write` or `str_replace` edits — the diff row expands after a page reload.
- SC-4: All current `/acp` v2 features work on `/acp-v3` at parity: session rail (workspace/day/status grouping), session creation with workspace picker, resume of exited sessions, cancel, close, queue, steer, crew panel, image paste, slash command palette, session deletion.
- SC-5: The v3 liveness detection probe produces a documented recommendation (whether `session.json` status, agent refusal timing, or a presence hook injection is the right approach for production).
- SC-6: `CLOSE_METHOD` behavior on v3 is measured — the spike confirms whether `_kiro.dev/session/terminate` works or a different method is needed.
- SC-7: `_on_notification` v3 compatibility is confirmed by running a real turn and logging all notification method names received.
- SC-8: All current tests pass. New tests cover `_get_tool_diffs_v3`, `_stored_session_cwd_v3`, and the `_on_agent_request` token handler.
- SC-9: MCP OAuth and `_kiro/spec/*` / `_kiro/workflow/*` are documented as roadmap items.
- SC-10: Browser verification via Playwright confirms `/acp-v3` feature parity with `/acp` for SC-1 through SC-4.

### Scope boundaries & non-goals

**In scope:**
- `_SupervisorV3(Supervisor)` subclass in `acp.py` — overrides `_spawn`, `_on_agent_request`, `load_session`, `_stored_session_cwd`, and `_build_kas_session_params_v3`
- `_get_tool_diffs_v3(session_id)` function inlined in `acp.py` — reads v3 `messages.jsonl`, extracts `fs_write`/`str_replace` diffs, returns same `{toolCallId: {path, oldText, newText}}` shape as v2
- `_stored_session_cwd_v3(session_id)` function inlined in `acp.py` — reads v3 `session.json` → `workspacePaths[0]`
- Token handler in `_on_agent_request` — calls `kiro-cli chat _ get-kas-token` via `subprocess.run` on demand, replies with `{accessToken, expiresAt, profileArn, provider}`
- `_supervisor_v3 = _SupervisorV3()` singleton alongside `_supervisor`
- `_publish_live()` on both supervisors emits the union of both session sets to the shared hook
- Shared `_registry`, `_bubbles`, `_tasks` between v2 and v3 supervisors
- `/acp-v3` GET route and `/ws/acp-v3` WebSocket route in `web.py`
- `/api/acp-v3/sessions`, `/api/acp-v3/workspaces`, `/api/acp-v3/sessions/delete` listing/management endpoints
- `acp.html` gains `engine` Jinja variable; WebSocket URL and v3-specific blocks gated on `engine === "v3"`
- Remote-address allowlist in `web.py` updated for `/acp-v3` and `/ws/acp-v3`
- V3 liveness detection probe: test `session.json` status field reliability, agent refusal round-trip timing, presence hook injection feasibility
- `CLOSE_METHOD` probe on v3: confirm `_kiro.dev/session/terminate` works or find the correct method
- `_on_notification` v3 compatibility probe: log all notification method names on a real v3 turn
- Feature inventory: document every `/acp` v2 feature against v3 behavior as the spike proceeds
- Roadmap documentation for MCP OAuth and `_kiro/spec/*` / `_kiro/workflow/*`
- New tests for inlined v3 helpers and token handler
- Playwright browser verification of `/acp-v3`

**Not in scope:**
- Merging `_SupervisorV3` back into `_Supervisor` (follow-on plan)
- Linux cross-platform support (follow-on)
- MCP OAuth flow (`_kiro/mcp/status` with `failedAuthorization`) — roadmap item
- `_kiro/spec/*` and `_kiro/workflow/*` notifications — roadmap item
- Production-grade liveness detection implementation (spike produces recommendation only)
- Removing or deprecating `/acp` v2 path

### 4. Existing patterns & constraints

**`acp.py` isolation boundary** (`acp.py` module header): `acp.py` imports exactly two guarded names from the `power_atlas` package: `config.CONFIG_DIR` and `launcher._SESSION_ID_RE`. A plan exit criterion greps for module names to enforce this. All v3-specific disk reads (`_stored_session_cwd_v3`, `_get_tool_diffs_v3`) must be inlined in `acp.py` rather than imported from `data_kiro_v3`.

**`_Supervisor` class** (`acp.py:2297–2420`): ~25 fields across 5 categories (spawn-time, session registry, sub-agent crew, compaction, per-session). `_SupervisorV3` inherits all of these unchanged. Methods that differ: `_spawn` (args: `("acp", "--agent-engine", "v3")`; no `-a`), `_on_agent_request` (token handler for `_kiro/auth/getAccessToken`), `load_session` (no lock hint, v3 cwd/diff paths), `_build_kas_session_params_v3` (adds `modeId`), `_stored_session_cwd` (reads v3 `session.json`). All other methods inherited unchanged.

**`_on_agent_request`** (`acp.py:3098–3128`): currently refuses all inbound agent requests with `-32601`. The three-way dispatch in `_on_message` (response / inbound-request / notification) already routes to this method. `_SupervisorV3._on_agent_request` needs a branch for `_kiro/auth/getAccessToken` before the catch-all refuse.

**Token retrieval** (probed): `kiro-cli chat _ get-kas-token` is an `.exe` (not `.cmd`), callable via `subprocess.run(["kiro-cli", "chat", "_", "get-kas-token"], capture_output=True)` without `shell=True`. Returns `{"kind":"getKasToken","data":{"accessToken":"...","expiresAt":"...","profileArn":"...","provider":"Enterprise"}}`. Enterprise account — `profileArn` is required in the token response per governance docs; omitting it causes `-32000 profileArn is required`.

**v3 session/new** (probed): `kiro-cli acp --agent-engine v3` starts KAS with `--auth=acp-callback`. KAS logs confirm `_kiro/auth/getAccessToken` is the handshake method. `session/new` params: `{cwd, mcpServers: [], _meta: {kiro: {modeId: "kiro_default", steering: [...]}}}`.

**v3 `messages.jsonl` field shapes** (probed from live sessions):
- `fs_write`: `payload.type="tool_call"`, `payload.toolName="fs_write"`, `payload.toolCallId`, `payload.args.path`, `payload.args.text`, `payload.status`, `payload.kind="edit"`
- `str_replace`: `payload.toolName="str_replace"`, `payload.args.path`, `payload.args.oldStr`, `payload.args.newStr`, `payload.args.replace_all`
- `tool_result`: `payload.type="tool_result"`, `payload.toolCallId`, `payload.success` (bool)

**v3 cwd resolution** (probed): v3 `session.json` has `workspacePaths[0]` (not `cwd`). `data_kiro_v3._find_v3_session_path(session_id)` resolves `messages.jsonl` path by scanning hash dirs. For cwd: read `session.json` → `workspacePaths[0]` inline.

**`_SESSION_ID_RE`** (`launcher.py:25`, `^[\w\-]+$`): passes `sess_<uuid>` format — probe confirmed.

**`serve_socket` / `_dispatch`** (`acp.py:4492`, `4569`): supervisor-agnostic. `_dispatch` calls module-level handler functions which call `_supervisor.*` directly. A `/ws/acp-v3` route needs a parallel `serve_socket_v3` backed by a `_dispatch_v3` that calls `_supervisor_v3.*`.

**`sessions_changed_hook`** (`acp.py:821`): Called by `_publish_live()`. For dual supervisors, both must call the hook with the union of both session sets.

**Remote allowlist** (`web.py:1130`): exact-match dict, checked by `same_origin_guard` and `_ws_origin_ok`. `/acp-v3` and `/ws/acp-v3` must be added to be remotely reachable.

**`CLOSE_METHOD = "_kiro.dev/session/terminate"`** (`acp.py:425`): v3 compatibility unverified — spike probes this.

**`acp.html`** (7,437 lines): inline JS maintains `ws` WebSocket, `sessionId`, `turnActive`, `toolRows`, `crews`, and ~30 other state vars. WebSocket URL is the only structural difference for v3. Engine variable (`engine`) injected as a Jinja/JS const controls the WS path.

**Test suite**: `tests/test_web.py` (17,112 lines), `tests/acp_page.test.mjs` (9,500 lines), `tests/test_data_kiro_v3.py` (748 lines). `acp_page.test.mjs` runs a DOM stand-in — covers JS behavior. Pre-commit hook `_check_test_names.py` catches duplicate test definitions.

### 5. Risks & mitigations

**R1 — `initialize` timing with `_kiro/auth/getAccessToken` (AS-6)**: If `initialize` blocks until the token is provided on stdio, `_request("initialize")` will time out before `_on_agent_request` can fire. Mitigation: the first thing the spike does is run a raw probe of the stdio handshake to confirm ordering. Per governance docs, `initialize` result does not wait for the token.

**R2 — `CLOSE_METHOD` on v3 (AS-5)**: `_kiro.dev/session/terminate` is v2-specific. If v3 uses a different method, the sweeper and close path fail silently. Mitigation: SC-6 explicitly probes this before implementing the close path in `_SupervisorV3`.

**R3 — `_on_notification` v3 method name incompatibilities (AS-4)**: v3 notification method names differ from v2 (`session/update` subtypes vs `_kiro.dev/*`). The existing `sessionUpdate` kind-based dispatch already handles the subtype path. The v2-only method branches (`_kiro.dev/commands/available`, `_kiro.dev/metadata`) become dead code for v3. SC-7 logs all notification method names on a real v3 turn to confirm no unknown methods break the dispatcher.

**R4 — `_find_v3_session_path` for ACP-created sessions**: `data_kiro_v3._find_v3_session_path` finds sessions by scanning hash dirs. ACP `session/new` writes a new v3 session to the store — the path scan may miss it until the `_session_path_cache` is refreshed. Mitigation: the spike verifies that diff recovery works on a session created via ACP `session/new`, not just pre-existing sessions.

**R5 — `profileArn` required for Enterprise accounts**: The token response must include `profileArn` and `provider`. If `kiro-cli chat _ get-kas-token` is called outside the normal KAS context (e.g., no active Q profile), it may fail or return an incomplete token. Mitigation: probe confirmed the token is available; the handler logs the token fetch result at WARNING on failure and refuses with a descriptive error.

**R6 — Dual-supervisor `_publish_live` union**: If `_supervisor_v3` is not yet initialized when `_supervisor._publish_live()` fires at startup, the union call raises. Mitigation: guard with `_supervisor_v3 is not None` check before union.

### 6. Resolved decisions

- Q1: What does success look like — Go/No-Go or working prototype? — A: Both; build the prototype as the validation. — **Decision: spike produces working `/acp-v3` prototype that also yields the cost estimate for full production transition.**
- Q2: Extend `/acp` or new `/acp-v3` page? — A: New page. — **Decision: `/acp-v3` is a separate route; v2 `/acp` is untouched during the spike.**
- Q3: Auth token source for the v3 handshake? — A: Shell out on demand. — **Decision: when `_kiro/auth/getAccessToken` arrives, call `kiro-cli chat _ get-kas-token` as `subprocess.run` (no `shell=True`, it's an `.exe`) at that moment and reply with `{accessToken, expiresAt, profileArn, provider}`.**
- Q4: Prototype scope? — A: Full — every current v2 feature plus v3-specific features. — **Decision: spike starts with a feature inventory; scope is decided per item from that inventory.**
- Q5: What counts as "new v3 features"? — A: Inventory-driven; surfaceable features in scope, MCP OAuth and spec/workflow out of scope with roadmap notes. — **Decision: surfaceable v3 behaviors in scope; invisible protocol differences in scope when required; MCP OAuth + spec/workflow out of scope with roadmap documentation.**
- Q6: One supervisor or two? — A: Parallel. — **Decision: `_SupervisorV3` is a separate instance alongside `_supervisor`; `/acp-v3` talks exclusively to it; v2 code path untouched.**
- Q7: Session store — read-only or write? Diff recovery in scope? — A: Read-only, diff recovery in scope. — **Decision: spike reads v3 store for rail and diff recovery (`messages.jsonl`); no new write paths; diff recovery is required.**
- Q8: Platform support? — A: Windows-only. — **Decision: same pywin32 job-object teardown as `_Supervisor`; Linux follow-on.**
- Q9: v3 cwd resolution — import `data_kiro_v3` or inline? — A: Inline. — **Decision: `_stored_session_cwd_v3` inlined in `acp.py`; reads v3 `session.json` → `workspacePaths[0]` directly.**
- Q10: `get_tool_diffs_v3` — in `data_kiro_v3.py` or inline? — A: Inline. — **Decision: `_get_tool_diffs_v3` inlined in `acp.py`; isolation boundary maintained.**
- Q11: v3 liveness detection — skip lock hint, or probe? — A: Probe as spike discovery goal. — **Decision: spike includes a liveness detection probe; result is a documented recommendation for the follow-on plan.**
- Q12: Single template or separate? — A: Single `acp.html` with `engine` Jinja variable. — **Decision: WebSocket URL and v3-specific blocks gated on `engine === "v3"`.**
- Q13: `_SupervisorV3` — subclass or copy? — A: Subclass. — **Decision: `_SupervisorV3(_Supervisor)` overrides only differing methods; inherits everything else.**
- Q14: Shared singletons? — A: Shared `_registry`, `_bubbles`, `_tasks`; `_publish_live()` emits union of both supervisors' sessions. — **Decision: both supervisors share module-level infrastructure; union guarded against `None` at startup.**

### 8. Recommended approach

**Phase 0 — Wire probes (before any code):**
Verify AS-6 (initialize/auth timing), AS-5 (CLOSE_METHOD), AS-4 (notification method names on a real v3 turn), and R4 (ACP-created session path discovery). Each probe is a short throwaway script; results are recorded in the project file and drive implementation decisions in Phase 1.

**Phase 1 — `_SupervisorV3` skeleton + auth handshake:**
Add `_SupervisorV3(_Supervisor)` to `acp.py` with:
- `_spawn`: `ACP_V3_ARGS = ("acp", "--agent-engine", "v3")`, same job-object teardown
- `_on_agent_request`: branch for `_kiro/auth/getAccessToken` — `subprocess.run(["kiro-cli", "chat", "_", "get-kas-token"])`, parse token, write response; fall through to `_refuse` for all others
- `_build_kas_session_params_v3`: adds `modeId: "kiro_default"` under `_meta.kiro`
- `_stored_session_cwd_v3` / `_get_tool_diffs_v3`: inlined helpers
- `_supervisor_v3 = _SupervisorV3()` singleton
- `_publish_live()` union fix on both supervisors
Verify: `ensure_started()` on `_supervisor_v3` completes the handshake.

**Phase 2 — Session creation and turn:**
Override `load_session` in `_SupervisorV3` (no lock hint, use `_stored_session_cwd_v3`, use `_get_tool_diffs_v3`). Add parallel handler functions `_handle_new_v3`, `_handle_load_v3`, `_handle_prompt_v3`, `_handle_cancel_v3`, `_handle_close_v3` that call `_supervisor_v3.*` instead of `_supervisor.*`. Add `_dispatch_v3` routing to these. Add `serve_socket_v3`.
Verify: create a session on `/ws/acp-v3`, send a prompt, observe a streamed turn with tool calls.

**Phase 3 — `/acp-v3` page + rail:**
Add `GET /acp-v3` route in `web.py` serving `acp.html` with `engine="v3"`. Add `/ws/acp-v3` WebSocket route. Add `/api/acp-v3/sessions`, `/api/acp-v3/workspaces`, `/api/acp-v3/sessions/delete` endpoints (parallel to existing v2 endpoints, calling `_supervisor_v3`). Update remote allowlist. Update `acp.html` with `engine` variable and v3-specific WS URL.
Verify: full page loads, rail shows v3 sessions, workspace picker works.

**Phase 4 — Diff recovery:**
Verify `_get_tool_diffs_v3` produces correct backfill for a session with `fs_write` and `str_replace` edits. Verify diff rows expand after page reload.

**Phase 5 — Liveness detection probe + CLOSE_METHOD probe:**
Test `session.json` status field for live vs idle distinction. Measure `session/load` refusal round-trip time on a live v3 session. Assess presence hook injection feasibility. Send `_kiro.dev/session/terminate` on a live v3 session; record response. Produce liveness recommendation.

**Phase 6 — Feature inventory sweep + roadmap documentation:**
Walk every `/acp` v2 feature against v3 behavior. Document gaps, differences, and new features. Add MCP OAuth and spec/workflow as roadmap items.

**Phase 7 — Tests + Playwright verification:**
Write pytest tests for `_get_tool_diffs_v3`, `_stored_session_cwd_v3`, token handler. Update `acp_page.test.mjs` for `engine` variable. Playwright verification of `/acp-v3` against SC-1 through SC-4 and SC-10.
