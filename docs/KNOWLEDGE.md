Framing is **NDJSON**, not LSP `Content-Length`. `session/new` takes **~5.4 s for the first session of a process**, spawn and handshake included, and **~2.5 s for each session after** — re-measured 2026-07-26 on 2.14.2, superseding the ~3.2 s single sample, which was neither the cold nor the warm case. **Both figures are themselves superseded on 2.16.0**: an eight-session run on 2026-08-01 measured **1.1 s** for the first and **~0.5 s** for each after, consistent with the 1.47 / 0.55 / 0.48 s reading below. Options: `--agent`, `--model`, `--effort`, `--trust-all-tools`, `--trust-tools`, `--agent-engine v1|v2|v3` (default v2).
  - *Verified — explicit slash-command invocation is ordinary prompt text*, not a proprietary RPC. `/tools` sent as prompt text returned in **1 millisecond** with a canned count — impossible for a model round-trip, proving agent-side interception. **This inverts the previous assumption**: `_kiro.dev/commands/available` is an agent→client *push notification* carrying the catalogue (25 built-in commands + 26 skill prompts as `prompts` with `serverName: "skill:config"`, 15 tools, live MCP server status); calling it as a client→agent request returns `-32601`. A standards-only client sees skills fine.
  - *Verified — `_kiro.dev/commands/execute` kills the agent process with exit code 0, no stderr, no JSON-RPC error.* Reproduced 2/2 across separate processes and two param shapes. Combined with the process writing nothing to stderr all session, a supervisor can trust **neither exit code nor stderr** for health. Also: one process is a **tree** (MCP servers are grandchildren — a plain kill leaks them). **Superseded 2026-08-12 for the object-form payload**: the kill was caused by using a *string* payload (the incorrect form); the TuiCommand *object* form `{"sessionId": sid, "command": {"command": name, "args": {}}}` is confirmed correct from tui.js and KiroCrew source analysis and is what PowerAtlas's `_handle_commands_execute` uses. The supervisor-trust note about exit code and stderr remains valid. Live probe (object form, output path, options shape) deferred to post-deployment. PowerAtlas `/acp` now dispatches slash commands via `_kiro.dev/commands/execute` with the TuiCommand object form (Phase 3, 2026-08-12).
  - **PowerAtlas `/acp` now handles three additional kiro notifications (2026-08-12, Phase 1/3); skills discovery added 2026-08-13 (Phase 1–4):**
    - `_kiro.dev/commands/available` — agent→client push carrying the full catalogue (`{commands:[{name,description}], prompts:[…], tools, mcpServers}`); no `sessionId` in params; attributed to the single inflight session. Probe-verified counts: **25 built-in commands** + **26 skill prompts** (each with `serverName: "skill:<name>"`). PowerAtlas stores both in `sessions[sid]`: commands under `meta["commands"]`, skills under `meta["skills"]`. Skills are extracted by `_parse_skills()`, which accepts entries from `prompts` (using `serverName.startswith("skill:")` as the discriminant) and from `available_commands_update` (using `_meta.kiro.type == "skill"`). Both a `"commands"` and a `"skills"` server frame are broadcast to subscribers; both are replayed to new subscribers in `_handle_subscribe`. A **`_pending_commands` single-slot buffer** on `_Supervisor` handles the race where all five `commands/available` notifications arrive during the `session/new` round-trip before `sessions[session_id]` is registered — the buffer is flushed immediately after session registration and cleared unconditionally in the `finally` block. A separate **`available_commands_update`** handler fires when `session/update` arrives with `sessionUpdate: "available_commands_update"` (mid-session agent mode switches); it re-extracts both lists from `params["update"]["availableCommands"]` and re-broadcasts both frames. The `/acp` slash-command palette (opened with `/`) shows both commands and skills in a flat list; skill entries are identified by a visible **`skill` badge** rendered alongside the entry name. Before the first `"commands"` or `"skills"` frame arrives the dropdown shows "Loading catalogue…"; after delivery a non-matching filter shows "No matching commands or skills".
    - `_kiro.dev/compaction/status` — agent→client push with `{status:{type:"started"|"completed"|"failed", error?}, summary?}`; no `sessionId`. PowerAtlas broadcasts a `compaction` server frame; `/acp` renders a system message ("Compacting conversation context…" / "Context compacted." / "Compaction failed."). On `completed`, the context-window meter is reset.
    - `_kiro.dev/clear/status` — agent→client push with no meaningful params; both tui.js and KiroCrew log/ignore it. PowerAtlas silently consumes it (`return` in `_on_notification`, no broadcast).
    - **Copy-to-clipboard button on code blocks** — labeled code blocks in `/acp` agent responses include a copy button (CSS class `.acp-md-copy`). Clicking it writes the code block's raw text to the clipboard via the Clipboard API, with a visual confirmation tick. No server round-trip; entirely client-side.
  - **`_kiro.dev/commands/options` is for argument completion, not command-name filtering (verified 2026-08-12).** Sending it with `command: ""` (empty command name) causes kiro-cli to exit with code 0, no stderr. The method is a client→agent **request** that expects a selected command name as `command` param and returns options for that command's arguments. When the user is still typing the `/prefix` to filter the command list, client-side filtering of the `commands/available` catalogue is the correct approach — no server round-trip. Only call `_kiro.dev/commands/options` after the user has selected a specific command, to populate its argument completions.
  - *Verified — `session/load` attaches to pre-existing sessions with full context, including ones the user's own terminal kiro-cli created.* Loading a real 17 KB `agent-playbook` session and asking what it had been working on returned `Plan 260724_QCLOSE_DOCUMENTATION_RIPPLE_SWEEP_AND_QPLAN_DOC_IMPACT_WIDENING, Phase 4` — matching the stored `title` exactly, unguessable. Load takes ~3.8 s and **replays history as `session/update` events including `tool_call`/`tool_call_update` pairs**, so a client can rebuild the full timeline without tailing JSONL. This answers the scope-defining question: ACP is not limited to sessions PowerAtlas itself launched.
  - *Verified — concurrent attach is hard-refused, not silently shared.* Ownership is a lock file `~\.kiro\sessions\cli\<sid>.lock` containing `{"pid":…,"started_at":…}`, and **an ACP process takes the same lock a terminal session does**. Loading a busy session returns in 0.84 s: `-32603 … "Session is active in another process (PID 23316)"`. Lock not stolen; the owner's turn completed normally; the final `.jsonl` had zero unparseable lines and none of the intruder's content. **Stale locks are correctly ignored** — the guard is a pid liveness check, not file presence, so crashed sessions stay attachable while live ones are protected. Reading the lock file is a cheap pre-check PowerAtlas could do without connecting at all.
  - **Corrected 2026-07-26 on 2.14.2 — the typed refusal is gone, and the relationship is inverted.** Measured live against a real terminal session holding the lock, the agent returns a bare `-32603 "Internal error"`: no PID, no text, indistinguishable from any other internal failure. So the **lock file is now the only thing that can name the holder**, not the cheap pre-check it was described as. And a pid-liveness-only pre-check would have been wrong *every time it fired*: of this machine's 803 lock files, 22 name a currently-existing pid and **all 22 are recycled** (svchost, firefox, RuntimeBroker, pwsh), created days to weeks after their lock was written; a repeat census at 804 locks found 25, again all recycled. A usable pre-check additionally requires the holder's process to have started at or before the lock's own `started_at`. Also measured: **`session/load` takes the lock too**, and locks survive the agent's exit — so a timed-out load leaves a lock naming your own agent, which reads as "active in another process" unless you recognise your own pid.
  - *Now verified*: the refusal generalises from ACP-vs-ACP to a live *interactive terminal* owner — driven end to end from `/acp`, which surfaces it as an in-use message rather than hanging.
  - *Verified — skills load the full SKILL.md body* (round 1's ~50% is now high confidence). Discriminator: flag names appearing only in `qmemory-eval`'s body Flags table while the frontmatter advertises different ones, with the wire catalogue entry confirmed to carry only the `description` string. Invoked with tools forbidden: **0 tool calls**, and it reproduced the script path, all four flags, and the five-row label taxonomy. Advertised set matches `~\.kiro\skills\` exactly — 25 each, set difference empty both directions. **Arguments inconclusive**: `/qsummarize-chat 1` honoured the body's output format but emitted 4 pairs rather than 1; cannot distinguish "argument never reached `$ARGUMENTS`" from "model ignored it".
  - *Verified — process model*: one process holds **multiple concurrent sessions** across different workspaces with no cross-talk (two parallel prompts: 3.71 s wall, not 6.75 s), so one process for everything is viable. But MCP servers spawn **per session**: **~2 + 5N processes and ~283 + 254N MB**, re-measured 2026-07-26 against a real supervisor — three concurrent sessions were **17 processes / 1,045 MB** against a **283 MB** one-agent baseline. That corrects the round-2 model in both directions: the per-session memory figure was ~20% high at 306 MB, and the process count was one short, the extra being the parent's own `conhost`. Time-to-first-token warm 1.88-2.14 s.
  - *Re-measured 2026-07-31 on kiro-cli **2.16.0**, and the model got materially cheaper — plus the close method was finally exercised.* Walking the agent's own process tree and summing RSS: **2 procs / 79 MB** at N=0, then **+3 procs and +150 MB per session** after the first (the first costs +374 MB because it pays the shared MCP/node startup). Three concurrent sessions are **11 procs / 754 MB**, against the **17 procs / 1,045 MB** on record — so the marginal session went from ~5 procs / 254 MB to **~3 procs / 150 MB**. *Caveat on the baseline*: 79 MB here vs the 283 MB recorded above is too large a gap to be version drift alone, and the likely reason is that MCP servers spawn on `session/new` rather than at `initialize`, so a genuine zero-session baseline has none running — treat the two baselines as possibly not measuring the same thing, and trust the **marginal** figure over the absolute. Session creation also collapsed: **1.47 s / 0.55 s / 0.48 s** for the first three, i.e. warm creation is now sub-second against ~2.5 s on 2.14.2.
  - *Verified — `_kiro.dev/session/terminate` still exists on 2.16.0, works, and actually reclaims.* All four candidates were probed: `session/close`, `session/terminate` and `_kiro.dev/session/close` each answer **-32601 Method not found**; only **`_kiro.dev/session/terminate`** works, returning `{}` in ~2 ms. **No documented replacement has appeared**, so the private-extension dependency stands exactly as feared — but the extension itself is real rather than hopeful: terminating one session **freed 3 processes and 172.6 MB**, it is **per-session** (a sibling session prompted fine afterwards, `end_turn`), and the terminated handle is properly gone (prompting it returns `-32603` with a typed `data: "No session found with id"`). **Critically for the dispatch-and-resume shape: terminate removes the `.lock` and leaves the `.json` intact**, so a terminated session stays resumable later. That makes an idle sweeper a straightforward design rather than a gamble — the memory lever works, it is just undocumented.
  - *Verified — `--agent` binds to **every** session on the process, not just the first, and neither it nor `--trust-tools` validates its argument.* The flag's help text says "when starting the first session", which describes when it is *read*, not what it scopes to: three sessions created under `--agent kiro_planner` all returned `modes.currentModeId: "kiro_planner"`, against `kiro_default` for an unflagged control. So one agent choice covers a whole multi-session process. **But a name that does not exist is accepted silently** — `--agent definitely-not-an-agent-xyz` spawned normally and fell back to `kiro_default` with no error and nothing on stderr, exactly as `--trust-tools` accepted a non-existent tool name. Neither flag fails loudly, so a client that depends on either must **read the setting back and assert it** (`currentModeId` from the `session/new` response) rather than trusting that the flag took.
  - **Verified 2026-07-31 — MCP startup is ~97% of the marginal session cost, and agent choice controls it. This is the largest single lever on this entry.** Same measurement method, `-a`, three sessions per configuration:

    | configuration | procs @ N=3 | RSS @ N=3 | marginal/session | MCP init notifications | warm create |
    |---|---|---|---|---|---|
    | default agent | 11 | 758.5 MB | ~151 MB | 11 (2 distinct servers) | 0.49-0.79 s |
    | `--agent kiro_planner` | **2** | **291.0 MB** | **~4.6 MB** | **0** | **0.006-0.01 s** |

    **The whole marginal cost is one MCP server.** `~\.kiro\settings\mcp.json` defines four servers, two enabled: **`playwright`** (stdio, `node …@playwright\mcp\cli.js`) and **`atlassian`** (HTTP, `mcp.atlassian.com`); `zoho` and `msgraph` are `disabled: true`. That maps exactly onto the measured `+3 procs` per session — `node.exe` + `cmd.exe` + `conhost.exe`, i.e. one stdio server spawned through a shell — while the HTTP server costs **zero** processes, consistent with `mcpCapabilities: {http: true}` from the handshake. Attribution is structural rather than per-process (tree totals were measured, and `cmd`/`conhost` are single-digit MB), but it is tight: **dropping the one stdio server captures ~97% of the saving while HTTP MCP servers can be kept for free.** *Caveat on the counter*: 11 notifications for 2 servers across 3 sessions means `_kiro.dev/mcp/server_initialized` fires more than once per server per session — use it as a presence signal, not a count.

    Without MCP the **process count does not grow with session count at all** — it stays at `kiro-cli.exe` + `conhost.exe` however many sessions are open — and marginal memory falls **33x**. The cost model therefore is not one model but two: **~306 + 151N MB with MCP**, **~277 + 4.6N MB without**. `kiro_default.json` sets `mcpServers: null` but carries `includeMcpJson`, so the default agent's MCP set arrives from `mcp.json`; `kiro_planner` does not pull it.
    - *The actionable form is not "use `kiro_planner`"* — that is a planning agent with its own prompt and tool set, not a general dispatch target. It is that a **PowerAtlas-specific agent controlling its own MCP set** captures nearly all of the saving while keeping whatever prompt and tools are wanted. And the trade is much smaller than "lose MCP": since only the **stdio** server carries the cost, a dispatch agent can keep every HTTP MCP server for free and drop only `playwright`. What that costs is browser automation inside dispatched sessions — a narrow, checkable question rather than a general capability loss.
    - **Decided 2026-07-31 — keep the default MCP servers. The lean-agent lever is closed and should not be re-proposed.** Dispatched sessions get the same MCP set as any other kiro-cli session, browser automation included. The consequences are accepted knowingly: the applicable cost model is **~306 + 151N MB**, not the lean one; session creation stays at **~0.5-1.4 s** rather than ~0.006 s; and every resumed session pays MCP startup again.
    - *Consequence for `MAX_SESSIONS`* — **acted on 2026-08-01, and the marginal figure moved again.** The old hardcoded 3 was priced against the superseded ~254 MB; at ~151 MB it read as 2.5x too conservative and **8** as the defensible replacement. That is what shipped: `acp_max_sessions` is config-driven with a default of 8, bounded 1-16, read once at startup. The limit is now the runaway-dispatch safety valve this bullet asked for, with the idle sweeper doing the real memory management. Measured at the cap rather than extrapolated from three sessions, the marginal cost is **3.0 processes / 177.8 MB** per session — eight concurrent sessions are 26 processes / 1,501 MB against a 2-process / 79 MB bare agent. The in-product cap message quotes 178 MB accordingly.
    - *And the sweeper's TTL should be generous, precisely because MCP is kept.* Every sweep-then-resume cycle re-pays MCP startup, so an aggressive TTL trades ~151 MB of idle memory for repeated multi-second stalls on the user's next interaction. Tens of minutes, not minutes. In the lean configuration an aggressive sweeper would have been nearly free; that option went with the decision above. **Shipped as `acp_idle_ttl_seconds`, default 1800** (30 minutes), bounded 300-86400, on a 60 s tick — the generous end this bullet argued for.
  - **Verified — the memory lever is an undocumented kiro extension, and this is the largest risk to anything that holds sessions open.** The cost model above is only bounded if sessions can be closed, and **`session/close` does not exist** on 2.14.2 (`-32601 Method not found`). What works is **`_kiro.dev/session/terminate`**, found by reading strings in the binary — a private method with no documented contract, which a release can withdraw without notice. It does work: one close measured **-5 processes and -253 MB**, and removed the session's `.lock`. A client that plans on N concurrent sessions is therefore betting the memory ceiling on a kiro-private extension; a build without it can only free memory by exiting the agent.
    - *The bet was taken, with a bounded downside — 2026-08-01.* The shipped sweeper calls that private method and **degrades rather than breaks** if it disappears: a failing terminate is logged and the pass continues, so the failure mode is memory growth, never a dead background task or a crashed app. Exercised deliberately by pointing the sweeper at a method the agent does not implement — 23 consecutive failures over 120 s left the task alive and the session correctly un-claimed, and restoring the method swept it on the next tick.
  - *Verified — other capabilities*: `session/cancel` interrupts a running turn cleanly (`stopReason: "cancelled"` at 8.01 s, after 118 chunks), and is best sent as a **notification** rather than a request — in that form, measured on 2.14.2, the outstanding `session/prompt` returns `stopReason: "cancelled"` in ~0.11 s and the session takes the next prompt on the same conversation. `session/set_mode` validates (`-32603` on a bad mode); ~~`session/set_model` accepts any string including nonsense without error, so its effect is unverified~~ — **verified 2026-08-03 on 2.16.0: `session/set_model` works and really changes the generator.** It returns `{}` and the switch is behavioural, not cosmetic: a session pinned to `qwen3-coder-next` answers "QWEN" when asked its model family, one pinned to `minimax-m2.5` answers "MINIMAX", 3/3 sessions each. **The reason it matters is a defect it fixes.** Unlike `--agent`, which binds to every session on the process (bullet above), **`--model` binds to the *first* session only** — sessions 2+ silently revert to `chat.defaultModel`, measured as `currentModelId: claude-sonnet-4.6` under `--model claude-haiku-4.5`. `acp.py` neither sends `set_model` nor reads `models.currentModelId` back from the `session/new` response, so at `MAX_SESSIONS: 8` seven of eight sessions run the default model whatever was asked for. The drift is invisible in latency; what exposed it was `_kiro.dev/metadata`'s `contextUsagePercentage`, which is tokens-over-window and so reads exactly 5x apart on a 200k vs a 1M model. This is the same "read the setting back and assert it" lesson the `--agent`/`--trust-tools` bullet above draws, on a third flag. Absent (`-32601`): `session/history`, `session/list`, `session/select_model`, `session/set_effort`, `session/close`, `_kiro.dev/session/compact`, `authenticate`, `fs/read_text_file`.
  - **Product-relevant caveat: creating and prompting MUTATE the user's store — attaching, on its own, does not.** A load-plus-prompt grew a real user session's `.jsonl` from 17,057 to 17,665 bytes and moved `updated_at`, so any surface that *prompts* leaves turns in the user's history even if it presents as read-only. Two refinements measured 2026-07-26. **`session/new` writes `<sid>.json`, `<sid>.jsonl` and `<sid>.lock` at creation, before any prompt** — every session such a surface opens is a permanent artifact among the ~13,300 already there, and the prototype had to enumerate the store by `cwd` before and after each phase to keep its own count honest. But **`session/load` alone leaves the transcript byte-identical** — `.json` and `.jsonl` are untouched and only the `.lock` is rewritten, which a graceful close then removes. So a genuinely read-only viewer of exited sessions *is* available; it is the turn and the creation that write, not the attach.
  - *Risks*: young protocol subject to breaking changes; the binary **self-updated mid-spike** (2.14.0→2.14.1, then →2.14.2 during the prototype), which a long-lived launcher will hit; Windows consumers must force UTF-8 and strip ANSI escapes.
  - **Verified — under `--trust-all-tools` an unprompted `shell` command executes, outside the session's own recorded scope.** Read back from the store's `.jsonl` transcripts 2026-07-26: kiro-cli ran a PowerShell command that read *and wrote* `<sid>.json` in the real session store, while that session's own recorded permissions were `allowed_write_paths: []` and `trusted_tools: []` — so `-a` overrides the recorded filesystem scoping rather than merely skipping a prompt. It fired on 2 of 3 sessions in one phase, and again mid-session on a turn that was not the first, so **the trigger condition is unknown**. Plan on an ungated command running on any turn; `-a` has to be re-decided before anything ships, and `session/request_permission` (which the protocol offers and the prototype never exercised) is the alternative.
  - *Product note*: a full ACP client turns PowerAtlas into an agent chat panel, a different product from the current launcher/dashboard, overlapping what Zed ships. That run has now happened — the state/control learning is what the bullets above record; committing the product to it is a separate decision, and still open.

- **[SPIKE — RUN 2026-07-31, kiro-cli 2.16.0] The permission round trip.   - **(1) The round trip completes, in both directions — this is the finding that reopens the rebuild.** `session/request_permission` arrives as **standard ACP**, not a kiro extension, and a standard response is honoured. *Allow*: the tool ran and returned its nonce, `stopReason: end_turn`. *Deny*: `tool_call_update` reported `failed`, the nonce never appeared anywhere in the transcript, and the turn still ended cleanly rather than hanging or erroring. **The denied run is the one that matters** — an agent treating rejection as advisory would look identical to a working gate until the moment it counted. Options offered are `allow_once` / `allow_always` / `reject_once`; **there is no `reject_always`**, so a policy engine can permanently say yes and never permanently no.

  - *The permission payload is richer than the spec requires, and this is the lever for unattended dispatch.* The `toolCall.title` carries **the full command line**, not just a tool name (`Running: Set-Content -Path "C:\…"`), so a policy engine can inspect what it is approving. The boundary half does not exist. Under `--trust-tools shell`, with the client configured to **reject everything it was asked**, a bounded canary test wrote a file **one directory above the session cwd with zero permission requests** — the client was never consulted. Trusting `shell` means trusting the whole filesystem at the user's privilege level. Two operational notes: tool names are `shell`, `write`, `read`; **`read` never prompts at all** (relevant to the read-only viewer, which therefore needs no permission handling); and `--trust-tools` **silently accepts names that do not exist** — a typo fails safe but gives no signal.

## kiro-cli v2 store (historical — removed 2026-09-17)

kiro-cli v2 stored sessions as flat files under `~/.kiro/sessions/cli/`:
- `<uuid>.json` — session metadata (`session_id`, `cwd`, `title`, `created_at`, `updated_at`, `parent_session_id`)
- `<uuid>.jsonl` — conversation content; NDJSON, each line `{"version":"v1","kind":"<kind>","data":{...}}`; kinds: `Prompt` (user), `AssistantMessage` (agent), `ToolResults` (tool output)
- `<uuid>.lock` — liveness lock; JSON `{"pid":<int>,"started_at":"<RFC3339>"}` while a session was open
- `<uuid>.history` — plain-text user input history

The SQLite DB at `%LOCALAPPDATA%\Kiro-Cli\data.sqlite3` (`conversations_v2` table) held a small number of "classic" sessions not otherwise stored on disk.

PowerAtlas removed v2 support in this plan. The `~/.kiro/sessions/cli/` directory is not cleaned; the files remain on disk but PowerAtlas no longer reads them. `kiro-cli chat --list-sessions` still does, so a workspace move rewrites them anyway (agent playbook, `providers/kiro/reference/kiro-cli-v2-local-data.md § Moving a workspace`).

## kiro-cli v3 sub-agent sessions — a full session folder with a `rootConversationId` (measured 2026-10-06, kiro-cli 2.28.0)

> What `data_kiro_v3._is_subagent_session` relies on. Measured by scanning every `~/.kiro/sessions/<hash>/sess_*/session.json` (key names only, no transcript content) after the dashboard's Live now tiles filled with `phase4-cycle2-regression · <reviewer>` rows that were not user sessions.

- **A workflow node or delegated sub-agent gets a session folder of its own.** It sits in the same workspace-hash directory as its parent, holds its own `session.json`, `messages.jsonl` and `snapshots/`, and has no `sub-executions/` folder. Of 376 stores, 67 were children: 61 under one love-nest parent and 6 under one system-engineering parent. All 67 sat in the same hash directory and the same `workspacePaths[0]` as their parent, and every parent was present on disk.
- **The only link is `rootConversationId`.** A child's `session.json` carries `rootConversationId: "sess_<parent>"` (a top-level session has no such key). The other keys that distinguish a child on this build: `workflowsEnabled: true` (all 67), `backgroundExecution`, `memoryConfig`, `memoryConfigSource` and `status`. `agentMode` was a custom or workflow agent in all 67 (`semantic_reviewer`, `wf-coder`, `wf-planner`, `wf-review-aggregator`, `dispatch-readiness-reviewer`), but a top-level session can use one too, so the mode is **not** the test. The parent's `messages.jsonl` names the child's id (66 of 67 children were found there, by plain substring search).
- **Not seen before 2026-10-06.** The earliest child was created at 19:02Z that day, on kiro-cli 2.28.0. Older sub-agents lived in the parent's `sub-executions/<uuid>.jsonl`, which PowerAtlas never lists. Whether 2.28.0 introduced the layout or the workflow feature was first used that day was not separated.
- **What PowerAtlas does.** `_cwd_to_sessions` and `refresh_stale_entries_for_cwd` skip any session whose `rootConversationId` is set and is not its own id, so the rail, the workspace session counts, the workspace recency and the Overview's Live now tiles show top-level sessions only. A child is still found by id (`find_session_workspace`, `_find_v3_session_dir`). The refresh skip matters: an unlisted child directory otherwise stays in the "new directories" set forever and forces a stale reload on every call.
- **Known gap: deleting a parent leaves its children on disk.** `delete_session` removes one `sess_<uuid>/` directory, and the children are unlisted, so they become invisible residue. Not changed here.
- **Not checked:** whether the Overview's Usage section counts a child's `messages.jsonl` tokens on top of the parent's.
- **Invalidated by.** A kiro-cli release that renames `rootConversationId` or starts writing it on top-level sessions. Re-run the scan: count `session.json` files whose `rootConversationId` differs from `id`, and confirm each names a session that exists.

### Sub-agent rollouts embed the parent's history

- **No usable window** (*full scan* of all 509, 2026-10-01). 446 carry an integer `subagent_history_start_ordinal` and 63 carry null, but a child's ordinals are its own numbering, and 433 of the 446 have no record at or after the start ordinal. Pre-start `token_count` cumulatives match the parent's in 3,185 of 6,770 cases (47 %) for `thread_spawn` and in 0 of 3,002 for `guardian`; a later review could not reproduce those two counts from the saved evidence, so read them as approximate. Summing sub-agent rollouts multiplies inherited history: a parent's cumulative total of 43.8 M sat beside children whose cumulative totals summed to 329.8 M.
- **Consequence.** PowerAtlas excludes every sub-agent rollout from `codex_tokens` and never lists one as a session, because no window can be recovered from a rollout. The sub-agent total comes from the state database instead: the lifetime `tokens_used` of each thread whose `source` starts `{"subagent"` and which was created in the window (`data_codex_state.subagent_usage`). It is drawn on its own line in the Codex Tokens block and never added to `codex_tokens`. When the database cannot be read the line is absent and the usage note says sub-agent threads are not counted. The reader reports a status beside the total (`codex_state_db_status`: `ok`, `absent`, `idle`, `stale` or `error`); `idle` means no `-wal` and `-shm` file sits beside the database, so PowerAtlas does not open it and the line is absent while Codex is closed (see "State database").
- **Measured size** (*full scan*, Codex 0.160.0, 2026-10-02, plan `261002_CODEX_LIVE_STATUS_CONTEXT_PRESSURE_AND_SUBAGENT_USAGE_FROM_STATE_DB`, Phase 0 items 1 and 7; the same threads read 24,530,488 tokens in the live read of 2026-10-05, see "State database"). In the 14-day window 3 top-level threads hold 37.0 M tokens and 26 sub-agent threads hold 24.2 M: 8 `thread_spawn` threads at 18.77 M and 18 `guardian` reviews at 5.40 M (8 of them with no tokens at all). The earlier "about 1.6 % of the top-level total, of unknown size" came from the six rollouts that had post-start records, which could only give a lower bound, and is withdrawn. The total is an upper bound, since a child's lifetime figure includes context inherited at spawn. In the window that inheritance is at most 0.58 M of the 24.2 M (2.4 %) by the first-event share, and 0 by the pre-start-cumulative match. **Sub-agent threads are therefore about 40 % of the Codex total in the window (24.2 M of 61.2 M), and that is an estimate resting on 3 top-level threads**; the exploration measured 4 top-level threads, one of which is now outside the window. Read any ratio between the two figures as an estimate. Method: a full scan of the 643 rows of `state_5.sqlite`, counts and sums only; `tokens_used` equals the rollout's last `token_count` total for every top-level thread that has one (see "State database"). Re-run: sum `tokens_used` over `threads` where `archived = 0` and `source LIKE '{"subagent"%'` and `created_at_ms` is inside the window, and compare it with the top-level rows.
- **Two inheritance measures that look different and are not** (*full scan*, codex 0.160.0, 2026-10-02, same plan, section 9, Phase 0 item 7). (A) The first-event share, the first `token_count` total over the final total, n=500 sub-agent rollouts: pooled median 7.3 % (p25 2.4 %, p75 22.4 %); `thread_spawn` (n=265) median 5.2 %, `guardian` (n=235) median 11.2 %; 71 of the 500 are 50 % or more. It counts the child's own first turn as well as anything inherited, so it is an upper bound on inheritance, not a measure. (B) The pre-start-cumulative match above reproduces exactly (3,185 of 6,770 `thread_spawn` events, 47.0 %; 0 of 3,002 `guardian`). It is a per-event rate dominated by forked children, whose history is copied from the parent: it matches in 42 of the 204 measurable children, and all 42 have `forked_from_id`, while no non-forked child matches. It describes those 42 children, not all sub-agents. In the window both agree that inheritance is negligible: at most 0.58 M of the 24.2 M (2.4 %) by (A), 0 by (B) (0 of 8 `thread_spawn` and 0 of 10 `guardian` children with events match their parent; 5 `guardian` parents are missing). The "upper bound" wording stays right for the whole store, where forked children can carry inherited history.
- **Invalidated by.** A Codex release that records a marker mapping a child's records to its own work. Re-run: the same per-kind comparison of pre-start cumulatives against the parent's.

### State database

> Measured 2026-10-02 (full scan of 644 rows, then 643) and 2026-10-05, **codex 0.160.0**, Windows 11, SQLite library 3.50.4, by the plan `261002_CODEX_LIVE_STATUS_CONTEXT_PRESSURE_AND_SUBAGENT_USAGE_FROM_STATE_DB` (section 9, Phase 0 results). All access was read-only; no id, path, title or message text was recorded. PowerAtlas reads this file only through `data_codex_state`, only as optional enrichment (the sub-agent line), and the rollout scan stays authoritative.

- **Where and how it is named.** `state_5.sqlite` in the Codex home folder itself, WAL mode, 42 columns in `threads`, 58 migrations (`state_<N>` with a higher N is plausible after an upgrade). A second, stale `state_5.sqlite` sits in a `sqlite` sub-folder of the Codex home: 737,280 bytes, last written 2026-06-14 (109.8 days old when measured), 29 columns, 115 rows, and **all six columns PowerAtlas selects present**, so a schema check alone would not reject it. Only the "Codex home folder only" rule and the file's age do, so the database location has varied between Codex versions. The live file's newest unarchived row was 0.2 days old. The reader takes the highest `<N>` in the Codex home, treats a missing column as "no database", and refuses a database whose newest `updated_at_ms` among unarchived rows lags the newest rollout activity by more than 1800 s.
- **Open mode.** `mode=ro` honours the WAL. `immutable=1` ignores it and missed the newest row (n=2 runs). `mode=ro&nolock=1` fails with `unable to open database file`. A missing column raises `sqlite3.OperationalError: no such column`, a missing table `no such table`. **Opening a WAL database `mode=ro` when no `-wal` and `-shm` exist creates both beside it, and they stay after close** (measured on a copy). With Codex running they already exist and the live files were unchanged by the checks. PowerAtlas therefore opens the database only when both sidecar files exist (the user's choice 2026-10-05) and reports `idle` otherwise; the cost is no sub-agent line while Codex is closed. A process that exits between that check and the open can still make the open create `-shm`. Live check, 2026-10-05, against the running Codex (the desktop app held the sidecars): the reader read the real database in place, status `ok`, 26 sub-agent threads and 24,530,488 tokens, equal to a direct read-only query, and no file appeared in the Codex home.
- **It does not disturb Codex** (2026-10-02, one throwaway session, n=1 run). While `codex exec resume` ran a turn that waited about 45 s (75.6 s in all, exit 0), a script opened the live database `mode=ro`, queried one row and a count and closed it about 10 times a second: 746 open-query-close cycles, 0 errors, the slowest 27 ms, no database or WAL error in Codex's output. Cold process: the rollout scan took 318 ms and the database query 8 ms (median of 5).
- **Fidelity against the rollouts** (2026-10-02, codex 0.160.0).

### Token records

- **Fields.** `total_tokens = input_tokens + output_tokens` in 749 of 759 sampled events, so cached tokens are a subset of input and reasoning tokens a subset of output. `last_token_usage` repeats across events: summing it over the top-level files gave 1,254 M against 852 M of final cumulative values, so it cannot simply be summed either. `token_count.info` exists in every era.
- **The cumulative series of one rollout can interleave two streams** (*full scan* of the 93 top-level rollouts, 2026-10-02: 14,017 `token_count` events, 86 files with `info`). The cumulative decreased 12 times: one true restart and 11 steps of a single rollout whose two series interleave (the other series runs up to 82 events in a row with the main one silent). Measured against each event's own last total: 5,048 deltas of zero (repeats), 8,860 equal to the last, none strictly between, 11 above it (each at least 329 times larger) and the 12 decreases. A sampled check of 759 events in 60 sessions had shown no decrease at all, so a sample cannot settle this.
- **The counting rule, and why it replaced two earlier ones.** The first rule counted a negative cumulative delta as a reset and added the new value; it counted the interleaved rollout 8.8 times its final cumulative (store total 2,507,476,672 against 858,485,862). Its replacement counted growth only within 4 times the event's last total; one lost event or one event with a zero last made it skip every later event of the file (a lost 100,000 event followed by turns of 1,000 counted 2,200 of 116,600). The final rule (schema 4) counts each event's own `last_token_usage` per field (input net of cached, cache read, output, cache write), unless the event's cumulative total equals one of the previous 8 events' totals (a duplicate, counted nothing). A first event whose cumulative exceeds its last counts its whole cumulative. An event without a usable last falls back to cumulative growth. The rule has no baseline to ratchet and no tuned constant. Store total 870,431,866; 84 files count exactly their final cumulative, the restart file counts its pre-restart total plus the restarted stream's total, and the whole difference from the 4x rule is the interleaved file (222,366,456 counted against 210,420,452 final; the ceiling of its own last totals is 12,190,095). An independent script with its own logic agreed with the parser on all 86 files.
- **Other usage facts.** Agent time is `task_complete.duration_ms` where present (trusted up to 24 h), else the `task_started` to `task_complete` timestamps capped at 30 minutes. `duration_ms` exists from 0.139; older agent time is an estimate. The 14-day cache-hit ratio shown by the dashboard (0.9471 on 2026-10-02) matched a recomputation from the raw files.
- **Context ratio behaves like context fill** (*full scan* of 13,957 `token_count` events, codex 0.160.0, 2026-10-02). `last_token_usage.input_tokens / model_context_window` has median 0.31, p99 0.80 and maximum 0.93, with none above 1.0. The window is 258,400 in 13,951 events and 272,000 in 6. After 20 of 20 compactions that began at 0.2 of the window or more, the next reading was about 0. PowerAtlas shows, per Codex day, the peak of 100 times that ratio (clipped to 0-100, window an integer from 1 to 10^9) as an estimate, in its own row of the Context pressure block beside kiro-cli's measured percentage; it never mixes the two. The ratio is the last request's input over the window, not a figure Codex reports, hence "estimate". Re-run: the same ratio over every `token_count` event, and the reading that follows each compaction.
- **Invalidated by.** A Codex release that changes what `last_token_usage` or `total_token_usage` mean. Re-run: the delta-against-last table above over the whole store; a result with deltas strictly between zero and last, or no interleaving file, would change the case for rule L.

### Writer lock

- **Protocol** (*source*, `codex-rs/rollout/src/writer_lock.rs`, 2026-10-01). `acquire(thread_id)` takes `thread-writer-locks/.coordination.lock` with a blocking whole-file lock, then opens `<id>.lock` (create, no truncate) and calls `try_lock` on the whole file (`WouldBlock` becomes "thread <id> already has an active writer"). The guard's `drop` takes the coordination lock, closes the file and removes the lock file. The first acquire per process removes stale lock files (it `try_lock`s each `*.lock` and deletes it when free). `delete_thread` takes the writer lock, then removes the rollout. `try_acquire_for_publication` holds the coordination lock through a rewrite, so the coordination lock can stay busy longer than a few milliseconds. Rust std's Windows lock range was not read, so "whole file" on Windows rests on the emulation.
- **Measured behaviour against a real `codex.exe`** (2026-10-01, `codex exec resume` on a throwaway session, because the screen was locked and no interactive TUI could be started; the first reading, that "an interactive TUI took no lock", was an artifact of the locked screen and is superseded: an idle `codex resume` TUI, and later a fresh `codex` terminal, did hold their locks, see "Lock owner"). Lock files are 0 bytes. While a turn of about 50 s ran, the probe read held from 0.2 s onward; after the clean exit the file was gone and the probe read not held. Lock files left by killed probe processes read as not held. A held lock file can still be opened for read-write. A TUI also creates a second lock for a helper thread that has no rollout. Resuming a held thread fails inside Codex.
- **The probe PowerAtlas uses** (`session_writer_locked`): open `.coordination.lock` without creating it, take a non-blocking one-byte lock on it, then open `<id>.lock` without creating it, try the same one-byte lock, release and close the thread file, and release the coordination lock last. Both files open read-only (`rb`): a read-only attribute made `r+b` fail, and locking needs no write access. Contention is retried 3 times at 5 ms, then the last cached answer is served, else not held; answers cache for 5 s, a busy answer for 1 s. Any other error reads as not held (fail open). Windows `msvcrt.locking` reports contention as EACCES or EDEADLOCK. A build without `.coordination.lock` reads as not held, so Resume shows for a held thread.
- **The tri-state the live rule uses** (`session_writer_state`, a sibling probe with its own cache; plan `261002_CODEX_LIVE_STATUS_CONTEXT_PRESSURE_AND_SUBAGENT_USAGE_FROM_STATE_DB`, decision D10). The bare probe above cannot tell "free" from "the probe failed", so the live rule needs three answers. `held`: another process holds the lock. `free`: the lock file is absent and `.coordination.lock` exists, or the probe took the lock itself. `unknown`: an invalid id, a stat error other than file-not-found, an `OSError` opening or locking `<id>.lock`, a coordination lock busy with no definitive answer younger than 60 s, and an absent `.coordination.lock` (an older Codex build). `held` and `free` cache for 5 s, `unknown` for 1 s. The bare probe keeps its behaviour on every platform, so the Resume gate did not change.
- **Why the coordination lock.** A plain one-byte try-lock on the thread file, with no coordination lock, made an emulated acquirer fail in 2.4 % to 4.1 % of 3,000 cycles (73 and 122 failures in two runs) and made the emulated lock-file removal fail in about half of the cycles (1,483 and 1,518), because a Python read handle omits `FILE_SHARE_DELETE`. A probe that takes the coordination lock first caused 0 failures in 3,000 cycles over 7,058 probes (4,240 found the coordination lock busy). A third-party issue (abruption/codex-unlock #55, no maintainer reply) reports 4,436 failures in 155,390 attempts for the plain probe.
- **The honest result.** Against a real `codex.exe`, 17 of 17 `codex exec resume` runs succeeded under a probe running at about 1 kHz (3 control runs and 14 probed runs, about 70,000 probes). The rejected plain probe was run the same way (12 real runs, about 44,000 probes) and **also caused 0 failures**. This harness therefore does not show the plain probe's hazard on a real Codex on this machine. The hazard rests on the source, the Windows emulation and the third-party report; the coordination-first probe is kept as the conservative choice and cost nothing observable.
- **What the lock means.** "Loaded in a running process", not "a turn is running". The desktop app holds the lock for every thread opened in a run until it exits ([#37450](https://github.com/openai/codex/issues/37450), Windows) and an SSH-orphaned TUI keeps it ([#44063](https://github.com/openai/codex/issues/44063)). PowerAtlas uses the lock to hide the Resume button, because Codex refuses to resume a locked thread, and, since `261002_CODEX_LIVE_STATUS_CONTEXT_PRESSURE_AND_SUBAGENT_USAGE_FROM_STATE_DB`, to find the lock owner that decides the live dot on Windows (next section; off Windows the earlier id-and-recency rule applies). It never marks the row locked or unopenable.

### Lock owner

> Measured with the Windows Restart Manager through `ctypes`, `psutil` and the lock probe, on **codex 0.160.0**, Windows 11: n=1 exploration run and a user-assisted run, both 2026-10-02 (plan `261002_CODEX_LIVE_STATUS_CONTEXT_PRESSURE_AND_SUBAGENT_USAGE_FROM_STATE_DB`, section 9, Phase 0 results and Phase 0b), then live checks on 2026-10-05. Counts, process kinds and timings only. The user-assisted run had one `codex` terminal started with `--no-daemon`, one default terminal (which uses the shared managed daemon), the desktop app and the VS Code extension, each with a thread, a second `codex resume` of a held thread, and a watcher logging lock and process transitions every 2 s.

- **Lookup cost.** `psutil.open_files` took about 5 s and the Restart Manager about 1.2 s in the n=1 run. In the user-assisted run one Restart Manager lookup took a median 0.55 to 0.66 s and at most 0.80 s (10 runs, two sessions); three held locks one after another took 1.5 to 2.4 s. Seven locks were held at once at one point and were not timed (about 4 to 5 s sequentially, by extrapolation). That is why the lookup runs on a background worker and is cached, not per poll.
- **Who holds a lock** (one holder per held lock in every case; PowerAtlas's own process excluded). A `--no-daemon` terminal: the terminal `codex.exe` itself, no helper token, a shell as its parent; it holds two locks from launch, before any prompt (the thread's and a helper thread's). A default terminal: a `codex app-server --listen --managed-daemon` child of the terminal, shared by later default terminals; it survives the terminal's exit (its parent is then gone) and its sibling `app-server` holds nothing. The desktop app: a `codex app-server` whose parent is `ChatGPT.exe`, holding two locks (a thread's and one with no rollout). The VS Code extension: a `codex app-server` whose parent is `Code.exe`. A refused second `codex resume` on a held thread was **not** a holder: it opens, shows "This conversation is open in another app" and blocks chat. The user also could not open an app-held or extension-held thread from the terminal, so Codex's own lock covers all four origins. An idle `codex resume` TUI (n=1, exploration) took its thread's lock plus a helper thread's, and both the Restart Manager and `psutil.open_files` named it as the holder of the lock file and the rollout.
- **The helper token alone does not decide.** The desktop app, the VS Code extension and a default terminal's daemon all run `app-server`, so the deny-list token cannot tell a terminal's lock from a desktop one. The `source` column cannot either: a thread hosted by the managed daemon has `source: vscode` (originator `codex-tui`), while `--no-daemon` and plain terminals have `source: cli`. PowerAtlas decides by the holder's process kind and parent. A holder that is a terminal process, or a `--managed-daemon` daemon, gives `terminal`. A helper whose live parent is a terminal gives `terminal`. A helper whose live parent is not a Codex process (`ChatGPT.exe`, `Code.exe`, any other host) gives `other`. A helper with a gone or unreadable parent, a start time that differs from the process snapshot by more than 2 s, a lookup that failed, or a mix of `terminal` and `other` holders gives `unknown`, never `other`.
- **Timing of lock and rollout.** The lock file is created at launch in both terminal modes. The rollout file appears at the first prompt (about 540 s after launch for one terminal; a different, earlier run saw a rollout about 15 s after launch with a first prompt). Both terminals' threads still held their locks after more than 5 minutes idle (rollouts created 387 s and 322 s earlier, no activity since).
- **Release timing.** The `--no-daemon` terminal quit: both locks went from held to free within the same 2 s poll and the lock files stayed on disk. The default terminal quit: its locks stayed held for about 59 s, then the lock files were deleted and the daemon kept running. A daemon-hosted thread's dot can therefore outlive its terminal by about a minute. After an idle `codex resume` TUI ended, its lock file stayed on disk, unlocked.
- **Live checks, 2026-10-05, codex 0.160.0** (PowerAtlas restarted for the checks; the throwaway Codex sessions were deleted afterwards).
  - An idle `codex resume` terminal resolved to `terminal` and stayed live for 5.5 minutes. A fresh `codex` terminal after one prompt stayed live (lock held, owner a terminal) for the whole 345 s watched, idle for most of it. Closing a terminal made its tile go within a few seconds. PowerAtlas restarted while a terminal stayed open: the tile was gone for about 16 s, then back as live.
  - **`codex exec resume` is not a terminal.** Its holder reads as `other`, so a `codex exec resume` run cannot be used to check the live dot, only the negative case. Checking the live dot needs a real interactive terminal and an unlocked screen.
- **Not measured.** `/new` and `/resume` inside one open terminal (the first terminal had quit before that measurement); a Linux or macOS mechanism (the lookup returns None off Windows); the terminal mode of the 2026-10-05 checks was not recorded, so the roughly one-minute lag of a daemon-hosted terminal's dot after quit was not re-checked against them.
- **Invalidated by.** A Codex release that changes who holds the lock (for example the desktop app or the managed daemon holding it for a terminal's thread, or a new helper subcommand that reads as a terminal), or a Windows change to the Restart Manager. Re-run: open a thread in each of a `--no-daemon` terminal, a default terminal, the desktop app and the VS Code extension; list the lock's holders with the Restart Manager and classify each by command line and parent; time one lookup; quit each and watch the lock files for 2 minutes.

### Handle sharing and the frozen mtime

- **Plain readers block Codex** (*measured* on a scratch copy, two processes, CPython 3.13.13, 2026-10-01). A reader handle from `open(path, "rb")`, `os.open` or `CreateFileW` with share READ and WRITE makes another process's rename and remove of the file fail (winerror 32) and a replace-over-target fail (winerror 5); an append by another process succeeds. A handle from `CreateFileW` with `FILE_SHARE_READ|WRITE|DELETE` (via `msvcrt.open_osfhandle`) allows rename and remove, but a replace-over-target still fails while any handle is open. Every Codex read in PowerAtlas therefore goes through one `data_codex.open_shared` helper and keeps handles short-lived (4 to 250 ms measured). The effect on a real `codex delete` is inferred from the scratch result, not measured.
- **A held shared handle did not disturb a running Codex** (*measured* 2026-10-02, three `codex exec resume` runs on one throwaway session, codex-cli 0.159.2, Windows 11). With a `FILE_SHARE_READ|WRITE|DELETE` handle open on the rollout for the whole run (6 s, and 24 s with a 12 s tool call), each run exited 0, appended to the same file, printed no error, and the file's index and creation time never changed (polled every 20 ms; the file was never missing). The handle read the whole rollout while Codex wrote. So Codex appends in place during a turn and does not replace the file. Not tested: compaction, archive, rename or delete of a thread while a handle is held.
- **The Windows mtime of a held-open rollout stays frozen** while its size grows (about 23 KB to 166 KB in the probe), so cache keys use (mtime_ns, size) and recency uses the last record's `timestamp`. A rollout appeared about 15 s after launch with the first prompt and was readable while Codex held it. A timestamp or mtime more than 5 s in the future is dropped, not clamped, so it cannot keep a session live.

### Process shape and the live dot

- **Terminal sessions.** An interactive TUI is its own `codex.exe` whose cwd is the workspace. A new session has no id on argv; `codex resume <id>` carries it right after `resume`. A bare `codex` with no prompt wrote no rollout and no lock in 30 s on 2026-10-01 with a locked screen; that is superseded: a fresh terminal creates its lock at launch and its rollout at the first prompt ("Lock owner"). **The live rule** (plan `261002_CODEX_LIVE_STATUS_CONTEXT_PRESSURE_AND_SUBAGENT_USAGE_FROM_STATE_DB`, decision D10) is: `resume <uuid>` on a command line is live (the id must be a UUID, so `resume --last` and `resume "<prompt>"` carry none). Otherwise, on Windows, the writer-lock state decides: `free` is not live; `unknown` falls back to the earlier rule, a Codex process in the workspace plus a rollout record newer than 300 s; `held` goes to the lock owner, where `terminal` is live (bypassing the folder gate), `other` is not live, and `unknown`, or a first sighting whose lookup is still pending, falls back to the earlier rule. Off Windows the earlier rule applies unchanged. Real runs of the earlier rule (2026-10-01): `codex resume <id>` made its row live about 3 s after the process appeared; a bare `codex` in a workspace with a recent record made that row live 1.1 s after it started and cleared 1.1 s after it ended. With only the desktop app's daemons running, 0 of 93 rows were live. `fork <uuid>` is a TUI but never an id carrier.
- **Daemons and helpers** (measured process table, desktop app running): the desktop-owned `codex.exe` runs as `app-server` (with `-c` options) and `exec-server` (with `--remote` and `--environment-id`); a managed daemon runs `app-server --listen unix:// --managed-daemon` and `app-server daemon pid-update-loop`. The desktop main process is `ChatGPT.exe`, its Chromium children carry `--type=`, and helper binaries (`codex-code-mode-host.exe`, `codex-computer-use-swift.exe`, `codex-windows-sandbox-service.exe`) do not equal `codex`, `codex.exe` or `codex.cmd`, so exact-name matching excludes them. Before the probes every running `codex.exe` was infrastructure.
- **The helper-subcommand deny-list (34 tokens).** A matched process is dropped when any later argv token equals one of: `app-server`, `exec-server`, `exec`, `e`, `mcp`, `mcp-server`, `plugin`, `login`, `logout`, `review`, `remote-control`, `app`, `completion`, `update`, `doctor`, `sandbox`, `debug`, `apply`, `a`, `queue`, `archive`, `delete`, `unarchive`, `migrate-rollouts`, `cloud`, `cloud-tasks`, `features`, `agents`, `help`, `daemon`, `responses-api-proxy`, `stdio-to-uds`, `execpolicy`, `tcp-tunnel`. It applies to Codex only. The list came from `codex --help` and `codex <name> --help` (0.159.2) and from the CLI source (hidden helpers `responses-api-proxy`, `stdio-to-uds`, `execpolicy`, `tcp-tunnel` and the `cloud-tasks` alias). `mcp-server` and `daemon` are not top-level subcommands in 0.159.2; they stay as a harmless over-deny for older builds.
- **Re-diffed on codex 0.160.0** (2026-10-02). `codex --help` and `codex help` are identical (137 lines, 27 commands). The only commands absent from the 34 tokens are `resume` and `fork`, both meant to be absent. Seven tokens are not in the help (the hidden helpers `cloud-tasks`, `execpolicy`, `responses-api-proxy`, `stdio-to-uds` and `tcp-tunnel`, and the retired `daemon` and `mcp-server`). Nothing needed adding.
- **Re-check the deny-list on each Codex upgrade.** Run `codex --help`, then `codex <name> --help` for every name, and read the CLI's `Subcommand` enum for hidden ones. The list now has two consumers. It still drops a helper from the live-dot match, and it marks a lock holder as `helper` rather than `terminal` in the lock-owner classification. A new helper subcommand missing from the list reads as a terminal, so a lock held by it gives a false dot, a false Working/Idle verdict and a false turn-end toast, **and the owner rule bypasses the folder and recency gates that bounded this error before** (the earlier rule also needed a record newer than 300 s). **Known false negative:** the list matches any argv token, so an option value equal to a token (`--profile review`, `-m e`) drops a real TUI, and so does a one-word prompt equal to one.
- **Desktop-held and VS Code-held threads still show no dot, verdict or Overview tile, now for a measured reason.** Their lock is held by a `codex app-server` whose parent is `ChatGPT.exe` or `Code.exe`, so the owner reads `other` and the row is not live (see "Lock owner"). Before the owner lookup the same result came from there being no terminal process. A thread hosted by a default terminal's managed daemon is the case the old rule could not separate: its `source` says `vscode`, yet its owner is `terminal` and it is live. So the 69 of 93 sessions that `source` calls `vscode` (2026-10-01) is no longer a count of rows without a dot. This follows the Claude Code rule and is accepted.

### Working/Idle verdict and turn-end toast

> Behaviour and live checks of plan `261002_CODEX_LIVE_STATUS_CONTEXT_PRESSURE_AND_SUBAGENT_USAGE_FROM_STATE_DB` (decisions D11 to D13; section 9, live QA of 2026-10-05), **codex 0.160.0**. Counts and timings only.

- **The verdict.** A terminal-owned row (lock `held`, owner `terminal`) gets `working` or `idle` from the last of three `event_msg` records in the rollout tail: `task_started` is working, `task_complete` and `turn_aborted` are idle. Records are matched by `type` and `payload.type`, never by substring, because rollouts quote these words in tool output. The first read takes the tail through `open_shared` (256 KiB, widening to a 2 MiB cap); after that only the bytes appended since are read while the file is still the same one grown by appends (a hash of its head and of the 4096 bytes before the read offset), so a turn longer than the tail window keeps its verdict, and a long gap since the last look reads only the newest 2 MiB window once. A line longer than one read (1 MiB) is skipped to its newline. No verdict (a neutral dot) when no such record is known, when a working verdict's newest record is older than 30 minutes (a stuck turn), or when a working turn is stamped in the future or has no timestamp. No approval record exists (see "Record shapes"), so Waiting cannot be proven and "Working" can include a turn that waits for approval. The rail refreshes about once a minute and the Overview tiles every 2 s, so a rail dot can lag a tile by up to a minute.
- **The toast.** One daemon thread ticks every 5 s and sends one toast per new `task_complete` record of a terminal-owned thread, only while notifications are on. A thread's first sight records the end of its last complete line, so earlier turns never toast. A turn that ends before the watcher first sees the lock (about one tick) can be missed. At most 3 toasts per thread per tick and 6 per tick overall are sent, the rest coalesced; a lock that appears after the watcher's first tick with no rollout yet starts at the start of the new rollout, so its first turn still counts; the label is the workspace folder name only.
- **Live checks, 2026-10-05.**
  - *Verdict:* for a real terminal turn of a 100 s command, the tile verdict was Working at 15 s and Idle at 119 s; after a PowerAtlas restart in the middle of a second turn it was Working at 38 s and Idle at 113 s.
  - *Rail dot lag, found by the same QA:* a Codex row stayed Working for over 100 s after its turn ended, because the dashboard listing returns no sessions for a workspace group that is listed lazily (an unpinned group), so the 60 s refresh never updated a row in a group the user had opened. Fixed in `8fdc368`: up to three open groups holding a live or Codex row are now refreshed on their own. With the fix (2026-10-06, one real turn of a 100 s command, n=1) the page's rail model for an opened group read Working at 50 s and Idle at 162 s, picked up by the next 60 s refresh after the turn ended at about 110 s; the dot was read from the page's rail model, not from drawn pixels.
  - *Toast:* one toast for a live turn. After a restart in the middle of a turn, one toast was sent when that turn ended: the first sight records the end of the file, so only the turn's end, appended later, counts. The plan had expected none for the turn in flight at startup; the user decided on 2026-10-05 to keep the shipped behaviour.
  - *Idle cost:* PowerAtlas process CPU over 30 s was 2.8 % of one core with no Codex terminal and 1.8 % with one idle terminal held (notifier on, no browser open); the difference is within noise.
  - *One rollout per thread:* a count of the rollout files under the Codex sessions folder on 2026-10-05 found 643 files for 643 thread ids, so no thread had more than one (the state database also held 643 rows that day).
  - *Hidden workspace:* on 2026-10-06 a 60 s terminal turn in a workspace tagged hidden gave no Overview tile and no toast log line (n=1; the tag was added to the config for the run and the file restored byte for byte).
  - *Not observed:* a thread open in the Codex desktop app, live. A usage limit on the Codex account twice stopped a run (a turn ended after 2 s with no command run), which is why the rail and hidden-workspace checks came last.
- **Invalidated by.** A Codex release that renames `task_started`, `task_complete` or `turn_aborted`, or that starts recording approval requests. Re-run: run a 100 s command in a real terminal and read the tile at 15 s and after the end; count `task_complete` records and toasts for the same turn.

## ACP v3 protocol limitations (no-wire-close, crash detection, MCP auth)

> Three structural findings about kiro-cli v3's ACP protocol. None is a to-do — they are hard limits of the current binary that constrain what PowerAtlas can do from the client side. Recorded together because they were all surface-level items in the same "ACP v3 Follow-up" roadmap section and have the same evidence pattern: a probe attempted a wire call, it returned -32601/-32603, and no alternative was found.

### Session close — no v3 method unloads a session; `session/delete` deletes it

**Measured on kiro-cli 2.23.1 (v3), 2026-09-23.** Wire close method status by build:

| Method | v2 (≤2.16.0) | v3 (2.22.0) | v3 (2.23.1) |
|---|---|---|---|
| `_kiro.dev/session/terminate` | ✓ `{}` in ~2 ms | `-32603` | `-32603 "Ext method has no persistence classification"` |
| `session/delete` | not tested | not tested | ✓ `{}` on success |
| `session/close` | — | `-32601` | `-32601` |
| `session/terminate` | — | `-32601` | `-32601` |
| `_kiro.dev/session/close` | — | `-32601` | `-32601` |

**`session/delete` (v3 2.23.1)**: Returns `{}` on first call; returns `-32000 "Something went wrong with the cloud session service"` on a second call (not idempotent). After a successful delete, the session is gone from kiro-cli's registry — subsequent calls referencing the session id return "Session not found".

**`session/delete` deletes the session from disk** (measured 2026-09-24, kiro-cli 2.24.0). Right after the call, `~/.kiro/sessions/<hash>/sess_<id>` was gone and kiro-cli emitted `_kiro/sessions/changed {"upserted": [], "deleted": ["sess_<id>"]}`. It is a delete, not a close: the dashboard can no longer list or resume the session. It is advertised in `initialize` as `agentCapabilities.sessionCapabilities.delete: {}` — an empty object, the ACP capability shape, which Python reads as falsy.

**Current status**: `close_session()` is local only and sends no wire call. Plan `260923_ACP_V3_SESSION_DELETE_WATCHDOG_MCP_STATUS` Phase 1 briefly sent `session/delete` from `close_session()` when the capability was advertised; it never fired in production, because its truthiness check read `{}` as absent. The 2026-09-24 QA of that plan measured the disk deletion and removed the wire path, because both callers (the Close button and the idle sweeper) mean "stop holding it", never "destroy its history". Not used anywhere, for close or for delete: the dashboard's Delete removes the session directory itself (`data_kiro_v3.delete_session`).

**v3 process model context**: In v3, all sessions share ONE process tree (kiro-cli.exe → bun.exe → node.exe). The ~3 processes / ~161 MB per session figure from v2 does NOT apply. With 27 sessions, the tree is 3 processes / ~655 MB total. Because the close is local only, kiro-cli keeps a closed session loaded for as long as its process lives; whether that holds meaningful in-process memory (within bun/node) is unverified. The sweeper therefore stops the agent once it has had no session for `AGENT_IDLE_RECYCLE_SECONDS` (900 s), which releases everything; the next session spawns a fresh one, as on first use after startup. The sweeper's memory value on v3 is freeing PowerAtlas's own data structures (history ring buffers, session meta dict), not kiro-cli processes.

**`_kiro.dev/session/terminate` dead on v3**: Kept working through v2's lifetime. The v3 error message "Ext method has no persistence classification" suggests the extension method registry was not updated when the v3 engine was built. Do not attempt to revive it, and do not substitute `session/delete`, which deletes the session (above).

**What `session/cancel` does** (distinct from close): cancels a running turn. Works as a notification; `stopReason: "cancelled"` arrives in ~0.11 s. Does not release session resources. Not a substitute for delete.

### Supervisor crash detection has a blind spot on Windows — kiro-cli.exe wrapper keeps the pipe alive

**Found 2026-09-19 on kiro-cli 2.22.0, confirmed on 2.23.1.** The actual process tree is `kiro-cli.exe` → `bun.exe` → `node.exe` (not just wrapper → node as originally stated). PowerAtlas's `Popen` holds pipes to `kiro-cli.exe`'s stdin/stdout. Both `bun.exe` and `node.exe` **inherit the write end of the stdout pipe** from their parent chain.

When `kiro-cli.exe` crashes or is killed (Task Manager, process kill), `node.exe` survives and still holds the write handle. The reader thread in `_reader_loop()` (`acp.py:3273`) calls `stream.read1(READ_BLOCK_BYTES)` in a loop; since the pipe is still open (write handle in `node.exe`), `read1()` **blocks indefinitely instead of returning `b""`** (EOF). The thread's `finally: self._post(self._on_agent_death, proc)` never fires.

**Observable symptom**: attended, the next request to the agent fails with `AgentDied` when `_send()` checks `proc.poll() is not None` (`acp.py:3265`). Unattended, the session stalls silently until someone sends a request.

**What already works**: the Windows job object (`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`) ensures the whole `kiro-cli.exe` + `node.exe` tree dies when PowerAtlas itself exits, which is the intended teardown guarantee. The blind spot is specifically the case where `kiro-cli.exe` dies during a live PowerAtlas session — `node.exe` outlives it (same tree but `node.exe` was already running and holds a handle the wrapper left open).

**Candidate fixes:**
1. **Periodic `proc.poll()` watchdog** — a background asyncio task that checks `proc.poll() is not None` every N seconds and triggers `_on_agent_death` directly, without waiting for the reader thread to see EOF. Does not kill the orphaned `node.exe` but detects the failure promptly.
2. **`PROC_THREAD_ATTRIBUTE_HANDLE_LIST` at spawn** — spawn `kiro-cli.exe` with `lpAttributeList` that explicitly excludes the stdout pipe from inheritable handles. `node.exe` would not receive the write handle and the pipe would EOF when the wrapper exits. Requires `CreateProcessW` via `ctypes` since Python's `Popen` does not expose this attribute. More surgical but complex.
3. **Windows job object notification** — set `JOB_OBJECT_MSG_END_OF_JOB_TIME` or `JOB_OBJECT_MSG_ACTIVE_PROCESS_ZERO` completion port on the existing job. Does not trigger on single-process exit within the job, so this does not help directly.

A watchdog (option 1) is cheap and correct for the attended case. Option 2 is architecturally cleaner (node.exe would not need to be reaped separately) but requires Win32 API usage. Both options are independent and could coexist.

**Stale-when**: kiro-cli changes its process model (e.g. a native single-process binary instead of a wrapper+node architecture) — re-check with `Get-Process kiro-cli | Select-Object -ExpandProperty Parent`.

### `_kiro/mcp/status` notification — MCP server status and OAuth URL confirmed

**Measured on kiro-cli 2.23.1 (v3), 2026-09-23.** `_kiro/mcp/status` is a real notification fired by kiro-cli v3. It is NOT a callable method (not in `extensionMethods`). Current PowerAtlas code logs it as an unhandled notification at INFO (falls through to `log.info` at `acp.py:4383`).

**Notification shape**: `{"sessionId": "<sess_id>", "servers": [...]}`

Each server entry:
```json
{
  "name": "atlassian",
  "status": "connecting" | "connected" | "failed" | "disabled",
  "authType": "oauth",           // only when OAuth is needed
  "failedAuthorization": true,   // only when auth attempt failed
  "authorizationUrl": "https://mcp.atlassian.com/...",  // when failedAuthorization
  "tools": [{name, description, disabled, inputSchema}, ...],  // when connected
  "_meta": {"kiro": {"resource": {"resourceType": "mcpServer", "source": {"origin": "user"}}}}
}
```

**Firing pattern**: Fires immediately after `session/new` (while servers are in "connecting" state), then again as servers reach "connected"/"failed"/"disabled". Also fires periodically (~50-60 min intervals, based on log observation). Sends ALL servers in one notification — state is replace-all, not delta.

**`authorizationUrl` is present** when `status: "failed"` + `failedAuthorization: true`. This was logged in PowerAtlas's own log today (2026-09-23 15:21:17) and on prior dates. The ROADMAP's statement "no `authorizationUrl`-bearing signal has ever been observed" was wrong — the signal exists, it was arriving all along, it just wasn't being handled.

**The feature is buildable, but not the way this section first said.** Opening `authorizationUrl` from the page does nothing useful: kiro-cli has already stopped its callback listener by then, and it keeps an MCP sign-in only in storage the ACP *client* provides. See the next section.

### MCP OAuth sign-in over ACP needs client-side secret storage

**Measured on kiro-cli 2.24.0, 2026-09-24**, from its bundled `acp-server.js` and live probes.

- kiro-cli keeps each OAuth MCP server's state (client registration, tokens, PKCE verifier, discovery) through the client, under keys `kiro.mcp.<connection hash>.{client,tokens,verifier,discovery}`. It does this only when `initialize` declares `clientCapabilities._meta.kiro.secretStorage: true`. The agent then sends the client `_kiro/secret/get` (`{key}` → `{value}` or `{}`), `_kiro/secret/store` (`{key, value}`) and `_kiro/secret/delete` (`{key}`).
- Without it, every agent start logs `Failed to connect ... Unauthorized` for Atlassian, even after a successful terminal sign-in. The terminal UI is an ACP client of the same agent that declares the capability (its log says "Client supports ACP secret storage"). Its store is its own. Ruled out as causes: the agent's cwd, and PowerAtlas's injected env vars.
- A sign-in opens a browser only in the "explicit-reauth" phase (user-started) or "lazy" (mid-session 401), never "passive" (agent start). It opens it by sending the client `_kiro/openExternalUrl` (`{url}`), and only if `clientCapabilities._meta.kiro.openExternalUrl: true`. The user-started trigger is `_kiro/mcp/resetServer` with `{sessionId, serverName, startOAuth: true}`, the terminal's `/mcp` sign-in. It answers only after the browser flow ends.
- kiro-cli receives the callback on its own `http://localhost:<port>/oauth/callback`, on the machine it runs on.
- Probe: with both capabilities declared, a Connect produced `connected` with 41 tools. A fresh agent given the same stored secrets reconnected with no browser.

**Implemented 2026-09-24**: `acp.py` `_SecretStore` (DPAPI-encrypted `acp-secrets.bin` in the config folder, Windows only), `_serve_secret`, `_open_external_url` (https only, one page per Connect press within 30 s of it, on the PowerAtlas PC's browser; `_kiro/openExternalUrl` names no server, so a lazy re-auth for another server inside that 30 s would also open), and the `mcp_signin` client frame (`_handle_mcp_signin`) behind the panel's Connect. Off Windows neither capability is declared, and OAuth servers stay "needs sign-in".

**Not in `extensionMethods`**: `_kiro/mcp/status` is a notification (server-to-client push), not a client-callable method. `extensionMethods` from `initialize` lists methods the agent handles; notifications it emits are not listed there.

**What remains unknown**: Whether the `authorizationUrl` is stable (same URL across multiple notifications for the same server requiring auth), or whether it rotates. This affects whether showing the URL as a button is safe vs. needing to use the latest notification's URL. The log entries suggest the URL appears for as long as the server is in the "failed" state and a new notification arrives when the state changes.

**Other new notification types confirmed on v3 2.23.1** (previously unknown, logged as unhandled):
- `_kiro/governance/state` — fires on session/new, unknown params shape
- `_kiro/tools/didChange` — fires on session/new, unknown params shape  
- `_kiro/powers/items_changed` — fires on session/new, unknown params shape

### Tool search must be forwarded at `initialize`, or one bad MCP schema fails every request

**Measured on kiro-cli 2.27.1, 2026-10-05**, from the agent's `kiro.log` and its bundled `acp-server.js`.

- `kiro-cli acp` does not read `~/.kiro/settings/cli.json`. The terminal UI reads it and forwards behaviour settings at `initialize` as `clientCapabilities._meta.kiro.settings` (its log: `[kas-settings] Built settings for initialize`). A client that sends none gets the agent's defaults. For `toolSearch` that default is off.
- With tool search off, every MCP tool's full schema goes to the model on every request. `custom_agent.tool_selection` in `kiro.log` shows it: 131 tools before the MCP servers connected, 284 after, against a steady 98 in the terminal UI on the same session.
- One session failed that way under PowerAtlas and ran fine in the terminal. Bedrock answered `TOOL_SCHEMA_INVALID` (`toolConfig.tools.N.toolSpec.inputSchema ... $.required: the items in the array must be unique`) on the first request after the zoho MCP server connected. 69 of its 128 tools list a `required` entry twice, e.g. `ZohoDesk_getTicket` lists `path_variables` twice. Claude Code rejects the same 69 tools up front. The failure names only a tool index, and the request never reaches a model, so no tool call is involved.
- The shape: `toolSearch: {enabled, minPct?, minTokens?}`, mapped from `toolSearch.enabled`, `toolSearch.minPct` and `toolSearch.minTokens`.

**Implemented 2026-10-05**: `acp.py` `_kiro_tool_search_settings` mirrors those three keys from `cli.json` into `_kiro_client_capabilities`, so an ACP session behaves as the terminal does and a user who turned tool search off stays off. This defers the broken schemas; it does not repair them. A zoho tool the model loads through tool search is still sent with its invalid schema, and a user who turns tool search off gets the original failure back.

**Repaired at the source 2026-10-05**: `~/.kiro/mcp-wrappers/dedupe-required.mjs` (outside this repo, user level) runs the zoho server and deduplicates `required` in each tool's `inputSchema`/`outputSchema` of `tools/list` results. Everything else passes through unchanged, and a tool without a duplicate is byte-identical. The zoho entry in `~/.kiro/settings/mcp.json` launches `node <wrapper> npx -y mcp-remote@latest <url>`, so the terminal UI and PowerAtlas both get valid schemas. Measured: all 128 tools kept with names and order, the 69 defective ones repaired (equal to an independent dedupe), and a live ACP agent with tool search **off** (232 tools per request, which failed before) ended its turn normally. To go back, restore `"command": "npx"` and drop the first two `args`. Any other MCP server that lists a repeated `required` entry needs the same wrapper in front of it; the symptom and the check are in the bullets above.

### An ACP session runs at `high` effort unless the client sets it; the terminal UI runs at `max`

**Measured on kiro-cli 2.27.1, 2026-10-05**, from a fresh `session/new` result, the stored `session.json` and the agent's bundled `acp-server.js`.

- `session/new` returns a `configOptions` entry `{id: "effortLevel", category: "thought_level", currentValue: "high", options: low | medium | high | max}`. `high` is the model default. A `thinking` option (`on`/`off`) sits beside it.
- The terminal UI runs at `max` because `cli.json` sets `chat.modelDefaults` (`output_config.effort: max`) and the UI applies it. `kiro-cli acp` does not read that file, so a PowerAtlas session ran one level below the same session in the terminal.
- The level is changed with `session/set_config_option` (`sessionId`, `configId: "effortLevel"`, `value`). The agent persists it as `effortLevel` in the session's `session.json`; a session that never had one has no such key.
- `kiro.log` never records the effort, so the stored `effortLevel` is the only evidence of what a session ran at.

**Implemented 2026-10-05** (`4a6902b`): `acp.py` `DEFAULT_EFFORT_LEVEL` is `"max"`. `_Supervisor._apply_default_effort` sets it right after `session/new`, and after `session/load` only when `_stored_session_effort_v3` finds no stored level, so a level chosen for a session is never overwritten on resume. It skips quietly when the agent does not offer the option or `max` is not among its levels, and a failed call is logged, never raised. Checked live after a restart: a new `/acp` session stored `effortLevel: "max"`. The value is a constant and ignores `cli.json`; exposing the choice is a roadmap item (*Expose the effort level*, `plans/ROADMAP.md`).

### `_kiro/workflow/*` notification family (probe 2026-10-08)

**Measured on kiro-cli 2.28.0 (`kiro-cli-chat 2.28.0`), 2026-10-08**, from a second `kiro-cli acp --agent-engine v3` process driven by a separate Python script (never the running PowerAtlas). Session settings: the production block (`thinking`, `knowledge`, `codeIntelligence`) plus `workflows` and `goal` both `enabled: true`, `modeId` `kiro_default`, `toolSearch` forwarded at `initialize`, scratch folder as `cwd`. Runs: one tool-list run (two sessions), four workflow runs (sequential, parallel, cancelled mid-run, deliberate-failure attempt) and one `session/load` of the finished sequential session. No `session/request_permission` fired in any run: `run_workflow` and the steps' `send_message` ran without asking. Plan: `plans/261008_ACP_SETTINGS_ALIGNMENT_AND_WORKFLOW_SUPPORT.md`, Phase 2 Step 2. Statements below are **measured** unless a bullet says *Inferred* or *Undetermined*. Ids are replaced by placeholders (`<parent>`, `<child-1>`, `<wf-1>`).

**Answers in one place**

- **Q1, which id is on the frame.** The outer `params.sessionId` is **absent** from `run_start`, from the first `node_start` of each step, from `node_complete` and from `run_complete`. It appears on exactly one frame type, the **second** `node_start` of a step, where it is the **child's** id. The parent id is always `params.parentSessionId`, on every workflow frame in all four runs. The child id lives in `params.sessionId` of that second `node_start`, in `finalState.root...children[].sessionId` of `run_complete`, and as `params.callerSessionId` of `_kiro/session/notify`. `node_complete` carries **no** child id: correlate it by `workflowId` + `nodeId` (+ `nodePath`).
- **Q2, failure signal.** `node_complete` has `status` (only `"completed"` observed) and `capturedOutput`. `run_complete` has `status` (only `"completed"` observed) and `finalState`, whose per-step entries carry `status`, `completionSignal` (`"success"`) and `completionSignalSource` (`"send_message"`). **A failing step was not obtained**: a step told to finish with `send_message` severity `error` produced a `_kiro/session/notify` with `severity: "error"`, and then no `node_complete`, `node_paused` or `run_complete` for the remaining 43 s of the capture (the child session stayed `in_progress`). So `error` severity is not a terminal signal, and the name of a failed `status` is **undetermined**. *Inferred, unverified:* a failed step would show a non-`"completed"` `status` on `node_complete`. Do not ship a `failed` branch keyed on a value this probe never saw.
- **Q3, parallel and loops.** Parallel: each branch has its own `nodeId`, `branchId` (equal to the step's `nodeId`) and child session id; the container node (`type: "parallel"`) gets its own `node_start`/`node_complete` with no `sessionId` and no `branchId`. `node_complete` frames of the branches arrived in the reverse order of the starts. **`loop_iteration` was not induced** (budget), so whether it reuses or mints child ids is **undetermined**. `paused`, `node_paused`, `steps_queued`, `recipes_changed` and `watch_poll` never occurred in any run.
- **Q4, cancel and prompt return.** `session/prompt` returns **before** the workflow ends: in the sequential run the response (`stopReason: "end_turn"`) came 2.0 s before `node_complete` of the last step and `run_complete`; in the parallel run 2.2 s before. The parent's turn ends once `run_workflow` has started the run and the model says it is waiting. After `run_complete` the parent runs an **agent-initiated turn with no `session/prompt` request**: its `agent_message_chunk` frames carry `_meta.kiro.agentInitiated: true` and `agentInitiatedReason: "workflow-complete-wake"`, and the parent's status on `_kiro/sessions/changed` goes `idle`, then `in_progress` at the instant the prompt returns, and `idle` again only after the wake turn ends (so `in_progress` spans the 4 s between the prompt response and the wake text). Cancel: `session/cancel` for the parent, sent the moment the id-bearing `node_start` of step 1 arrived, was answered 72 ms later with `stopReason: "cancelled"`. **No `run_complete`, `node_complete` or any other workflow frame followed** for the 74 s the capture continued. The step's child kept running (its `_kiro/session/notify` arrived 6 s after the cancel, and its `session.json` status was still `in_progress` with `contextUsage` records every 1.5 s when the process was killed). So cancelling the parent's turn neither stops the workflow nor produces `run_complete`. Not tested: the `workflow-cancel` slash command or any other cancel route.
- **Q5, Probe C.** Direct observable: a prompt asking for the exact tool names. A `workflows: true` session lists `run_workflow`, `inspect_workflow`, `update_workflow`, `send_message` and `save_workflow_definition` and **no** `invoke_sub_agent`; a session created without the workflows keys in the same process lists `invoke_sub_agent` and none of those five (the `invoke_sub_agent` suppression is now measured, not only read from the bundle). Cheap observable that the setting took effect: `_meta.workflowsEnabled: true` in the `session/new` result (and in `session.json`). Proxy: `available_commands_update` held 100 commands in the workflows session and 96 in the other, the difference being exactly `workflow-run`, `workflow-resume`, `workflow-status`, `workflow-cancel`. `session/new` result `_meta` has no tool inventory.
- **Q6, `workflow-progress` chunks.** None arrived on the **live** stream in any of the four runs (0 occurrences). They exist **on disk and on replay**. In the session's `messages.jsonl` each persisted entry is `payload.type: "user"`, `payload.source: "steer"`, `id: "wf-progress-<uuid>"`, `payload.content` = the frame serialised as a JSON string with a `method` key added, and `payload._meta.kiro.notification = {kind: "workflow-progress", workflowId, eventType}`. For the sequential run (read after the run) there were six: `run_start`, `node_start` and `node_complete` for each of the two steps, and `run_complete` with the full `finalState`. The persisted `node_start` is the **first** variant (no `sessionId`); the id-bearing second `node_start` is not persisted. The key is `_meta.kiro.notification.kind`, **not** `_meta.kiro.kind` (the plan's Step 7 sketch says the latter).
- **Q7, `session/load` of the finished run.** With the shipped block plus `workflows` and `goal` on, the load result had keys `_meta`, `modes`, `configOptions`. **Zero `_kiro/workflow/*` notifications were replayed.** The same six entries came back as `user_message_chunk` frames (shape below), in original order, interleaved with the rest of the transcript: the user prompt chunk, the `run_workflow` `tool_call` and `tool_call_update` (both `status: "completed"`), then `run_start`, `node_start` (step 1), a `system-notification` chunk with the step's message, `node_complete` (step 1), `node_start` (step 2), a `steeringClearedIds` boundary chunk, a `system-notification` chunk, `node_complete` (step 2), `run_complete`, a last boundary chunk. **Consequences for the Phase 2 design (Inferred from the measurements above, not themselves measured)**

- A router that reads `params.sessionId` and returns when it is not a string drops every frame except the second `node_start`. Route on the method prefix and take the parent from `params.parentSessionId`; the plan's `_resolve_workflow_parent` ladder reduces to that one field (keep the ladder only as a fallback when it is missing).
- Each step produces two `node_start` frames. The first has no child id; the second has it. Treat the pair as one start: register the crew entry from the second, tolerate the first.
- `node_complete` must be matched by `(workflowId, nodeId)`; build that map from the id-bearing `node_start`, or read child ids from `run_complete`.
- Container nodes (`type` other than `"step"`) have no child session; they must not create crew entries.
- The prompt returns before the run ends and a parent turn follows the run with no prompt request, so turn-end must not clear workflow children and the wake turn's chunks arrive with no request pending.
- A cancel of the parent's turn gives no `run_complete`; a staleness bound on active-workflow state is required, not optional.

**PowerAtlas side (implemented 2026-10-08, plan Phase 2; `acp.py`, `_Supervisor._on_workflow_notification` and the `_workflow_*` helpers)**

- *Routing.* `_on_notification` sends every method starting `_kiro/workflow/` to the router first, before `_stamp_activity` and the SC-1 early-frame buffer. The parent is `params.parentSessionId`; a frame with it missing, or naming a session that is not in `sessions`, is logged at INFO ("dropped") and changes nothing. The outer `sessionId` plays no part. The router stamps activity on the parent, so the prompt-silence watchdog does not cancel a long workflow turn. Every workflow frame is logged at INFO, plus the number of children tracked after each change. The line is built from a bounded copy of the params, then cut at 600 characters: strings are clipped to 200 characters (marked `...(N chars)`), lists and dicts to 20 items, and `run_complete`'s `finalState` is reduced to its status plus one `nodeId=status/sessionId` string per step (ids cut to 12 characters), non-`completed` steps listed first so a failure is never the part that is cut. A long `capturedOutput` therefore never reaches the log.
- *Handlers.* Real: `node_start`, `node_complete`, `node_paused`, `run_complete`. Logged stubs, no state: `run_start`, `loop_iteration`, `watch_poll`, `steps_queued`, `recipes_changed`, and the run-level `paused` (which deliberately clears nothing). `node_paused` and `paused` shapes were never captured; the handler assumes `node_paused` carries `workflowId` and `nodeId` (or the child's `sessionId`).
- *Crew entries.* Created only from the second, id-bearing `node_start` of a step; the first variant and container nodes (`type` `parallel` or `sequence`) make nothing. The entry has the same 12 keys as a sub-agent entry; every row also carries an internal `workflow` key (it marks the row for the turn-boundary eviction below), and a row closed with no verdict carries a transient internal `reaped` key too; neither is ever sent on the wire (`reaped` is removed when the row is reopened or settled). `role` is `nodePath` without its leading workflow id, joined with `/` (`run-both/step-a`), because `nodePath` is a list on the wire. `task` and `sessionName` are `agentName`, `action` is `running`, and `fan_out_id` is the parent's current `_active_fan_out_wave` (the payload filter compares against it). A repeat `node_start` never resets `startedAt`, `order` or history and never re-opens a step that finished; the one exception is a row closed with no verdict (status `stale`, below), which a repeat reopens because it proves the step is alive. `node_complete` is matched through an index `(parent, workflowId, nodeId) -> child` recorded at the id-bearing `node_start`. If that key already points at another child (a loop iteration or a re-run), the index now points at the new one and an INFO line names both. The `workflowId` is also recorded on the child (internal `_workflow_child_meta`), so `run_complete` finalises exactly the children of its own run, including ones whose index key was replaced.
- *`failed` is inferred.* `node_complete.status == "completed"` maps to `done`; any other non-empty status maps to `failed` with that string as the error text. `run_complete` applies the same rule to its top-level `status` for the children still tracked, scoped to the frame's `workflowId`. No failing value has ever been captured, so revise this when one is.
- *Waiting.* `node_paused` keeps the child tracked as `waiting`, sets the entry's `status` and `action` to `waiting`, and leaves `stoppedAt` unset so the elapsed timer keeps running. The crew row reads only `done` and `error` for its state and `action` for its text, so a waiting step shows as a working row labelled "waiting"; a failed step (done with error text) shows as errored. No template change was needed in `acp.html` or `index.html`. The `waiting` state is reachable only through `node_paused`, which was never captured, so it is untested against a real run. The pause signal the plan names, a step's `send_message` with severity `warning`, is expected to arrive as `_kiro/session/notify` (read from the plan, not measured), which PowerAtlas does not handle (it is only logged at INFO); the probe saw only `success` and `error` severities, so `warning` as the pause signal is read from the plan, not measured.
- *Lifetime and the staleness bound.* `_workflow_children` is cleared by `node_complete`, `run_complete`, crew eviction of the child's row, `close_session` and `_detach`. The bound does not clear anything: a RUNNING child unseen for more than 600 s (`_WORKFLOW_CHILD_STALE_S`, strictly greater than) is merely not counted by `has_active_workflow`/`workflow_state`, which are pure reads with no mutation or logging (any-thread safe). Its tracking entry and node index stay, so a late `node_complete` or `run_complete` still finds and finishes its row. A WAITING child (`node_paused`) gets a longer bound, 6 h (`_WORKFLOW_WAITING_STALE_S`), because a person may take hours; 6 h is a judgement, not a measurement. Staleness is liveness-only. Three loop-side writers act on the rows of stale tracked steps, and all close a row the same way (done, no error, `status` "stale", action "no longer reporting", the internal `reaped` marker; the pages show that action text for a done row with status `stale` and 'done' for every other finish). (1) The sweeper tick (`_sweep_once` -> `_Supervisor._workflow_reap`, isolated per parent, traceback logged once per persistent fault) does so for a stale, still-open step and sends one `subagents` frame per affected parent; it KEEPS the tracking entry and node index, so a late `node_complete` or `run_complete` still finds the row and settles it with the real status (done or failed). (2) The turn-end sweep does so for a stale tracked not-done row (logged at INFO), and the `_evict_crew_children` that follows drops the evicted row's tracking. (3) The user-cancel cascade does so for a stale tracked row and leaves fresh children running. Consequence of (2) and of the eviction at the next turn start: a real `node_complete` arriving after a turn boundary that evicted a REAPED row finds no registered child and is ignored ("no registered child" at INFO). A row of a step that finished normally is not affected: it is kept across the boundary while a sibling is live (below), and its tracking is gone by then anyway. Revive: a frame carrying a tracked child's own `sessionId` refreshes it even if it was past its bound (`_workflow_touch` reads the raw tracked entry), and reopens a row the reap had marked done (done false, timer running, action back to running or waiting). A row finished by `node_complete`/`run_complete` has no tracking left and is never reopened. The bound exists because a cancelled run emits no `run_complete`. A frame from the child's own `sessionId` (its transcript traffic) also counts as seen, because the workflow family is silent between a step's `node_start` and `node_complete`; without that a step longer than 600 s would read as dead. That refresh has an absolute cap: once a child is older than `_WORKFLOW_CHILD_MAX_AGE_S` (6 h since its `node_start`; a judgement, not a measurement) its own frames stop refreshing the clock and the normal bound applies, so a dead child that keeps emitting housekeeping frames still goes stale. The cap is logged once per child at INFO, and the start time is NOT reset when a waiting step resumes, so waiting time counts toward the 6 h. Workflow frames still refresh without a cap. Turn end does not clear anything, whatever its `stopReason`, and the turn-end sweep, the user-cancel cascade and the idle sweeper all leave a live child alone. `session/prompt` returns about 2 s before the run ends (measured), so the turn boundary falls mid-run; a FINISHED workflow row is therefore kept by the turn-start and turn-end eviction while the parent still has a live workflow child (so the panel header count does not fall at the first boundary), and goes as any done row does once none is live (at the next turn start after `run_complete`). The per-session cap of 64 rows still applies. A finished workflow child's `subagent_sessions`/`subagent_history` are released at the next turn start once its row is gone (workflow children only; legacy sub-agent behaviour is unchanged), and a viewer of the freed read-only view gets a note saying the step's view was released, not the generic "session closed" text. Bound: a child evicted at turn end keeps that history until the parent's next prompt or its close. Consequence: after the user presses Stop, a still-running step keeps showing as working until it finishes or goes stale. PowerAtlas has no way to stop a workflow: Stop sends `session/cancel` for the parent, which returns `cancelled` while the step keeps running (measured). The `workflow-cancel` slash command (listed in `available_commands_update`) was never tried.
- *Resumed sessions.* By the Probe B tool-inventory result, a session created before workflows were enabled gets the workflow tools when `session/load` carries the block, so its parent is in `sessions` and its live `_kiro/workflow/*` frames are handled like any other. What is not handled is a workflow that was still running when the session was loaded: replay sends no live frames and the `workflow-progress` chunks below are ignored, so its steps have no rows and no liveness until a live frame arrives (a `node_complete` for an untracked child is ignored). Roadmap entry in `plans/ROADMAP.md`.
- *`workflow-progress` chunks.* There is no handler: the key that identifies them is `_meta.kiro.notification.kind` (not `_meta.kiro.kind`), and the `user_message_chunk` branch deliberately does nothing with it. They change no state and nothing renders from them; the chunk goes down the ordinary user-chunk path, so a replayed session still shows the JSON as a user bubble. Replayed chunks never re-send live frames, so there is no double-apply to guard against.

### Workflow liveness: what the disk shows, and where the status call sites overlay it (probe 2026-10-08, plan Phase 3)

**Measured on kiro-cli 2.28.0** with a second `kiro-cli acp --agent-engine v3` process in a scratch folder, one run of the Phase 2 two-step prompt (production settings block plus `workflows` and `goal`). The parent's and both children's files under `~/.kiro/sessions/<hash>/` were sampled every 0.5 s (`session.json` `status` and mtime, `messages.jsonl` mtime and size). n = 1, two steps of about 4 s each. Throwaway sessions deleted afterwards.

- **Status literals seen** on `session.json`: `in_progress` and `idle`, plus an absent `status` key in the first sample of the second child, taken just after its folder appeared. `waiting_on_user` was **not** seen (no step paused).
- **`rootConversationId` format**: `sess_`-prefixed, equal to the parent's full session id (`sess_<parent uuid>`). A child's folder sits in the parent's hash directory. Confirms the "kiro-cli v3 sub-agent sessions" section.
- **The parent stays `in_progress` for the whole turn**: from the first write after `session/prompt` until the prompt response, then `idle` in the first sample after the response. No `idle` reading in between, including while the children ran. A child is `in_progress` from its creation until its step completes, then `idle`.
- **Timing differs from the Phase 2 runs.** Here `session/prompt` returned 5.0 s AFTER `run_complete` and no `agentInitiated` (wake-turn) frame arrived; the Phase 2 runs returned about 2 s BEFORE the end and had a wake turn. So the order of prompt return and `run_complete` varies from run to run, which is why liveness cannot hang on `inflight` and the staleness bound is mandatory.
- **The parent's `messages.jsonl` is written throughout the workflow.** Records during the run: `workflow-progress` entries at each `run_start`/`node_start`/`node_complete`/`run_complete`, a `system-notification` record in the middle of each step (the step's `send_message`), and the step's result record. The longest gap between parent writes from `run_start` to `run_complete` was 2.7 s (a 9.6 s gap came earlier, before `run_start`, while the `run_workflow` call was being prepared). `_LIVE_MTIME_WINDOW` is 300 s (`web.py`), so for this run the parent reads live by the existing rule (a provider process in the folder and a transcript written within 300 s) for the whole run.
- **Decision: Part B (`active_workflow_children` in `data_kiro_v3.py`) was not built.** The parent already reads live through the workflow in this run, and nothing in the rail or Overview gives a terminal kiro-cli row a Working verdict at all: a row this PowerAtlas does not hold gets only the neutral live dot (`_session_is_live`), so an inverse lookup of children could keep that dot lit and nothing more.
- **Silent step longer than 300 s: measured 2026-10-09 (kiro-cli 2.28.0), and the parent's transcript does go quiet past the window.** Same method (second ACP process, scratch folder, production block plus `workflows` and `goal`), one run of a one-step workflow whose step ran the PowerShell command `Start-Sleep -Seconds 330` and was told to send no message before it finished (no permission request fired). The parent's and the child's `session.json` `status` and the files' mtimes were sampled every 5 s; the record timestamps in both `messages.jsonl` files give the exact write times. A first run of the same design that was cut off by an API limit left the same picture on disk (parent gap 332.5 s, child gap 330.4 s, parent `idle` and child `in_progress` at the last sample, 335 s in).
  - *Parent writes:* the parent's last write before the step's output was its `session_start` record 25.4 s after its creation, which is the end of the turn that started the workflow (the model said the workflow had started, the turn ended, `usage_summary`, `session_event`, `turn_end`). Nothing was written to the parent's `messages.jsonl` for **331.1 s** (the longest gap in the file; the next longest was 12.7 s). The next write was the step's `send_message` text arriving as a `steer` record, then `node_complete`, `run_complete` and a wake turn. No heartbeat, no `session_metadata` record and no `workflow-progress` entry fell inside the gap.
  - *Parent `session.json` `status`:* `in_progress` until the turn ended at about 30 s into the run, then `idle` for the whole silent step (30 s to 363 s), then `in_progress` for the wake turn and `idle` again. So the parent's status reads `idle` while its child is running, and the on-disk status is no better a signal than the transcript.
  - *Child:* `in_progress` for the whole step. Its `messages.jsonl` was silent for **330.5 s** too: its `execute_pwsh` `tool_call` and `tool_result` records are written when the command ends, not when it starts, and it emitted no `session_metadata` records while the command ran. So the child shows no more activity on disk than the parent does.
  - *Live rule, applied to the sampled mtimes:* `_session_is_live`'s recency test (`_LIVE_MTIME_WINDOW` 300 s on the parent's `messages.jsonl` mtime, `web.py`) was true until the parent's file reached 300 s old and **false for 31 s** (the last 31 s of the 331 s gap), then true again at the next write. That is measured on the disk side only. The sampled `msg_age` first exceeded 300 between the 328 s and 333 s samples and was back under it at the 363 s sample.
  - *Classifier, replayed on the on-disk records:* `classify_kiro_v3` applied to the parent's records up to 10, 120, 299, 301 and 330 s into the gap returned `waiting` every time (the last meaningful record is the `assistant` text of the turn that started the workflow; `session_start`, `session_event`, `usage_summary` and `turn_end` are skipped or structural). Never `working`. This matters only for an ACP-held session, which Part A overlays; a terminal row gets no classifier verdict.
  - *Inferred, not measured (no real terminal session was run, and `snapshot.is_live` was not exercised):* a terminal kiro-cli row whose process was started without `--resume-id` is live only through the recency rule, so its live dot (and its Overview tile, which uses the same gate) **would drop for about (step length minus 300) s near the end of a silent step**, 31 s for this 330 s step, and light again at the step's next write. A row whose terminal was started with `--resume-id <session id>` stays live through the process-command-line signal and would not drop. The window grows one second per second of extra silence, so a step of 10 minutes would read not live for about 5 minutes.
  - *Consequence for Part B:* the gap is real and bounded, so Part B (`active_workflow_children`) is needed only if a dot that flickers off during a silent step longer than 300 s matters; it could only keep the neutral live dot lit, not give a terminal row a Working verdict. A silent step shorter than 300 s is unaffected. The contract is in the plan's Phase 3 Part B.

**PowerAtlas side, Part A (ACP-held sessions; `web.py`)**

- *One snapshot per request, on the loop.* `_workflow_states(supervisor, held)` returns `{session id: "working" | "waiting"}` from `_Supervisor.workflow_state`, built where `held` is built (`api_acp_sessions`, `api_dashboard_sessions`, `api_dashboard_overview_live`, `api_session_availability`) and passed down as a parameter (`_acp_listing`, `_acp_flat_listing`, `_overview_live`). The staleness bound itself (600 s running, 6 h waiting) is what ends a silent child; nothing pushes the rail when it passes.

## ACP permission wire shapes (measured 2026-09-23, kiro-cli KAS 2.23.1)

> Measured during Phase 7 of `260921_ACP_PERMISSION_PROFILE_AND_LOOPBACK_CREDENTIAL`, against the running PowerAtlas build and directly against `kiro-cli acp`. The first finding was a PowerAtlas defect and is fixed; the others are kiro-cli behaviour that PowerAtlas now relies on.

### The permission reply must use the ACP spec's `outcome` shape — a flat reply is read as a rejection

**Measured on KAS 2.23.1, 2026-09-23. Fixed in `91362a7`.** PowerAtlas used to answer `session/request_permission` with `{"result": {"optionId": <id>}}`. kiro-cli's tool-approval code reads the reply as `result.outcome.outcome === "selected"` inside a `try`. With no `outcome` key that read throws, and the `catch` logs `[ACP ToolApproval] requestPermission failed` and returns a reject. So **every Allow was delivered as a Deny**, and Deny still denied, which is why nothing looked broken.

- *Live, through PowerAtlas*: Allow on a shell prompt produced "The user rejected this tool call." and `status: failed`.
- *Live A/B, direct to kiro-cli*: the same kind of prompt answered with `{"result": {"outcome": {"outcome": "selected", "optionId": "accept"}}}` ran the command to `status: completed`, exit code 0.
- *The fix*: `_handle_permission_response` now sends the spec shape for Allow and Deny alike. `tools/acp_permission_probe.py` had the same flat shape and was fixed in the same commit. A re-probe confirmed Allow runs the command.
- *Why it stayed hidden*: the defect predates the permission profile. Sessions ran under this machine's allow-all `permissions.yaml`, so no prompt ever fired from PowerAtlas. The 2026-07-31 spike's Allow result (the `[SPIKE]` entry above) came from a standalone probe, not from `acp.py`'s reply code, so it did not catch this either.
- *Options offered on 2.23.1*: `accept` (allow_once), `reject` (reject_once) and `always-reject` (reject_always). There is no `allow_always`. The 2026-07-31 spike on 2.16.0 recorded the reverse (`allow_always` offered, no `reject_always`); read that as version drift.

### `session/load` binds the request's `modeId` when kiro-cli has no saved metadata for the session

**Measured on KAS 2.23.1, 2026-09-23, with no model calls.** The vendored KAS source selects `persisted ? persisted.metadata.agentMode : modeId ?? "vibe"` (`hydrateSessionForLoad`). Measured directly against `kiro-cli acp`:

- A load of a session id kiro-cli had never seen **succeeds**, with no error.
- With `_meta.kiro.modeId: "kiro_default"`, that load bound `kiro_default`.
- With the key omitted, it bound `vibe`.
- With `modeId: "poweratlas-acp"` while the permission setting was on (measured on the restarted build at `91362a7`), it bound `poweratlas-acp`, reported as both `agentMode` and `currentModeId`.

So the earlier finding that `modeId` is ignored on load holds only for a session that has persisted metadata. For one that does not, the request decides the posture. Since `91362a7`, PowerAtlas sends the mode a Default `session/new` would bind at that moment: `poweratlas-acp` while the permission profile is in effect, otherwise `kiro_default`. It never omits the key. Sending `poweratlas-acp` unconditionally would be wrong too, because of the next finding.

### Deleting a custom agent moves the sessions kiro-cli still holds to `vibe`

**Measured 2026-09-23.** When turning the permission setting off deleted `~/.kiro/agents/poweratlas-acp.md`, kiro-cli sent `_kiro/customAgent/not_found` with `requestedAgent: "poweratlas-acp", fallbackAgent: "vibe"` for a session it still held, followed by a `config_option_update` to `vibe`. `vibe` runs under the user-scope `permissions.yaml`, which on this machine allows everything. So turning the setting off also stops running sessions from asking, and the settings copy says so. This was first seen on a session PowerAtlas had already closed (PowerAtlas's `close` sends nothing over the wire, so kiro-cli keeps the session). It was then measured on a session that was still open: with the setting on, a Default session bound `poweratlas-acp` and asked before running `echo pa-mid-1` (denied); the setting was turned off; in that same open session, `echo pa-mid-2` then ran with zero permission prompts. The reverse direction, regenerating the file while a session is live, was not tested.

*Superseded 2026-09-25 by `260924_ACP_PERMISSION_MODES_YOLO_AUTO_MANUAL`.* There is no off state any more: no setting deletes the derived agent, so the path that moved live sessions to `vibe` no longer runs, and the settings copy now says that a change applies to sessions created afterwards. The kiro-cli behaviour above still holds for any deleted custom agent. The reverse direction is now measured (P-C, kiro-cli 2.24.0): rewriting the bound agent file mid-session is not picked up; the live session keeps its original rules.

### The kiro-cli permission model, and how the premise was corrected three times

**Recorded 2026-09-19 to 2026-09-21; moved here from `plans/ROADMAP.md` on 2026-09-23 when the interactive permission item shipped.** Full measurements: `plans/260921_ACP_PERMISSION_PROFILE_AND_LOOPBACK_CREDENTIAL.md` § 1 (Current State) and § 9 (Implementation Divergences).

- *The model, from kiro-cli's docs.* A rule is `{capability, match?, exclude?, effect}`, with `effect` one of `allow`, `ask` or `deny`. Capabilities are `fs_read`, `fs_write`, `shell`, `web_fetch`, `web_search`, `mcp`, `subagent`, `skill`, `power`, `context`, `diagnostics` and `sandbox_network`, plus the meta-values `all`, `builtin` and `filesystem`.
- *Six scopes contribute*: Kiro (hardcoded), administration, **user** (`~/.kiro/settings/permissions.yaml`), **workspace** (`~/.kiro/workspace-roots/<hash>/permissions.yaml`), **agent** (embedded in the agent profile) and session.
- *They merge with no precedence between them: the most restrictive effect wins* (`deny > ask > allow`). That is why an `ask` rule in an agent profile overrides this machine's allow-all user file, for sessions using that agent only. One measured exception to reading this too broadly: an agent that names no rule for a capability inherits the wider scopes for it, not `ask` (§ 9 Phase 0 Step 7), so the shipped overlay names every gated capability explicitly. *Superseded 2026-09-25: the overlay file is deleted; `compile_block` in `agent_profile.py` generates the block and, in Manual, names every capability including `power` for the same reason (`260924_ACP_PERMISSION_MODES_YOLO_AUTO_MANUAL` D-11, D-12).*
- *ACP policy presets* (`_meta.kiro.policyPreset`: `allow-all`, `edit-workspace`, `read-workspace`, `read-all`, `read-only-shell`, `dev-shell`) are allow-only. They remove prompts rather than add them, so a preset cannot tighten anything.
- *The premise, corrected three times.* (1) It began as "drop `-a` and decide each request automatically". (2) Corrected 2026-09-19 to "`-a` is gone and every request waits for a human, so an unattended session stalls". Measurement falsified that: an ACP session under `kiro_default` ran shell, read, write and an out-of-cwd absolute-path write with `session/request_permission` raised zero times across 5 sessions. (3) A first reading of that concluded no gate exists on `acp` + v3. That was wrong too: this machine's `permissions.yaml` reads `rules: [{capability: all, effect: allow}]`, so the mechanism was never missing, only turned off globally. kiro-cli's documented default is the opposite: `fs_read` on `./**`, read-only git and system info, and everything else prompting. The durable statement is a configuration fact, not a protocol limit, and the agent-profile `ask` rule is how PowerAtlas now fixes it per session.

### What else the live run settled for the `on` profile

- Loading the base agent's `resources:` (steering files under `~/.kiro/steering/`, outside `./**`) raised **no** prompt at session start.
- `./**` matches the absolute Windows path kiro-cli reports: a read of a file in the session folder ran with no prompt.
- `git status` ran silently; `web_fetch` prompted with `matchedRule {web_fetch, ask}`.
- Every prompt carried `consent.scope: "agent"` and `consent.source: "agent-profile"`, and kiro-cli reported the bound mode as `poweratlas-acp` with no coercion to `vibe`.
- Not settled: whether `*` in a shell pattern stops at `&&`. The shipped overlay uses exact strings, so it did not need the answer. *Superseded 2026-09-24 — settled on kiro-cli 2.24.0 (P-A2, P-0.8 below): kiro-cli splits a command at `&&` and the other separators and matches each part on its own, so `*` does stop there. It does not stop at `>`: `git status > x.txt` runs silently under `git status*`. The seed commands and the prompt-card prefill are exact strings for that reason.*

## ACP permission rules — measured 2026-09-24 and 2026-09-25, kiro-cli 2.24.0

> Measured for `260924_ACP_PERMISSION_MODES_YOLO_AUTO_MANUAL` (probe IDs P-A1 to P-C, P-0.1 to P-0.12, F-1 to F-7, and the Phase 1-3 probes; full tables in that plan's § 1 and phase notes). Every probe ran against a separate `kiro-cli acp --agent-engine v3` driven by `tools/acp_permission_probe.py`, never the running instance, with throwaway `pa-probe-*` agents and canary files. "Refused" means kiro-cli's `Tool call denied by user's permissions. Rule: …` text with no prompt.

**Shell patterns**
- Literal and case-sensitive (F-4): `*.ssh*` does not match `.SSH`. `\` is a literal character, so `*.config\gcloud*` does not match `.config/gcloud` (P-0.3). `*.ssh*` also matches `notes.sshx` (P-0.3).
- A command is split at `&&`, `;`, `|`, `&`, `||`, a newline and `$(…)`; each part is matched on its own (P-A2, P-0.8). A command wrapped in `powershell -Command "…"` is not split: it is matched as one string, so a block pattern such as `Remove-Item *` does not catch `powershell -Command "Remove-Item …"` (P-0.8i). The prompt's `consent.triggeringResource` names the part that hit the ask: the second part when the first was allowed (P-B), the first part under a bare ask row (Phase 3).
- Output redirection is not a separator: `git status > x.txt` runs silently under `git status*` and writes the file with no `fs_write` check (P-0.8). A pattern without `*` matches the whole command exactly, so redirection and extra arguments fall to the ask (F-3).
- Shell writes bypass every `fs_write` rule: `echo pwned > .kiro/agents/target.md` ran under an `fs_write` deny on that file (F-6).

**File patterns (`fs_read`, `fs_write`)**
- Case-insensitive, and relative and absolute spellings of a path both hit the rule (P-A3, P-0.11); `~` expands to the home folder (P-0.2); a forward-slash absolute pattern matches a backslash path of any drive-letter case (P-0.6, Phase 3). An absolute path inside the workspace arrives relativised, and a relative pattern matches relative to the workspace (Phase 3).
- 8.3 short names are not mapped: `SSH~1\dummy` read past an `fs_read` deny on `**/.ssh/**` (P-0.11), and `KIRO~1\settings\…` wrote past both an agent `fs_write` deny and kiro-cli's own `.kiro/settings` deny (F-5). A `**/ssh~*/**` glob closes it. `\\?\` and `\\localhost\C$` forms were refused (P-0.11). A trailing dot or space names a different, missing folder, not a bypass (F-2, F-5).
- Rules match a symlink's resolved target. A link inside a folder with an ask rule that points outside it escapes the ask (F-1), and a link to a denied folder escapes an `fs_read` deny (F-1b); a link whose target is inside the rule is caught (P-0.4). An ask on the absolute resolved target, in a path with a space, catches a write through the link. kiro-cli's built-in `kiro-scope:workspace-escape` refuses writes through a link whose target is outside the session workspace (Phase 1, 2026-09-25).
- An `fs_read` deny also filters the search tools: `grep_search` and `file_search` run but silently leave denied paths out of their results (P-0.1).

**Rule composition**
- An agent block with `all: allow` plus narrower `deny` rules refuses what the denies name and runs the rest with no prompt (P-A1). `deny` with `exclude` works, and a full Manual-shaped block loads without failing open (P-0.7). A blanket `ask` must carry `exclude` for any narrower `allow` to take effect: without it the ask still fires on what the `allow` names (`plans/done/260924-0525_ACP_PERMISSION_PROFILE_AND_LOOPBACK_CREDENTIAL.md` § 9, Phase 0 Step 4); with it the `allow` runs silently (P-B, P-0.7).
- `web_fetch`'s `consent.resource` is the host (`example.com`), not the URL, so only host patterns match (P-0.5). For `mcp`, `subagent` and `skill`, an allow pattern equal to `consent.resource` (`paecho/pa_echo`, `kiro_default`, `pa-probe-skill`) suppresses the prompt (P-0.9).
- A sub-agent runs under the parent session's agent rules: `kiro_default` spawned from a probe agent was refused on the canary (P-0.12).
- Non-ASCII patterns match: kiro-cli sends and reads plain UTF-8 (F-7).
- The bound agent file is read at session start only; a mid-session rewrite is not picked up (P-C).

**kiro-cli's built-in rules (`source: kiro-scope`), present even under `all: allow`** (P-0.10, F-5)
- Ask on writes to `.git`, `.vscode`, `*.code-workspace`, `.kiro/agents` and `.kiro/hooks`, in the workspace and under `~`.
- Deny on writes to `.kiroignore`, `.kiro/settings`, `~/.kiro/workspace-roots`, `~/.kiro/sandbox-state`, `~/.kiro/web-session`, `~/.kiro/powers/installed/*/mcp.json` and `~/.kiro/cloud-cache`. Nothing built in covers `.kiro/steering` or `.kiro/skills`.
