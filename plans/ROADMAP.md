## Automation & Workflows

- **Dispatch no-interactive tasks** — launch kiro-cli with `--no-interactive` and a prompt, fire-and-forget from the UI
- **Open session with specific prompt/skill** — generic prompt input, local/user skill execution with params
- **Template prompts** — save reusable prompt templates per workspace (e.g., "/qdev {latest plan file}" as one-click)
- **Scheduled tasks** — cron-like recurring kiro-cli launches (e.g., "/qdream every Sunday 10am in agent-playbook")
- **Chained launches** — "when session X exits, auto-launch session Y in folder Z" (pipeline mode)
- **Plan-file shortcuts** — detect plan files in `plans/` and offer one-click "/qdev on this plan" buttons

## Session Control & Integration

> Candidate paths to move PowerAtlas from read-only observation toward control, spiked over two rounds on 2026-07-24. Raw findings, wire logs, captured payloads and benchmark scripts are archived outside the repo at `Downloads\260724_PowerAtlas-spikes\` (`REPORT.md` for round 1, `REPORT-ROUND2.md` for round 2). Claims are marked *verified* (observed on this machine, with logs) or *unverified* (inferred from shipped code or docs, not executed). Pinned to Claude Code `2.1.219` and kiro-cli `2.14.0`/`2.14.1` — the kiro KAS bundle self-updated mid-spike, so code offsets rot.

> **Round 2's headline: the incumbent is fast but wrong, and the two biggest correctness defects are local bug fixes, not integration work.** Rank accordingly — the items below are ordered by value per day, not by ambition.

- **[P0] Fix the transcript tail size — `status_classifier.py:84`** — **DONE 2026-07-24 (`a973715`, hardened in `ee998c2`).** Default raised 4096 → 65536, and the read now widens and retries when a seeked read yields no complete line, so no fixed window can reintroduce the failure. Measured on 79 local transcripts: `None` verdicts 49% → 8%, **41.8% of sessions changed verdict**, every observed example `None → WAITING`. Cost 127 µs → 183 µs median, and 65536 proved no dearer than 16384.
  - *Verified defect*: `_read_tail_lines` defaults to `max_bytes=4096`, then discards the first partial line after seeking (`:109-111`). Claude Code JSONL lines are routinely larger than that — median 1,617 B, p95 **19,136 B**, max 154,917 B, with **24.7% of all lines exceeding 4096 B** and final lines disproportionately the large ones. So the tail read consumes everything and yields zero complete lines.
  - *Measured impact*: over 150 sampled Claude Code transcripts, **116 (77.3%) classify as `None`**, 111 of them recovering zero complete lines. All 116 disagree with the full-file verdict, which is predominantly `waiting`. Then `web.py:176-181` converts `None` to `"working"` (*"A running process = working"*) — **so a Claude Code session that has finished and is waiting for the user displays as working**, on roughly 3 of 4 sessions. That is a direct inversion of the signal the dashboard exists to provide.
  - *The fix*: raise the default. Measured sweep on the same corpus — 4096 → 77.3% `None`; 16384 → 12.0%; **65536 → 0.0%**. Cost is negligible: classification is tail-bounded, ~101 µs median, and a 56.79 MB transcript classifies in 161 µs vs 71 µs for a 64 KB one.
  - *Scope*: Claude-Code-specific. kiro-cli v2 is healthy (6.7% `None`) because its lines are smaller.
  - *Follow-up worth considering separately*: once the tail is fixed, revisit whether `None` should still fall back to `"working"` or to an explicit unknown state — the fallback is only safe when `None` is rare.
  - *Independent of every integration path below. Nothing here involves hooks, ACP, or `serve`.*

- **[P0] Fix provider matching — `presence.py:170-180`** — **DONE 2026-07-24 (`a973715`).** Electron helpers rejected via the `--type=` switch, removing 10 of 13 `claude.exe` matches. *Residual, accepted*: Claude Desktop's **main** process carries no `--type=` and still matches, so a phantom `live_cwds` entry remains possible if Desktop is launched from a project directory. The alternatives were install-path hardcoding or requiring a session file, which would trade instant workspace detection for a ~3 s startup blind spot.
  - *Verified defect*: `_match_provider` matches on basename only, so Claude Desktop's Electron subprocesses (`--type=renderer`, `--type=gpu-process`, `--type=crashpad-handler`) are classified as `claude-code` CLI sessions. 10-11 of 16 matched processes on this machine were Claude Desktop — provider precision ~35%.
  - *Currently latent*: their cwd is `C:\windows\system32`, which matches no workspace. That is luck, not design — launching Claude Desktop from a project directory would produce phantom live workspaces.
  - *The fix*: check the executable path, or exclude processes carrying Electron `--type=` switches.

- **[P1] Row-level identity for kiro-cli via lock files** — **DONE 2026-07-24 (`a973715`).** `live_sids` went 0 → 3 on this machine with correct cwd attribution; scan cost 51 → 68 ms median. Detail below retained as the rationale.
  - *The mechanism*: every live kiro-cli session holds `~\.kiro\sessions\cli\<session-id>.lock` containing `{"pid":…,"started_at":"<RFC3339>"}`. The session id is the filename; the sibling `<session-id>.json` carries `cwd`, `title`, `created_at`, `updated_at`. **That is exactly the session-id → live-process mapping `presence.py` cannot get from argv** — authoritative, written by kiro-cli itself, and available for sessions started anywhere including a terminal.
  - **The trap, measured — a naive implementation is worse than no detection.** Of 785 lock files on this machine, **21 have a currently-alive pid but only 1 is genuine**; the other 20 are PID reuse, their pids now belonging to `svchost.exe`, `firefox.exe`, `RuntimeBroker.exe`, `Kiro.exe`, `FortiESNAC.exe`. A "lock exists and pid is alive" check reports 21 live sessions when there is 1 — a 95% false-positive rate.
  - *The guard that fixes it*: require `|lock.started_at − process.create_time()| < tolerance`. Measured separation is enormous — the genuine lock is off by **1.2 s**, the closest impostor by **9,547 s**, most by millions. Any tolerance from ~30 s to an hour is correct. **Both clauses are mandatory.**
  - *Cost*: a full scan of 785 locks plus `process_iter(['pid','create_time'])` measures **~115 ms median** (min 102 ms; one 1.8 s outlier under concurrent disk load). That is above the current 51.9 ms poll, so it needs a stat-keyed cache — lock contents change only when a session starts or ends, and `os.stat` over 785 files is a few ms. Do not put an uncached 115 ms scan on the 5-second path.
  - *Verified applicable to real terminal sessions*: a user-run `kiro-cli chat -a` produced lock `ceb1ecf5-…` held by pid 11344 with `started_at` 1.2 s from that process's creation time.
  - *Process-tree note*: the pid in the lock is **not** the process the user launched. `kiro-cli chat` is a wrapper — `kiro-cli.exe chat -a` → `bun.exe tui.js chat -a` → `kiro-cli.exe acp --trust-all-tools`, and the **grandchild** holds the lock. Identity and liveness need only the lock; any "focus" or "kill this session" feature must walk up the tree to the process the user recognises.
  - *Known gap*: a `--no-interactive` one-shot creates **no lock and no persisted session at all**, so it stays invisible. It is also ephemeral, so this may not matter.
  - *Scope*: **kiro-cli only.** Verified that Claude Code has no per-session equivalent — `~\.claude\projects\` holds only `.jsonl` transcripts plus occasional `bridge-pointer.json`, and the sole `.lock` under `~\.claude\` is `ide\<port>.lock`, which maps an IDE instance to a workspace, not a session.

- **[P1b] Row-level identity AND live status for Claude Code — `~\.claude\sessions\<pid>.json`** — **DONE 2026-07-24 (`a973715`; status wired to display in `8d97162`).** The `status` value domain was read out of the binary rather than inferred from observation: `wDy=["busy","shell","idle","waiting"]` — **four values, including a real `waiting`**, plus a free-form `waitingFor` reason string. Precedence is asymmetric: `busy`/`shell` → working, `waiting` → waiting, and **`idle` defers to the classifier** because it covers finished, errored and never-started alike, and the classifier is the only source of `errored`. An unrecognised value degrades to prior behaviour, which matters for undocumented state in a self-updating binary. *Open follow-up*: `waitingFor` (observed `"sandbox request"`, `"input needed"`, `"dialog open"`, `"worker request"`) is the natural source for the **blocked-on-approval vs asked-a-question** distinction listed under Workspace Intelligence. Detail below retained as the rationale.
  - **Claude Code writes a per-process session file while a session is running**, containing everything the dashboard needs:
    ```json
    {"pid":51516,"sessionId":"3ee4f6fb-c84a-4681-8f91-e574a3c62300",
     "cwd":"C:\\Users\\...\\PowerAtlas","startedAt":1784920809496,
     "version":"2.1.219","kind":"interactive","entrypoint":"cli",
     "name":"poweratlas-d2","nameSource":"derived",
     "status":"busy","updatedAt":...,"statusUpdatedAt":...,
     "bridgeSessionId":"session_01Rf9..."}
    ```
  - *This is the Claude Code analogue of kiro-cli's `.lock` files, and strictly better* — it carries `sessionId` **and** a live `status` (`"busy"` / `"idle"`) with its own `statusUpdatedAt`. Observed correct in practice: a session actively working read `busy` while two idle ones read `idle`.
  - *Consequences*: it closes the row-level identity gap for Claude Code with a directory read; it may also serve **live status directly**, without tailing JSONL, for sessions that are currently running; and `startedAt` gives the same PID-reuse guard the kiro lock files need. `name` is a human-readable derived label the dashboard does not currently have.
  - *Why it was missed*: the file is already documented in the playbook, described as *"process metadata. Not useful for session content extraction."* True for content, and that framing is exactly why nobody looked at it for **liveness**.
  - *To determine before building*: how promptly `status` flips (`statusUpdatedAt` gives freshness, but the transition latency is unmeasured); whether the file is removed on clean exit and on SIGKILL; whether `status` has values beyond `busy`/`idle`; and whether it covers non-interactive (`kind` was `"interactive"` on all three observed). Also reconcile against `presence.py` — with 14 live `claude.exe` processes only 3 had session files, consistent with the rest being Claude Desktop (see the [P0] provider-match bug).
  - *Superseded*: the cwd+mtime correlation heuristic previously proposed here. Keep it only as a fallback if the session file turns out to be unreliable. The `sessions-index.json` observed in 1 of 20 project dirs remains an unexplained opportunistic cache, not a source of truth.

- **Baseline — measured 2026-07-24, at real scale** (84 workspaces, 1,709 sessions, 1.9 GB transcripts, 500-process table)
  - *Speed is not the problem*: a full status poll costs **51.9 ms median**, of which **43.1 ms (83%) is one psutil scan** and 9.4 ms is all classification and assembly — roughly **1% of one core** at the 5-second cadence. Worst case with all 84 cwds live: 104 ms for 1,897 classifications.
  - *Within the scan, `cmdline()` is ~96% of the cost*: `process_iter(["name"])` = 2.66 ms, adding `cmdline` = 57.8 ms. 213 of 502 processes are access-denied and still pay a failed syscall. ~0.1 ms per process, roughly linear in process-table size.
  - *Classification is cheap and size-independent*: ~101-113 µs median, flat from 64 KB to 57 MB because it is tail-bounded. One cliff: `_resolve_jsonl_path` costs 17.2 µs on a v2 hit but **303 µs on a miss** (`:56-64` falls through to iterating `~/.kiro/sessions/`) — an 18× penalty on exactly the sessions that fail to resolve. Worth caching negative lookups.
  - *Already solved, do not spend effort here*: workspace-level fresh-session detection is **11 ms**; session-end detection is **0 ms** at the scan layer (≤8 s end-to-end through the TTL and poll interval).
  - *The one real gap*: **row-level liveness matches zero sessions.** All 16 live provider processes had `session_id=None`, including the user's own interactive `kiro-cli chat -a`. `Snapshot.is_live()` returns `False` for every session, always. A `--resume-id` positive control matched in **0.124 s**, so the mechanism works — it is simply never exercised, because `launcher.py:80/86` emits those flags only for sessions PowerAtlas itself launches. Anything started in a terminal is invisible at row level for its entire life.
  - *Also measured*: the dashboard polls `POST /api/session-status` every 5 s (`templates/index.html:350`); card refresh runs 15 s × 8 then 30 s steady (`:344`). `discover_workspaces_with_counts()` costs 1,045 ms cold and ~0 ms warm — a once-per-refresh cost, not on the hot path.

- **Push-based session status via hooks (Claude Code + kiro-cli)** — replace polling with agent-emitted events. **Status: roadmap item, not scheduled. Mechanism fully proven over two rounds; deliberately not implemented pending the [P1] heuristic result.**
  - *Problem it solves*: `status_classifier.py` derives Working/Waiting/Errored by tailing JSONL transcripts behind a 5-second cache, and `presence.py` detects liveness by matching the session id in a running process's command line (`--resume` for claude-code, `--resume-id` for kiro-cli, `presence.py:63-66`) — so a freshly started session with no id on argv is not matched **at row level**. Note `presence.py:15-17`: workspace-level liveness already works via cwd tracking, so the gap is narrower than "sessions are invisible".
  - *Verified — mechanism works end to end*: a project-level `.claude/settings.json` drove 28 real hook events into a FastAPI endpoint across 4 sessions; 7 hook types fired, zero delivery failures.
  - *Verified — `SessionStart` fires for fresh sessions*, carrying `source: "startup"` (vs `"resume"`), a `session_id` byte-identical to the JSONL name `status_classifier.py:66-70` keys on, plus `transcript_path` and `cwd` outright — which removes the need for `_get_project_folder()`'s cwd-mangling. Confirmed three independent ways.
  - *Verified — Working vs Waiting is derivable from `hook_event_name` alone*, no transcript read. `Stop.last_assistant_message` even carries the final text. **Trap**: `SubagentStop` fires ~5s before the parent `Stop`; a rule that does not check `hook_event_name` (and `agent_id`, present on `SubagentStop`, absent on `Stop`) will flip a session to Waiting mid-work.
  - *Verified — the catalogue is far larger than documented*: 31 hook event types have schemas in the 2.1.219 binary. Only 8 were wired. The unwired set includes `PermissionRequest`, `PermissionDenied`, `StopFailure`, `PostToolUseFailure`, `TeammateIdle`.
  - *Verified — kiro-cli HAS hooks*, resolving the previous unknown. Not in `kiro-cli settings` (no hook keys) and not in the empty `~/.kiro/hooks/`, but **per-agent in the agent JSON** — both `agent_config.json.example` and the live `kiro_default.json` carry a top-level `"hooks": {}`. Five triggers, extracted from the binary: `agentSpawn`, `userPromptSubmit`, `preToolUse`, `postToolUse`, `stop`. Per-hook fields: `command`, `matcher?`, `timeout_ms?` (default 10s), `max_output_size?` (default 10240), `cache_ttl_seconds?`.
  - *Verified — kiro-cli `agentSpawn` DOES yield a session id, in the environment rather than the payload.* The JSON body carries only `hook_event_name`, `cwd`, `prompt`. But the hook subprocess environment contains `KIRO_SESSION_ID` (e.g. `ef360af4-9374-4931-8e4c-ba67c87e898f`), matching `kiro-cli chat --list-sessions -f json` exactly for that cwd — **the same identifier namespace `presence.py:65` already correlates on via `--resume-id`**. This resolves the load-bearing kiro-cli question affirmatively. `agentSpawn` fires ~1.17 s *before* `userPromptSubmit` and carries the prompt, so it is a genuine fresh-session signal.
  - *Caveat on that*: no transcript for that id was found at either path `status_classifier.py` knows (v2 `~/.kiro/sessions/cli/<id>.jsonl`, v3 `sess_<id>/messages.jsonl`). Its `"source":"classic"` points at the sqlite store (`data_kiro.py:16-25`), unopened. So the **id** is confirmed; transcript-path resolution for a classic-source session is undetermined.
  - *Verified — reactivity, measured in-band* (the tool printed `time.time_ns()`; the sink stamped arrival on the same clock): tool result → `PostToolUse` at sink is **266-321 ms**. Against the incumbent's ~2.5 s expected median staleness that is **~9× at the median, ~19× at worst case**. But decompose it: **~180 ms of that is the Python forwarder** (56 ms interpreter startup + 122 ms script) and only ~90 ms is Claude Code's own detect-and-spawn. kiro-cli is ~4× slower — `postToolUse` arrived **1,189 ms** after the tool's timestamp, with comparable forwarder cost, so ~900 ms is kiro-side.
  - *Verified — hooks BLOCK the session, serially. This is the dominant implementation constraint.* Identical 4-turn workload: no hooks 12,184 ms; 31 events wired with a fast forwarder **16,676 ms (+4.5 s, ~280 ms per event)**; a `sleep 5` hook **49,931 ms (+37.7 s)**; a `sleep 15` hook under `timeout: 10` **84,231 ms (+72.0 s)**. `duration_api_ms` stayed flat at 6.3-7.4 s across all four, proving the delta is pure hook blocking, not model latency. The configured `timeout` caps the damage but does **not** make hooks asynchronous. **A shipped implementation must not spawn a Python interpreter per tool call** — a compiled binary or fire-and-forget socket write is the single highest-leverage engineering item here.
  - *Verified — no delivery guarantee.* A session with three simultaneous failure modes (exit 1, unreachable endpoint, uncaught exception) completed `is_error: false` and *faster* than the clean baseline. Non-zero exit is logged at DEBUG only; nothing reaches the model or stderr. **Exactly one delivery attempt per event across all 205 records — no retries.** Good: a dead PowerAtlas endpoint degrades silently. Bad: a missed event is simply gone.
  - *Verified — `SessionEnd` does NOT fire on abnormal termination.* `taskkill /F /T` on a live session (21 events already delivered) produced zero further events, sink count unchanged 8 s later. **`presence.py` cannot be retired**; a hook-only model pins a hard-killed session at "Working" forever, and the process scan must *win* against stale hook state.
  - *Verified — delivery quality is otherwise good*: zero duplicates across 205 events; causally correct ordering in all 38 complete tool cycles; two simultaneous sessions in the same project interleaved with the correct `session_id` on every event and no cross-contamination.
  - *Verified — subagent attribution trap*: a subagent's own tool events carry the **parent** `session_id`. Only `SubagentStart`/`SubagentStop` carry `agent_id`/`agent_type`, so events between them cannot be attributed by `session_id` alone — the consumer must track the open-subagent window.
  - *Verified — 12 of 31 event types fire* (round 2 added `PostToolBatch`, `MessageDisplay`, `InstructionsLoaded`, `SubagentStart`, `CwdChanged`). **No event name is rejected by the settings schema — a typo is silently accepted and simply never fires.**
  - *Verified — `PermissionRequest` and `Notification` DO fire, but only with a real TTY.* Four headless approaches produced nothing (two with genuine `permission_denials` recorded); an interactive session produced both immediately. `PermissionRequest` carries `tool_name` and `tool_input` and lands **1.2 s after `PreToolUse`**; `Notification` follows ~6 s later with `notification_type: "permission_prompt"`, message `"Claude needs your permission"`. Since PowerAtlas watches sessions users run in real terminals, this is the *available* path, not a theoretical one.
  - *Verified — `Notification` has at least two types.* `permission_prompt` (above) and `idle_prompt` (`"Claude is waiting for your input"`), the latter firing **60.3 s after `Stop`** and **exactly once** across ~660 s of idling — a one-shot, not a heartbeat. Useful shape: `Stop` is the immediate turn-ended transition; `idle_prompt` is the "has been unattended a while" nudge that suits the toast-notification item under Workspace Intelligence.
  - *Verified — `PermissionDenied` never fires*, on either denial path, despite being in the binary schema.
  - *Verified — the two denial paths are distinguishable without it.* An **interactive rejection** yields `PreToolUse` → `PermissionRequest` → `Notification(permission_prompt)` → nothing (no `PostToolUse`, no `PostToolBatch`). A **`deny`-rule refusal** yields `PreToolUse` → `PostToolBatch` with no `PermissionRequest`, and `PostToolBatch.tool_calls[].tool_response` carries the reason verbatim: `"Permission to use PowerShell with command systeminfo has been denied."`
  - *Fallback for headless sessions*: a `PreToolUse` with no matching `PostToolUse` still marks blocked/denied — it flagged both denial sessions and none of 38 successful tool calls.
  - *Limitations, verified*: hooks instrument **only sessions started after installation** — a settings file written mid-session is not picked up by the running session. kiro-cli config is **per agent**, so install means editing every `~/.kiro/agents/*.json` plus project-local ones, and silently misses agents added later. kiro-cli has **no `sessionEnd`, no notification and no permission trigger** at all.
  - *Gotchas for implementation*: **kiro-cli executes hook commands through PowerShell, not cmd** — the Claude-Code-style `"<python.exe>" "<script>" label` form is a PowerShell parse error and 0 of 5 hooks ran; it requires the call operator `& "<python.exe>" "<script>" label`. kiro's `tool_name` is `execute_cmd`, not the `execute_bash` name in the agent config's `tools` array; its `stop` carries `assistant_response` (final assistant text, directly usable). `config.py:53` defaults the port to 0 (OS-assigned), so a hook command cannot hardcode one; `same_origin_guard` (`web.py:371-383`) 403s any POST lacking `Origin`/`Referer`. A file-spool transport sidesteps both.
  - *Untested*: whether kiro-cli's 10 s default `timeout_ms` blocks the agent the way Claude Code's does. Likely — it prints `✗ 0 of 1 hooks finished in 1.13 s` synchronously in turn output — but unmeasured.
  - *Effort*: **3-5 days.** Ingest + state machine ~0.5 d; config deployment ~1 d (Claude Code is one global file; kiro-cli is the tax); a low-overhead forwarder ~0.5-1 d (**prerequisite, not follow-up**); liveness-backstop reconciliation ~1 d (the real design work — reconciling fast-but-lossy hooks against slow-but-authoritative process scan); "waiting on human" ~0.5 d plus unresolved risk.

- **ACP client (kiro-cli + Claude Code)** — structured agent control over JSON-RPC instead of terminal scraping
  - *What it buys, verified on kiro-cli*: streaming `agent_message_chunk`s, `tool_call`/`tool_call_update` with real command and output, a clean `session/request_permission` round trip, `stopReason` as an authoritative idle signal, and `_kiro.dev/metadata` carrying live **context-window usage percentage** and turn duration — data unavailable from transcript tailing.
  - *Verified — `kiro-cli acp` works today with no auth at all* (`"authMethods":[]`). Framing is **NDJSON**, not LSP `Content-Length`. `session/new` takes ~3.2s (MCP startup dominates). Options: `--agent`, `--model`, `--effort`, `--trust-all-tools`, `--trust-tools`, `--agent-engine v1|v2|v3` (default v2).
  - *Verified — explicit slash-command invocation is ordinary prompt text*, not a proprietary RPC. `/tools` sent as prompt text returned in **1 millisecond** with a canned count — impossible for a model round-trip, proving agent-side interception. **This inverts the previous assumption**: `_kiro.dev/commands/available` is an agent→client *push notification* carrying the catalogue (24 built-ins, all 25 user skills as `prompts` with `serverName: "skill:config"`, 15 tools, live MCP server status); calling it as a client→agent request returns `-32601`. A standards-only client sees skills fine.
  - *Verified — `_kiro.dev/commands/execute` kills the agent process with exit code 0, no stderr, no JSON-RPC error.* Reproduced 2/2 across separate processes and two param shapes. Combined with the process writing nothing to stderr all session, a supervisor can trust **neither exit code nor stderr** for health. Also: one process is a **tree** (MCP servers are grandchildren — a plain kill leaks them).
  - *Verified — Claude Code ACP gate is OPEN.* The `@zed-industries/claude-code-acp` bridge hardcodes `settingSources: ["user","project","local"]` (`acp-agent.js:777`), which is the documented source loading `~/.claude/skills/`; prompt text passes through unrewritten (`:992-1006`); no `/q*` skill is on its `UNSUPPORTED_COMMANDS` deny-list. Static analysis only — never executed.
  - *Verified — two Claude Code SDK-path gaps*: `allowed-tools` in SKILL.md is **silently ignored** through the SDK, and the bridge **drops hook lifecycle events** (`hook_started`/`hook_progress`/`hook_response` fall through to `break;` under a `// Todo`) — precisely the data PowerAtlas wants. Statusline is absent from both packages.
  - *Verified — `session/load` attaches to pre-existing sessions with full context, including ones the user's own terminal kiro-cli created.* Loading a real 17 KB `agent-playbook` session and asking what it had been working on returned `Plan 260724_QCLOSE_DOCUMENTATION_RIPPLE_SWEEP_AND_QPLAN_DOC_IMPACT_WIDENING, Phase 4` — matching the stored `title` exactly, unguessable. Load takes ~3.8 s and **replays history as `session/update` events including `tool_call`/`tool_call_update` pairs**, so a client can rebuild the full timeline without tailing JSONL. This answers the scope-defining question: ACP is not limited to sessions PowerAtlas itself launched.
  - *Verified — concurrent attach is hard-refused, not silently shared.* Ownership is a lock file `~\.kiro\sessions\cli\<sid>.lock` containing `{"pid":…,"started_at":…}`, and **an ACP process takes the same lock a terminal session does**. Loading a busy session returns in 0.84 s: `-32603 … "Session is active in another process (PID 23316)"`. Lock not stolen; the owner's turn completed normally; the final `.jsonl` had zero unparseable lines and none of the intruder's content. **Stale locks are correctly ignored** — the guard is a pid liveness check, not file presence, so crashed sessions stay attachable while live ones are protected. Reading the lock file is a cheap pre-check PowerAtlas could do without connecting at all.
  - *Unverified*: the refusal above is ACP-vs-ACP. A live *interactive terminal* owner could not be scripted. See Open experiments — `USER-TEST-terminal-attach.md` is written and ready.

- **[P2] Replace filesystem session enumeration with `_kiro.dev/session/list`? — ANSWERED: no.** Measured 2026-07-24. It is slower on every axis and would *lose* coverage.
  - *It does work pre-session* — no `session/new` needed, so no MCP children and no ~3.2 s session cost; the enumerator process is a single `kiro-cli.exe` at **~88 MB** with zero children, and exits cleanly on stdin close. Per-entry shape is `{sessionId, cwd, title, updatedAt, messageCount}` — **`title` is included**, which round 2's key list missed.
  - **Timing kills it.** ACP **6.82 s cold** (n=6 fresh processes) and **5.87 s warm** (n=8, same process) versus a re-measured filesystem baseline of **1,041 ms cold / 0.004 ms warm** (30 s TTL cache). Spawn and handshake are free (0.08-0.11 s) — the list call itself *is* the cost. Payload is 1.80 MiB (~334 bytes/session); parsing it into PowerAtlas's shape is ~19 ms, i.e. negligible. So it is ~6.5× slower cold and effectively unbounded times slower warm, for the same data.
  - **It is the same data.** Set difference against the raw `sessions\cli\*.json` meta set is **zero in both directions** — `_kiro.dev/session/list` is the v2 filesystem store re-derived by kiro-cli, not a separate index.
  - **The apparent coverage win is sub-agent noise.** ACP returns 5,652 vs PowerAtlas's 1,120, but **all 4,532 extra sessions carry a `parent_session_id`** — they are the `/qreview` and `/qdev` sub-agent fan-outs that `data_kiro.py:63,113` deliberately skips. `1,120 + 4,532 = 5,652` exactly. No user session is hidden.
  - **Swapping would lose coverage.** PowerAtlas reports 58 workspaces to ACP's 55 because `data_kiro.py:76-89` merges sqlite `conversations_v2` keys, contributing 3 cwds that exist in no file store. ACP cannot see them.
  - *Undocumented param found*: `{"cwd": "<path>"}` **is honoured** and cuts a single-workspace query to **1.45 s / 659 sessions**. `limit`, `offset`, `cursor`, `includeSubagents`, `parentSessionId` are all **silently ignored** — unknown params raise no error, so absence of an error is not evidence a param exists. Still slower than the full 1,041 ms filesystem scan.

- **[P2b] Session stores PowerAtlas cannot currently see — a real coverage gap, quantified**
  - **23 v3 sessions** under `~\.kiro\sessions\<hash>\sess_*\` are invisible to PowerAtlas *and* to `_kiro.dev/session/list`. PowerAtlas has a v3 **read** path (`status_classifier.py:55-63`) but no v3 **discovery** path — `data_kiro.py` only globs `sessions\cli\*.json`.
  - *Who writes that store — answered 2026-07-24: not Kiro IDE, and nothing currently.* A live test creating a fresh Kiro IDE agent session left the count at **23**; the IDE writes to its own tree, `%APPDATA%\Kiro\User\globalStorage\kiro.kiroagent\workspace-sessions\<base64-cwd>\<uuid>.json`, which `data_kiro_ide.py:24` **already reads** — which is why that session appeared in the UI immediately. Combined with the 2026-06-18 → 2026-07-16 date range, the v3 store is a dormant artifact of the v3 migration period, not a live blind spot.
  - **11 "classic" sqlite conversations** in `conversations_v2` (`%LOCALAPPDATA%\Kiro-Cli\data.sqlite3`) have **no file on disk at all** and appear in neither candidate. PowerAtlas already merges their *cwds* for workspace discovery but not the sessions themselves.
  - **`kiro-cli chat --list-sessions -f json` is the only source that unifies all three stores**, tagging each entry with `source` (`v2`/`v3`/`classic`) — per-entry shape is the ACP shape plus `source`. From `C:\Users\QSylvestre.POLESTAR` it returned 277 sessions: 256 v2, **18 v3, 3 classic**. Cost ~2.13 s per query and it is **cwd-scoped, not global**, so covering 58 workspaces means 58 spawns. Worth considering as a targeted supplement for a single workspace, not as a global replacement.

- **[P3] `load_sessions()` is O(workspaces × files)** — latent scaling problem, not yet user-visible
  - Full per-session enumeration across all 58 kiro workspaces takes **60.5 s**, because `data_kiro.py:103` re-globs all 5,653 session metas *per workspace*. PowerAtlas does this lazily and behind a cache so it is not on any hot path today, but the cost grows with the product of workspace count and store size — and the store is already 5,653 files / 1.65 GB.
  - Fix shape: glob once, group by cwd, rather than filtering the full set per workspace.

- **`kiro-cli serve`** — persistent V3 agent server over WebSocket. **Status: CLOSED for status purposes on 2.14.1.** Two independent structural walls, the deeper one documented design intent rather than a bug. Revisit only if kiro-cli grows an auth flag or changes the execution-locality model.
  - *Verified — it is genuine ACP over WebSocket*, not a Kiro-specific protocol. `serve` is a thin wrapper launching `@kiro/agent/dist/server/acp-server.js --transport=ws --auth=acp-callback` under Node; the whole 20 MB implementation is readable on disk under a content-hashed per-release path. Flag surface is only `--port` (default 8082), `-v`, `-h`. **v3-only structurally** — a different binary, not a mode switch.
  - *Verified — it is a multiplexer.* Multiple simultaneous clients attach with `role=observer`; only the first `initialize` reaches the agent and later clients get a cached result, so a second observer is cheap and does not restart the agent. Good shape for a dashboard. (It also leaks its connection count.)
  - *Verified — session-mutating calls are blocked.* `session/new` and `session/load` hang forever: `serve` hardcodes `--auth=acp-callback`, in which the agent requests its token *from the client* via `_kiro/auth/getAccessToken` — and observer-role clients never receive that frame. `session/new` reaches the agent (~100ms, id allocated and logged) but never becomes addressable.
  - *Verified — `session/list` works unauthenticated, but returns the wrong sessions and a masked status.* It returned 23 sessions with `_meta.kiro.status`, `title`, `cwd`, `updatedAt`, `agentMode` and sometimes a model-authored `description`. Round 2 established that this is not the read-only status source it first appeared to be, for two independent reasons below.
  - **Wall 1 — two disjoint session stores, and `serve` reads the wrong one.** `kiro-cli chat` (including `--v3`) writes to `~\.kiro\sessions\cli\` — flat `<uuid>.json`/`.jsonl`/`.lock`, snake_case, and **no `status` field at all**. The KAS v3 agent writes to `~\.kiro\sessions\<hash>\sess_<uuid>\` — camelCase, has `status`. `session/list` returns only the latter. A busy test session and the user's own live `chat -a` both landed in `cli/` and never appeared; the `sess_*` count stayed pinned at 23. **The `cli/` store is exactly what `status_classifier.py` tails, so `serve` is blind to the sessions PowerAtlas watches** — and because that store has no status field, "read the kiro store directly instead of tailing JSONL" is not available as a shortcut either.
  - **Wall 2 — cross-process liveness is deliberately suppressed.** `hasActiveExecution` was extracted and is **purely in-memory** (`this.chatAgentExecutionQueue`, `this.executionQueue`, `this.activeExecution`) — no file read, no lock file, no IPC. `activeAwareStatus` therefore masks every externally-owned `in_progress` down to `idle`, with the source's own JSDoc explaining why: a crashed process leaves a stale `in_progress`, and *"reporting that as active would be wrong."* Proof: three sessions carry `"status":"in_progress"` on disk; one was returned as `"idle"` on the wire. Persisted census `{in_progress: 3, None: 11, idle: 9}` versus **23/23 `idle`** returned. Status enum is `["in_progress","waiting_on_user","completed","idle","failed"]`, and the non-`in_progress` values are **LLM-authored** (a system prompt instructs the model to set them) — best-effort, never reconciled.
  - *Verified — auth is structurally unreachable, and it is a bug.* `serve` hardcodes `--auth=acp-callback`, where the agent requests its token *from* the client — a **request**, therefore role-gated, therefore never delivered to an observer. And **no WS client can ever be `primary`**: searching the whole bundle for `"primary"` yields one minifier alias and two read-only comparisons, with **no assignment anywhere**. The `kiro-cli --remote <ws-url>` client the server's own banner advertises **does not exist** (`error: unexpected argument '--remote' found`).
  - *Verified — notifications are NOT role-gated* (correcting an earlier reading). Only requests check `role`; the notification path has no role reference, subscription is implicit on any message carrying a `sessionId`, and `_kiro/sessions/changed` is a connection-scoped broadcast to every client. Server→observer delivery was confirmed empirically. **This does not rescue the path**, because the emitters (`broadcastTurnStart`/`broadcastTurnEnd`) are subject to the same process-locality as Wall 2.
  - *Unverified*: **who authors the 23 v3 sessions.** `session.json` has no creating-client field and a grep of Kiro IDE storage timed out inconclusively; support is circumstantial (IDE-flavoured settings `modelId`, `autopilot`, `semanticReviewEnabled`, `ftaEnabled` absent from the CLI store). Decides whether the inventory serves anyone. Settled by creating one session in Kiro IDE and watching 23 → 24.
  - **Security, verified**: the server binds `0.0.0.0` with **no authentication on the WebSocket upgrade** — no subprotocol, no header, no token. Any local process or routable host can connect and enumerate every session on the machine; capabilities claim `sessionListScopes: ["workspace"]` but listing is machine-global in practice. There is no `--host`/`--bind` flag. Corroborated by an unrelated Firefox tab attaching to the probe server by accident. This is a property of the tooling and warrants a decision independent of whether PowerAtlas adopts the path.
  - *Scope note*: kiro-cli only. Provides no path for Claude Code, so it complements rather than replaces the items above.
  - *Effort*: **not worth estimating for status.** Building a WS/JSON-RPC client to poll `session/list` would cost ~1-2 days and return a constant `idle` for every session PowerAtlas cares about. The only honest remaining slice is a v3-session **inventory** (titles, cwds, `updatedAt`, `description`, status pinned to `idle`) at ~1-2 days, contingent on the authorship question above.
