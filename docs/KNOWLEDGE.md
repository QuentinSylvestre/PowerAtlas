## Session control and ACP — the 2026-07-24 spike record

> Candidate paths to move PowerAtlas from read-only observation toward control, spiked over two rounds on 2026-07-24. Raw findings, wire logs, captured payloads and benchmark scripts are archived outside the repo at `Downloads\260724_PowerAtlas-spikes\` (`REPORT.md` for round 1, `REPORT-ROUND2.md` for round 2). Claims are marked *verified* (observed on this machine, with logs) or *unverified* (inferred from shipped code or docs, not executed). Pinned to Claude Code `2.1.219` and kiro-cli `2.14.0`/`2.14.1` — the kiro KAS bundle self-updated mid-spike, so code offsets rot. The ACP entry below additionally carries re-measurements taken on kiro-cli **2.16.0** (2026-07-31 and 2026-08-01); where a bullet names 2.16.0, that figure supersedes the section pin.
>
> **The two correctness defects the spikes found (transcript-tail size, provider matching) and both row-level identity gaps shipped on 2026-07-24 as local fixes, with no integration work at all** (`a973715`, `ee998c2`, `8d97162`, `abc28db`). What remains below is genuine integration, ordered by value per day rather than by ambition.

  - *A Claude Code ACP half was scoped and dropped, 2026-08-04.* The `@zed-industries/claude-code-acp` bridge was analysed statically and looked viable, but it needs a separate npm bootstrap and was never started. Removed as a roadmap item rather than carried; the static-analysis findings are in git history for this file.
  - **The rebuild verdict at the foot of this entry is superseded, and how it was wrong is worth keeping.** It read "do not rebuild the chat client — ship the read-only half, gate the chat client on the permission experiment", on the argument that the prototype answered *chat* while the reason for the item was *unattended dispatch*. The permission experiment then ran (2026-07-31) and closed the first two blockers, and the product decision moved: the chat surface **is** the product. The rebuild itself was declined for a different reason than the one recorded below — `260731_...` D1 kept and hardened `acp.py` rather than rewriting it, because the module a rebuild would have discarded needed the least change and its 250 white-box tests had no seam to re-point. So "do not rebuild" survived; "not this shape, not yet" did not. The chat-vs-unattended distinction is still live: what shipped is a chat surface with a human present, and everything under `## Automation & Workflows` in `plans/ROADMAP.md` still turns on the unattended question.
  - *What it buys, verified on kiro-cli*: streaming `agent_message_chunk`s, `tool_call`/`tool_call_update` with real command and output, a clean `session/request_permission` round trip, `stopReason` as an authoritative idle signal, and `_kiro.dev/metadata` carrying live **context-window usage percentage** and turn duration — data unavailable from transcript tailing.
  - *Verified — `kiro-cli acp` works today with no auth at all* (`"authMethods":[]`). Framing is **NDJSON**, not LSP `Content-Length`. `session/new` takes **~5.4 s for the first session of a process**, spawn and handshake included, and **~2.5 s for each session after** — re-measured 2026-07-26 on 2.14.2, superseding the ~3.2 s single sample, which was neither the cold nor the warm case. **Both figures are themselves superseded on 2.16.0**: an eight-session run on 2026-08-01 measured **1.1 s** for the first and **~0.5 s** for each after, consistent with the 1.47 / 0.55 / 0.48 s reading below. Anything sized on the 5.4 s number is over-costed by roughly 5x on latency. MCP startup dominates the first one. Options: `--agent`, `--model`, `--effort`, `--trust-all-tools`, `--trust-tools`, `--agent-engine v1|v2|v3` (default v2).
  - *Verified — explicit slash-command invocation is ordinary prompt text*, not a proprietary RPC. `/tools` sent as prompt text returned in **1 millisecond** with a canned count — impossible for a model round-trip, proving agent-side interception. **This inverts the previous assumption**: `_kiro.dev/commands/available` is an agent→client *push notification* carrying the catalogue (25 built-in commands + 26 skill prompts as `prompts` with `serverName: "skill:config"`, 15 tools, live MCP server status); calling it as a client→agent request returns `-32601`. A standards-only client sees skills fine.
  - *Verified — `_kiro.dev/commands/execute` kills the agent process with exit code 0, no stderr, no JSON-RPC error.* Reproduced 2/2 across separate processes and two param shapes. Combined with the process writing nothing to stderr all session, a supervisor can trust **neither exit code nor stderr** for health. Also: one process is a **tree** (MCP servers are grandchildren — a plain kill leaks them). **Superseded 2026-08-12 for the object-form payload**: the kill was caused by using a *string* payload (the incorrect form); the TuiCommand *object* form `{"sessionId": sid, "command": {"command": name, "args": {}}}` is confirmed correct from tui.js and KiroCrew source analysis and is what PowerAtlas's `_handle_commands_execute` uses. The supervisor-trust note about exit code and stderr remains valid. Live probe (object form, output path, options shape) deferred to post-deployment. PowerAtlas `/acp` now dispatches slash commands via `_kiro.dev/commands/execute` with the TuiCommand object form (Phase 3, 2026-08-12).
  - **PowerAtlas `/acp` now handles three additional kiro notifications (2026-08-12, Phase 1/3); skills discovery added 2026-08-13 (Phase 1–4):**
    - `_kiro.dev/commands/available` — agent→client push carrying the full catalogue (`{commands:[{name,description}], prompts:[…], tools, mcpServers}`); no `sessionId` in params; attributed to the single inflight session. Probe-verified counts: **25 built-in commands** + **26 skill prompts** (each with `serverName: "skill:<name>"`). PowerAtlas stores both in `sessions[sid]`: commands under `meta["commands"]`, skills under `meta["skills"]`. Skills are extracted by `_parse_skills()`, which accepts entries from `prompts` (using `serverName.startswith("skill:")` as the discriminant) and from `available_commands_update` (using `_meta.kiro.type == "skill"`). Both a `"commands"` and a `"skills"` server frame are broadcast to subscribers; both are replayed to new subscribers in `_handle_subscribe`. A **`_pending_commands` single-slot buffer** on `_Supervisor` handles the race where all five `commands/available` notifications arrive during the `session/new` round-trip before `sessions[session_id]` is registered — the buffer is flushed immediately after session registration and cleared unconditionally in the `finally` block. A separate **`available_commands_update`** handler fires when `session/update` arrives with `sessionUpdate: "available_commands_update"` (mid-session agent mode switches); it re-extracts both lists from `params["update"]["availableCommands"]` and re-broadcasts both frames. The `/acp` slash-command palette (opened with `/`) shows both commands and skills in a flat list; skill entries are identified by a visible **`skill` badge** rendered alongside the entry name. Before the first `"commands"` or `"skills"` frame arrives the dropdown shows "Loading catalogue…"; after delivery a non-matching filter shows "No matching commands or skills".
    - `_kiro.dev/compaction/status` — agent→client push with `{status:{type:"started"|"completed"|"failed", error?}, summary?}`; no `sessionId`. PowerAtlas broadcasts a `compaction` server frame; `/acp` renders a system message ("Compacting conversation context…" / "Context compacted." / "Compaction failed."). On `completed`, the context-window meter is reset.
    - `_kiro.dev/clear/status` — agent→client push with no meaningful params; both tui.js and KiroCrew log/ignore it. PowerAtlas silently consumes it (`return` in `_on_notification`, no broadcast).
    - **Copy-to-clipboard button on code blocks** — labeled code blocks in `/acp` agent responses include a copy button (CSS class `.acp-md-copy`). Clicking it writes the code block's raw text to the clipboard via the Clipboard API, with a visual confirmation tick. No server round-trip; entirely client-side.
  - **`_kiro.dev/commands/options` is for argument completion, not command-name filtering (verified 2026-08-12).** Sending it with `command: ""` (empty command name) causes kiro-cli to exit with code 0, no stderr. The method is a client→agent **request** that expects a selected command name as `command` param and returns options for that command's arguments. When the user is still typing the `/prefix` to filter the command list, client-side filtering of the `commands/available` catalogue is the correct approach — no server round-trip. Only call `_kiro.dev/commands/options` after the user has selected a specific command, to populate its argument completions.
  - *Verified — `session/load` attaches to pre-existing sessions with full context, including ones the user's own terminal kiro-cli created.* Loading a real 17 KB `agent-playbook` session and asking what it had been working on returned `Plan 260724_QCLOSE_DOCUMENTATION_RIPPLE_SWEEP_AND_QPLAN_DOC_IMPACT_WIDENING, Phase 4` — matching the stored `title` exactly, unguessable. Load takes ~3.8 s and **replays history as `session/update` events including `tool_call`/`tool_call_update` pairs**, so a client can rebuild the full timeline without tailing JSONL. This answers the scope-defining question: ACP is not limited to sessions PowerAtlas itself launched.
  - *Verified — concurrent attach is hard-refused, not silently shared.* Ownership is a lock file `~\.kiro\sessions\cli\<sid>.lock` containing `{"pid":…,"started_at":…}`, and **an ACP process takes the same lock a terminal session does**. Loading a busy session returns in 0.84 s: `-32603 … "Session is active in another process (PID 23316)"`. Lock not stolen; the owner's turn completed normally; the final `.jsonl` had zero unparseable lines and none of the intruder's content. **Stale locks are correctly ignored** — the guard is a pid liveness check, not file presence, so crashed sessions stay attachable while live ones are protected. Reading the lock file is a cheap pre-check PowerAtlas could do without connecting at all.
  - **Corrected 2026-07-26 on 2.14.2 — the typed refusal is gone, and the relationship is inverted.** Measured live against a real terminal session holding the lock, the agent returns a bare `-32603 "Internal error"`: no PID, no text, indistinguishable from any other internal failure. So the **lock file is now the only thing that can name the holder**, not the cheap pre-check it was described as. And a pid-liveness-only pre-check would have been wrong *every time it fired*: of this machine's 803 lock files, 22 name a currently-existing pid and **all 22 are recycled** (svchost, firefox, RuntimeBroker, pwsh), created days to weeks after their lock was written; a repeat census at 804 locks found 25, again all recycled. A usable pre-check additionally requires the holder's process to have started at or before the lock's own `started_at`. Also measured: **`session/load` takes the lock too**, and locks survive the agent's exit — so a timed-out load leaves a lock naming your own agent, which reads as "active in another process" unless you recognise your own pid.
  - *Now verified*: the refusal generalises from ACP-vs-ACP to a live *interactive terminal* owner — driven end to end from `/acp`, which surfaces it as an in-use message rather than hanging.
  - *Verified — skills load the full SKILL.md body* (round 1's ~50% is now high confidence). Discriminator: flag names appearing only in `qmemory-eval`'s body Flags table while the frontmatter advertises different ones, with the wire catalogue entry confirmed to carry only the `description` string. Invoked with tools forbidden: **0 tool calls**, and it reproduced the script path, all four flags, and the five-row label taxonomy. Advertised set matches `~\.kiro\skills\` exactly — 25 each, set difference empty both directions. **Arguments inconclusive**: `/qsummarize-chat 1` honoured the body's output format but emitted 4 pairs rather than 1; cannot distinguish "argument never reached `$ARGUMENTS`" from "model ignored it".
  - *Verified — process model*: one process holds **multiple concurrent sessions** across different workspaces with no cross-talk (two parallel prompts: 3.71 s wall, not 6.75 s), so one process for everything is viable. But MCP servers spawn **per session**: **~2 + 5N processes and ~283 + 254N MB**, re-measured 2026-07-26 against a real supervisor — three concurrent sessions were **17 processes / 1,045 MB** against a **283 MB** one-agent baseline. That corrects the round-2 model in both directions: the per-session memory figure was ~20% high at 306 MB, and the process count was one short, the extra being the parent's own `conhost`. Time-to-first-token warm 1.88-2.14 s.
  - *Re-measured 2026-07-31 on kiro-cli **2.16.0**, and the model got materially cheaper — plus the close method was finally exercised.* Walking the agent's own process tree and summing RSS: **2 procs / 79 MB** at N=0, then **+3 procs and +150 MB per session** after the first (the first costs +374 MB because it pays the shared MCP/node startup). Three concurrent sessions are **11 procs / 754 MB**, against the **17 procs / 1,045 MB** on record — so the marginal session went from ~5 procs / 254 MB to **~3 procs / 150 MB**. *Caveat on the baseline*: 79 MB here vs the 283 MB recorded above is too large a gap to be version drift alone, and the likely reason is that MCP servers spawn on `session/new` rather than at `initialize`, so a genuine zero-session baseline has none running — treat the two baselines as possibly not measuring the same thing, and trust the **marginal** figure over the absolute. Session creation also collapsed: **1.47 s / 0.55 s / 0.48 s** for the first three, i.e. warm creation is now sub-second against ~2.5 s on 2.14.2.
  - *Verified — `_kiro.dev/session/terminate` still exists on 2.16.0, works, and actually reclaims.* All four candidates were probed: `session/close`, `session/terminate` and `_kiro.dev/session/close` each answer **-32601 Method not found**; only **`_kiro.dev/session/terminate`** works, returning `{}` in ~2 ms. **No documented replacement has appeared**, so the private-extension dependency stands exactly as feared — but the extension itself is real rather than hopeful: terminating one session **freed 3 processes and 172.6 MB**, it is **per-session** (a sibling session prompted fine afterwards, `end_turn`), and the terminated handle is properly gone (prompting it returns `-32603` with a typed `data: "No session found with id"`). **Critically for the dispatch-and-resume shape: terminate removes the `.lock` and leaves the `.json` intact**, so a terminated session stays resumable later. That makes an idle sweeper a straightforward design rather than a gamble — the memory lever works, it is just undocumented.
  - *Verified — `--agent` binds to **every** session on the process, not just the first, and neither it nor `--trust-tools` validates its argument.* The flag's help text says "when starting the first session", which describes when it is *read*, not what it scopes to: three sessions created under `--agent kiro_planner` all returned `modes.currentModeId: "kiro_planner"`, against `kiro_default` for an unflagged control. So one agent choice covers a whole multi-session process. **But a name that does not exist is accepted silently** — `--agent definitely-not-an-agent-xyz` spawned normally and fell back to `kiro_default` with no error and nothing on stderr, exactly as `--trust-tools` accepted a non-existent tool name. Neither flag fails loudly, so a client that depends on either must **read the setting back and assert it** (`currentModeId` from the `session/new` response) rather than trusting that the flag took.
  - **Verified 2026-07-31 — MCP startup is ~97% of the marginal session cost, and agent choice controls it. This is the largest single lever on this entry.** Same measurement method, `-a`, three sessions per configuration:

    | configuration | procs @ N=3 | RSS @ N=3 | marginal/session | MCP init notifications | warm create |
    |---|---|---|---|---|---|
    | default agent | 11 | 758.5 MB | ~151 MB | 11 (2 distinct servers) | 0.49-0.79 s |
    | `--agent kiro_planner` | **2** | **291.0 MB** | **~4.6 MB** | **0** | **0.006-0.01 s** |

    **The whole marginal cost is one MCP server.** `~\.kiro\settings\mcp.json` defines four servers, two enabled: **`playwright`** (stdio, `node …@playwright\mcp\cli.js`) and **`atlassian`** (HTTP, `mcp.atlassian.com`); `zoho` and `msgraph` are `disabled: true`. That maps exactly onto the measured `+3 procs` per session — `node.exe` + `cmd.exe` + `conhost.exe`, i.e. one stdio server spawned through a shell — while the HTTP server costs **zero** processes, consistent with `mcpCapabilities: {http: true}` from the handshake. Attribution is structural rather than per-process (tree totals were measured, and `cmd`/`conhost` are single-digit MB), but it is tight: **dropping the one stdio server captures ~97% of the saving while HTTP MCP servers can be kept for free.** *Caveat on the counter*: 11 notifications for 2 servers across 3 sessions means `_kiro.dev/mcp/server_initialized` fires more than once per server per session — use it as a presence signal, not a count.

    Without MCP the **process count does not grow with session count at all** — it stays at `kiro-cli.exe` + `conhost.exe` however many sessions are open — and marginal memory falls **33x**. The cost model therefore is not one model but two: **~306 + 151N MB with MCP**, **~277 + 4.6N MB without**. `kiro_default.json` sets `mcpServers: null` but carries `includeMcpJson`, so the default agent's MCP set arrives from `mcp.json`; `kiro_planner` does not pull it.
    - *The actionable form is not "use `kiro_planner`"* — that is a planning agent with its own prompt and tool set, not a general dispatch target. It is that a **PowerAtlas-specific agent controlling its own MCP set** captures nearly all of the saving while keeping whatever prompt and tools are wanted. And the trade is much smaller than "lose MCP": since only the **stdio** server carries the cost, a dispatch agent can keep every HTTP MCP server for free and drop only `playwright`. What that costs is browser automation inside dispatched sessions — a narrow, checkable question rather than a general capability loss.
    - **Decided 2026-07-31 — keep the default MCP servers. The lean-agent lever is closed and should not be re-proposed.** Dispatched sessions get the same MCP set as any other kiro-cli session, browser automation included. The consequences are accepted knowingly: the applicable cost model is **~306 + 151N MB**, not the lean one; session creation stays at **~0.5-1.4 s** rather than ~0.006 s; and every resumed session pays MCP startup again.
    - *Consequence for `MAX_SESSIONS`* — **acted on 2026-08-01, and the marginal figure moved again.** The old hardcoded 3 was priced against the superseded ~254 MB; at ~151 MB it read as 2.5x too conservative and **8** as the defensible replacement. That is what shipped: `acp_max_sessions` is config-driven with a default of 8, bounded 1-16, read once at startup. The limit is now the runaway-dispatch safety valve this bullet asked for, with the idle sweeper doing the real memory management. Measured at the cap rather than extrapolated from three sessions, the marginal cost is **3.0 processes / 177.8 MB** per session — eight concurrent sessions are 26 processes / 1,501 MB against a 2-process / 79 MB bare agent. The in-product cap message quotes 178 MB accordingly.
    - *And the sweeper's TTL should be generous, precisely because MCP is kept.* Every sweep-then-resume cycle re-pays MCP startup, so an aggressive TTL trades ~151 MB of idle memory for repeated multi-second stalls on the user's next interaction. Tens of minutes, not minutes. In the lean configuration an aggressive sweeper would have been nearly free; that option went with the decision above. **Shipped as `acp_idle_ttl_seconds`, default 1800** (30 minutes), bounded 300-86400, on a 60 s tick — the generous end this bullet argued for.
  - **Verified — the memory lever is an undocumented kiro extension, and this is the largest risk to anything that holds sessions open.** The cost model above is only bounded if sessions can be closed, and **`session/close` does not exist** on 2.14.2 (`-32601 Method not found`). What works is **`_kiro.dev/session/terminate`**, found by reading strings in the binary — a private method with no documented contract, which a release can withdraw without notice. It does work: one close measured **-5 processes and -253 MB**, and removed the session's `.lock`. A client that plans on N concurrent sessions is therefore betting the memory ceiling on a kiro-private extension; a build without it can only free memory by exiting the agent.
    - *The bet was taken, with a bounded downside — 2026-08-01.* The shipped sweeper calls that private method and **degrades rather than breaks** if it disappears: a failing terminate is logged and the pass continues, so the failure mode is memory growth, never a dead background task or a crashed app. Exercised deliberately by pointing the sweeper at a method the agent does not implement — 23 consecutive failures over 120 s left the task alive and the session correctly un-claimed, and restoring the method swept it on the next tick.
  - *Verified — other capabilities*: `session/cancel` interrupts a running turn cleanly (`stopReason: "cancelled"` at 8.01 s, after 118 chunks), and is best sent as a **notification** rather than a request — in that form, measured on 2.14.2, the outstanding `session/prompt` returns `stopReason: "cancelled"` in ~0.11 s and the session takes the next prompt on the same conversation. `session/set_mode` validates (`-32603` on a bad mode); ~~`session/set_model` accepts any string including nonsense without error, so its effect is unverified~~ — **verified 2026-08-03 on 2.16.0: `session/set_model` works and really changes the generator.** It returns `{}` and the switch is behavioural, not cosmetic: a session pinned to `qwen3-coder-next` answers "QWEN" when asked its model family, one pinned to `minimax-m2.5` answers "MINIMAX", 3/3 sessions each. **The reason it matters is a defect it fixes.** Unlike `--agent`, which binds to every session on the process (bullet above), **`--model` binds to the *first* session only** — sessions 2+ silently revert to `chat.defaultModel`, measured as `currentModelId: claude-sonnet-4.6` under `--model claude-haiku-4.5`. `acp.py` neither sends `set_model` nor reads `models.currentModelId` back from the `session/new` response, so at `MAX_SESSIONS: 8` seven of eight sessions run the default model whatever was asked for. The drift is invisible in latency; what exposed it was `_kiro.dev/metadata`'s `contextUsagePercentage`, which is tokens-over-window and so reads exactly 5x apart on a 200k vs a 1M model. This is the same "read the setting back and assert it" lesson the `--agent`/`--trust-tools` bullet above draws, on a third flag. Absent (`-32601`): `session/history`, `session/list`, `session/select_model`, `session/set_effort`, `session/close`, `_kiro.dev/session/compact`, `authenticate`, `fs/read_text_file`.
  - **Product-relevant caveat: creating and prompting MUTATE the user's store — attaching, on its own, does not.** A load-plus-prompt grew a real user session's `.jsonl` from 17,057 to 17,665 bytes and moved `updated_at`, so any surface that *prompts* leaves turns in the user's history even if it presents as read-only. Two refinements measured 2026-07-26. **`session/new` writes `<sid>.json`, `<sid>.jsonl` and `<sid>.lock` at creation, before any prompt** — every session such a surface opens is a permanent artifact among the ~13,300 already there, and the prototype had to enumerate the store by `cwd` before and after each phase to keep its own count honest. But **`session/load` alone leaves the transcript byte-identical** — `.json` and `.jsonl` are untouched and only the `.lock` is rewritten, which a graceful close then removes. So a genuinely read-only viewer of exited sessions *is* available; it is the turn and the creation that write, not the attach.
  - *Risks*: young protocol subject to breaking changes; the binary **self-updated mid-spike** (2.14.0→2.14.1, then →2.14.2 during the prototype), which a long-lived launcher will hit; Windows consumers must force UTF-8 and strip ANSI escapes.
  - **Verified — under `--trust-all-tools` an unprompted `shell` command executes, outside the session's own recorded scope.** Read back from the store's `.jsonl` transcripts 2026-07-26: kiro-cli ran a PowerShell command that read *and wrote* `<sid>.json` in the real session store, while that session's own recorded permissions were `allowed_write_paths: []` and `trusted_tools: []` — so `-a` overrides the recorded filesystem scoping rather than merely skipping a prompt. It fired on 2 of 3 sessions in one phase, and again mid-session on a turn that was not the first, so **the trigger condition is unknown**. Plan on an ungated command running on any turn; `-a` has to be re-decided before anything ships, and `session/request_permission` (which the protocol offers and the prototype never exercised) is the alternative.
  - *Product note*: a full ACP client turns PowerAtlas into an agent chat panel, a different product from the current launcher/dashboard, overlapping what Zed ships. That run has now happened — the state/control learning is what the bullets above record; committing the product to it is a separate decision, and still open.
  - *Effort — measured, not estimated.* The vertical slice ("drive a kiro-cli session from PowerAtlas, including one the user started") was built as `260725_KIRO_CLI_ACP_CLIENT_PROTOTYPE` across **two calendar days** — roughly **13 hours of elapsed working time** once the overnight gap is removed, first phase commit 2026-07-25 17:48, last 2026-07-26 16:17. That is elapsed time on a plan run with heavy parallel review rather than a solo hand-coded week, so it is not like-for-like with the hand-written day figures elsewhere on this page; read it as a floor.   - **(1) The round trip completes, in both directions — this is the finding that reopens the rebuild.** `session/request_permission` arrives as **standard ACP**, not a kiro extension, and a standard response is honoured. *Allow*: the tool ran and returned its nonce, `stopReason: end_turn`. *Deny*: `tool_call_update` reported `failed`, the nonce never appeared anywhere in the transcript, and the turn still ended cleanly rather than hanging or erroring. **The denied run is the one that matters** — an agent treating rejection as advisory would look identical to a working gate until the moment it counted. Trusting `shell` means trusting the whole filesystem at the user's privilege level.
