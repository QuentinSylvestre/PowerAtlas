# ACP v3 Production Hardening

> **Date**: 2026-09-08
> **Status**: Exploring
> **Scope**: Bring `/acp-v3` (kiro-cli v3 ACP protocol support) from throwaway-spike quality to production quality, on par with the mature `/acp` (v2) surface — without merging the two engines.

---

## Intent

### Problem statement & desired outcomes

`plans/done/260908-1636_ACP_V3_SPIKE.md` built a working `/acp-v3` prototype and validated protocol feasibility, but was explicitly scoped as throwaway spike infrastructure. A live-testing pass against the running PowerAtlas instance (same session, prior to this exploration) found it functionally usable for the core loop (create/prompt/stream/edit/reload/resume/close) but confirmed one real regression-shaped gap (session deletion, explicitly stubbed as not-implemented) and one root-caused cosmetic bug. Deep codebase research (three parallel sub-agent traces) and live protocol probes against a standalone kiro-cli v3 process (bypassing the running PowerAtlas app entirely) then surfaced a substantially larger set of gaps: several shared helper functions silently no-op for v3 sessions because they're hardcoded to the v2 singleton, one entire notification kind (`session_info_update` — carrying context %, steering feedback, title updates, and MCP-auth signals) has no dispatch branch on either engine, slash-command execution is entirely broken on v3, and the crew/subagent panel has zero v3 wiring despite the underlying protocol support being confirmed present and simpler than v2's.

Desired outcome: `/acp-v3` reaches the point where it can be recommended as a genuine v2-parity alternative, hardened enough that a user reaching for it hits no silent data loss, no silently-broken features, and no unhandled hangs — while `_SupervisorV3` remains a separate class from `_Supervisor` (merging them is an explicit non-goal of this pass, per user decision).

### Success criteria

- SC-1: The `new_session()` notification-drop race (frames arriving before `self.history[session_id]` is registered — confirmed via orchestrator.log evidence, root-caused to asyncio scheduling order) is fixed generally, not just for the one observed `fetch_cloud_config` case.
- SC-2: Individual v3 session deletion works end-to-end (`sess_`-prefixed IDs no longer hit "not yet implemented"), and workspace-level delete correctly enumerates and deletes v3 sessions too (currently silently blind to them, per `_acp_sessions_for_workspace`'s own docstring).
- SC-3: `_on_notification` gains a `session_info_update` branch (v3-specific — v2 never emits this kind) that surfaces: context-window percentage, the three-state steering echo (`steering_queued`/`steering_injected`/`steering_cleared`), session title/focus updates, and MCP-auth-required signals (`_meta.kiro.displayError`).
- SC-4: `_flush_bubble`, `_emit_subagents_frame`, and `_handle_subagent_subscribe` (currently hardcoded to the v2 `_supervisor` singleton even when invoked from a v3 code path) are made engine-aware, so v3 sessions get correctly-recorded "rendered" markdown frames and correctly-routed sub-agent detail-panel replay.
- SC-5: The crew/subagent panel works on v3 — live, mid-turn, not just at turn-end. Confirmed wire shape (live probe, this session): subagent spawn/progress/completion arrives as ordinary `tool_call`/`tool_call_update` frames tagged `_meta.kiro.kind: "agent-subtask"` with an `agentSubtaskId`, and the subagent's own output streams as `agent_message_chunk` tagged with the same `agentSubtaskId` — no child session exists at all (architecturally simpler than v2). Server-side translation into the existing (engine-agnostic) `subagents` frame shape is the only new work; the client-side `setCrew()` renderer needs no changes.
- SC-6: `presence.py`'s `_match_provider` correctly attributes resumed v3 sessions to `"kiro-cli-v3"` instead of always `"kiro-cli"` (currently dead code — the `"kiro-cli-v3"` dict entry is unreachable).
- SC-7: Production liveness detection is implemented per the spike's Phase 5 recommendation — read `session.json`'s `status` field, zero ACP round-trip. Re-confirmed live this session on kiro-cli 2.21.1: concurrent `session/load` still succeeds (no refusal) despite v3 now writing `.lock` files, so lock-file-based checking remains the wrong approach; the file-status-field approach is unaffected by this and stays correct.
- SC-8: `_kiro.dev/commands/options` and `_kiro.dev/commands/execute` — confirmed broken on v3 via live probe (`-32603`, identical "no persistence classification" error the spike found for `session/terminate`) — are replaced with whatever the correct v3-native mechanism turns out to be, found via a dedicated Phase-0-style probe (protocol unknown, not yet resolved). Confirmed via client-code read that selecting *any* slash command from the `/acp-v3` palette currently triggers this broken path (`acp.html:2152`).
- SC-9: `session/request_permission` (a genuine inbound *request* — confirmed live via probe in spec mode: the agent asking a structured multiple-choice clarifying question and blocking the turn on an answer) is handled with a real interactive UI: the question and its named options render in the transcript, the turn blocks until the user picks one, the chosen `optionId` is sent back over the wire.
- SC-10: The "unrecognized notification kind" fallback (both `_Supervisor` and `_SupervisorV3`'s `_on_notification`) is promoted from DEBUG (invisible — production runs at INFO) to a visible level, so a future/unknown kind is diagnosable from `orchestrator.log` without deliberately enabling DEBUG first.
- SC-11: `_SupervisorV3` overrides and all 9 `_handle_*_v3` WS-frame functions get direct test coverage (currently zero — confirmed via full-file grep against `tests/test_web.py`).
- SC-12: All existing tests (`pytest`, `node tests/acp_page.test.mjs`) continue to pass, and `/acp` (v2) is verified unaffected by every change (shared-helper fixes in particular touch code v2 also calls).

### Scope boundaries & non-goals

**In scope:** every gap enumerated in SC-1 through SC-11, all confirmed live where a live probe was possible (this session standalone-probed: concurrent-load behavior, `_session/steer`, `commands_options`/`execute`, a real two-way subagent fan-out, and spec-mode's `session/request_permission` — all against a throwaway kiro-cli v3 process bypassing the running PowerAtlas app, cleaned up after use).

**Explicitly out of scope, with reasoning (all confirmed with the user):**
- **Merging `_SupervisorV3` into `_Supervisor`.** User decision: keep them parallel. 84% of `_SupervisorV3`'s methods already inherit unchanged from `_Supervisor` (verified via full method-by-method diff), and zero drift has occurred in the shared `_on_notification` logic since the spike (verified: `git log -L` on the v2 body's line range shows no commits since 2026-08-18, pre-spike). A merge would touch the base class the entire v2 daily-driver path depends on for a task whose goal is v3 parity, not a v2 refactor. Stays an explicit, separately-scoped future follow-up (ROADMAP.md already sequences it this way).
- **Linux cross-platform support.** User decision: excluded. Verified via trace that v3's `_spawn` reuses the *identical* Windows-only `_create_job()` guard v2 already has — there is no new, v3-specific platform gap. Since this plan's goal is v2 parity, and v2 has the identical limitation today, this isn't a parity gap to close.
- **Mode-switcher UI** (letting a user pick `spec`/`quick-spec`/`bug-fix`/`plan`/etc. instead of always `kiro_default`). Not in scope — `/acp-v3` stays hardcoded to `kiro_default`, matching that `/acp` v2 has no mode-selection UI either (not a parity gap). SC-9's `session/request_permission` handling exists to protect `kiro_default` sessions from any built-in tool that might ask a clarifying question, not to unlock the other modes as a user-facing feature.
- **Full MCP OAuth "Connect" flow.** Narrowed after live evidence: the real signal (`session_info_update` → `_meta.kiro.displayError`, `errorType: "mcp_connection_error"`) carries a human-readable message, not a structured `authorizationUrl` — nothing was observed that a one-click "Connect" button could target. SC-3 covers surfacing the message; a full OAuth completion flow is not buildable from what's been confirmed and stays a future item if a URL-bearing shape is ever found.
- **`_kiro/spec/*` notifications as originally imagined.** Narrowed after live evidence: no such dedicated notification methods exist. Spec mode only adds a `"spec"` tag to the builtin-tools list (`_kiro/tools/didChange`) and relies on the same `session/update` subtypes as every other mode, plus (per SC-9) the `session/request_permission` interaction. Nothing further to build here beyond SC-9 and SC-10.
- **"Kiro Crew"** (`kiro-cli crew` subcommand) — confirmed via `kiro-cli --help`/`kiro-cli crew --help` to be a wholly separate, standalone installable CLI product, unrelated to the ACP protocol surface. Not relevant to this plan.
- **Removing or deprecating `/acp` v2.** Unchanged from the spike's own non-goals.

### Existing patterns & constraints

- **Governance, hard constraint**: `AGENTS.md:5` — *"Never restart PowerAtlas autonomously. Restarting kills every kiro-cli ACP process the supervisor is managing, terminating all active sessions. Always defer to the user."* Every fix in this plan touches `acp.py`, `web.py`, `presence.py`, or `status_classifier.py` — all Python-level, all requiring a user-timed restart to verify live (`AGENTS.md:7`: Python changes need a restart; template/CSS changes don't). This shapes the whole testing strategy (see below) — batch changes, minimize restart count, verify everything restart-independent first.
- **`record()`'s silent-drop idiom is deliberate and repeated**, not a one-off bug shape: `acp.py:4254-4266` (`record`) and `acp.py:3245-3286` (`_stamp_activity`) both no-op silently when `session_id` isn't yet registered, and `_stamp_activity`'s own docstring (`3284`) says explicitly *"record() and _note_context() model the idiom."* A fix for SC-1 should respect this idiom's intent (never raise on an unregistered session) while closing the actual data-loss gap.
- **`load_session` already solves the "register before the round-trip" problem** the exact way SC-1 needs generalized (`acp.py:4176-4183` docstring states the rationale) — but `new_session()` structurally *cannot* do the same thing, because the session_id doesn't exist client-side until the RPC result names it (`result._meta.id`, `acp.py:4807`). The race is forced by asyncio scheduling: a notification enqueued via `call_soon_threadsafe` from the reader thread (`acp.py:3149-3161`) can run in the same event-loop pass as the RPC-response callback that resumes `new_session()`, while `new_session()`'s own post-await continuation is deferred to the *next* pass.
- **One existing buffering precedent, structurally too narrow to reuse as-is**: `_pending_commands` (`acp.py:4150`, write sites `4019-4026`/`4642-4645`, flush `4143-4171`, called from `new_session` at `4123`/`4814`) buffers exactly one thing (the commands/skills catalogue) in a single last-writer-wins slot — justified because that content is session-agnostic. A generalized SC-1 fix needs a keyed (not single-slot) buffer, since `tool_call` payloads are NOT interchangeable across sessions.
- **Contrast with the AS-6 auth-token race** (spike's own prior finding, `getAccessToken` arriving before `initialize`'s result): that path is naturally robust because `_fulfill_token` (`acp.py:4720-4787`) depends on zero per-session state — it routes purely by JSON-RPC `id`, not by ACP `session_id`. `tool_call`'s entire effect is keyed by `session_id` in dicts `new_session()` populates only after its own round-trip. This is *why* one race is already handled and the other isn't — not an oversight, a structural difference.
- **acp.py's isolation-boundary constraint is narrower than its own docstring claims.** Docstring (`14-24`) says "exactly two names" (`config.CONFIG_DIR`, `launcher._SESSION_ID_RE`); actual imports (`82-84`) are three, including `data_kiro`. The *mechanically enforced* rule (Phase 1's own exit-criterion grep, still passing today) only forbids importing `data_kiro_v3` — already known-stale, already accepted as out-of-scope-to-fix in the spike's Post-Implementation Review (finding #9). `web.py` has no such constraint at all — it already imports `data_kiro_v3` freely via the provider registry (`data.py:98,106`). **Implication for SC-2**: a v3 delete helper belongs in `data_kiro_v3.py` (called from `web.py`), not inlined into `acp.py` — this violates nothing, unlike the diff-backfill helper's inlining, which was specifically to avoid touching acp.py's grep contract.
- **v2's delete implementation, to mirror for SC-2**: `api_acp_delete_sessions` (`web.py:3019-3113`) → `_acp_delete_many` (`web.py:2849-2915`) → `_acp_delete_session` (`web.py:2764-2846`), targeting `_acp_session_paths` (`web.py:2746-2761`: `KIRO_SESSION_DIR/{id}{.json,.jsonl,.history,.lock}` plus an optional bare-id directory). Uses rename-to-staging-then-unlink (`_ACP_DELETE_STAGING = ".pa-deleting"`) to survive Windows sharing violations (`winerror 32`). No `data_kiro.py` delete function exists — v2 deletion is bespoke in `web.py`, not delegated to the data layer; the same shape (bespoke in `data_kiro_v3.py` or `web.py`) is appropriate for v3.
- **v3 on-disk layout, directly verified this session** (not just cited): `~/.kiro/sessions/<workspace-hash>/sess_<uuid>/` is a **directory** (unlike v2's flat sibling-files layout) containing `messages.jsonl`, `session.json`, `publish.cursor`, and — only for sessions that used subagents — `sub-executions/<agentSubtaskId>.jsonl` and `publish-sub.cursor`. A delete implementation needs to remove the whole directory tree, not a fixed file-suffix list.
- **`_acp_sessions_for_workspace`'s v2-only blindness, confirmed** (`web.py:2929-2930` docstring: *"covers only v2 sessions... v3 sessions... are not enumerated"*) — the workspace-level delete path silently no-ops for v3-only workspaces rather than refusing; SC-2 needs to close this too, not just the per-session guard.
- **`session_info_update` has no dispatch branch at all**, confirmed by direct grep (`session_info_update`/`contextUsage`/`steering_queued`: zero matches in `acp.py`) and by reading `_on_notification`'s full branch list (`acp.py:3633-4045`/`4466-4653`) — `kind = update.get("sessionUpdate")` (`3637`) extracts it correctly, but no `if kind == "session_info_update"` branch exists on either class. `METADATA_METHOD` (branch 2) only matches the *separate*, v2-only top-level method `_kiro.dev/metadata` — it does not catch this. Every `session_info_update` frame today falls through to the DEBUG-only, currently-invisible fallback (`4036-4044`/`4651-4653`) — this is why v3's context-window bar never populates (confirmed absent in this session's own earlier live browser screenshots) and why the steer lifecycle produces no client-visible feedback beyond the immediate RPC ack.
- **Turn-end display is unaffected by the `session_info_update` gap** — it's read directly off the `session/prompt` RPC *result* (`{"result": {"stopReason": "end_turn"}}`), not off any notification, so SC-3 doesn't risk regressing it.
- **Live-verified `session_info_update` `_meta.kiro.kind` vocabulary** (this session's probes, not the spike's): `context_usage` (carries `contextUsage.usagePercentage` and a token breakdown), `steering_queued`/`steering_injected`/`steering_cleared` (carries `messageId`, `content`), `focus_update` (session title, auto-derived from the first prompt), `user_message_id_assigned`, `turn_end` (redundant with the RPC result, per above), `display_error` (carries `message`/`errorType`, e.g. `"mcp_connection_error"`), `pendingInteraction` (precedes a `session/request_permission` request with the same question/options preview).
- **`_flush_bubble`, `_emit_subagents_frame`, `_handle_subagent_subscribe` are hardcoded to `_supervisor`** even when invoked from `_SupervisorV3`'s own code paths (`_flush_bubble` calls `_emit(...)` unconditionally at `acp.py:5108`, never `_emit_v3`; `_emit_subagents_frame` reads `_supervisor.crews`/`_supervisor.crew_spawn_toolcallids` at `5037`/`5042`; `_handle_subagent_subscribe` reads `_supervisor.crews`/`_supervisor.subagent_history` at `5567`/`5579`). A correctly-scoped `_emit_subagents_frame_v3` already exists (`7269-7280`) but is only called at turn-end, not on each live update — this is the concrete mechanism behind SC-5's "live, not just at turn-end" requirement.
- **Confirmed live wire shape for SC-5** (superseding the exploration's earlier "unverified" framing): subagent spawn is an ordinary `tool_call` with `title: "Sub-agent: <name>"`, `_meta.kiro.kind: "agent-subtask"`, `agentSubtaskId`, `rawInput: {name, prompt, explanation, contextFiles}`; NOT `_meta.kiro.toolName == "subagent"` (the field the existing spawner-anchor logic at `3806-3828`/`4529-4538` checks — that check will never match on v3, needs a parallel `_meta.kiro.kind == "agent-subtask"` check). Completion: `tool_call_update` with `status: "completed"`, `rawOutput` carrying the subagent's final answer directly.
- **`presence.py`'s v3 gap is genuinely dead code, and cosmetic-only in impact**: `_PROVIDER_SPECS` (`70-74`) declares `"kiro-cli"` before `"kiro-cli-v3"`; `_match_provider()` (`552-571`) returns on first match, so `"kiro-cli-v3"` is unreachable. But `status_classifier.py:574-578` shows the *status computation itself* is unaffected — when mislabeled as `"kiro-cli"`, `_classify_from_path` auto-detects the v3-format transcript via `_is_v3_format()` (`452-467`) and still calls `classify_kiro_v3()`. Only the provider *attribution* (which row/group a session files under) is wrong, not the WORKING/WAITING/ERRORED status itself.
- **Liveness: `classify_kiro_v3()` already exists and works**, shipped one day before the ACP v3 spike began (`260818_KIRO_CLI_V3_DASHBOARD_SUPPORT`, commit `da6dfd8`) — a *separate* effort covering the read-only dashboard listing, distinct from this plan's interactive-driving surface. It classifies status from `messages.jsonl` tail `payload.type` values, not from `session.json.status` (the spike's Phase 5 recommendation, still unimplemented anywhere — confirmed via full-tree grep for `in_progress`/`waiting_on_user` in a session.json-reading context). SC-7 should decide whether to extend the existing transcript-tail approach or implement the file-status-field approach fresh — both are legitimate options now that they're known to coexist rather than conflict; the exploration recommends the file-status approach since it's zero-round-trip and was the deliberate Phase 5 conclusion, but this is a `/qplan`-level design call, not settled here.
- **The literal lock-file mechanism ROADMAP.md:38 describes, located precisely**: `acp._lock_holder()` (`2116-2172`), called from `_acp_availability()` (`web.py:1795-1825`), which v3 listing already goes through (`_acp_listing_v3`, `web.py:2238`). For a `sess_`-prefixed ID this hardcoded-to-`KIRO_SESSION_DIR` path never matches → `FileNotFoundError` → caught → returns `None` → fails open to `"available"`. Not a crash risk, just a v3 session actively held by a live terminal shows as falsely "available" in the rail today.
- **`_session/steer` works functionally on v3**, confirmed by live probe: model actually followed the steered instruction. The echo mechanism is the three-state `session_info_update` sequence above (SC-3 territory), not v2's single `AgentExecutionSteeringInjected` kind (which doesn't exist as a concept on v3 at all — `_kiro.dev/*` methods aren't part of v3's namespace).
- **`commands_options`/`commands_execute` are confirmed broken**, not just theoretically mismatched-namespace: live probe returned the identical `-32603 "[PersistenceClassification] Ext method ... has no persistence classification"` error the spike found for `session/terminate`. `acp.html:2152` confirmed to call exactly this path when a user selects any palette entry — today, opening the v3 slash-command palette looks fully functional (population works, confirmed live) but selecting anything silently errors.
- **`session/request_permission`, confirmed live, is a real inbound request** (has an `id`, blocks the turn on a response) — arrived during a spec-mode probe as the agent asked a genuine multiple-choice clarifying question, preceded by a `session_info_update` (`kind: "pendingInteraction"`) carrying the same question/options as a preview. PowerAtlas's `_on_agent_request` (`4713-4718` v3 override, falls through to base `3215-3226` for anything but `getAccessToken`) has no handler for this — the probe session hung until killed. Not reachable in `kiro_default` mode based on this session's testing (several different live prompts never triggered it), but structurally possible if any built-in tool asks a clarifying question in any mode.
- **Test coverage gap, precisely bounded**: `TestSupervisorV3` (`tests/test_web.py:19808-20319`, 13 tests) covers only `_get_tool_diffs_v3`, `_stored_session_cwd_v3`, `_fulfill_token`, and `_publish_live` union — zero tests touch `new_session`, `load_session`, `close_session`, `_on_notification`, `_emit_v3`, `steer`, or any of the 9 `_handle_*_v3` functions (confirmed: 217 references to v2 `_handle_*` functions in test_web.py, 0 to any v3 counterpart). `tests/acp_page.test.mjs` has exactly 3 `engine: "v3"` checks, all URL-construction only, none behavioral.

### Risks & mitigations

- **R1 — Shared-helper fixes (SC-4) touch code v2 also calls.** `_flush_bubble` etc. are called from both engines' code paths; an engine-aware fix must preserve v2's exact current behavior while adding the v3 branch. Mitigation: SC-12 requires explicit v2-regression verification for every shared-helper change, not just v3 behavior checks.
- **R2 — SC-1's generalized fix touches `new_session()`, a core session-creation path for both engines** (the race and its asyncio-scheduling cause are structurally identical for v2 and v3, per the mutation-trace agent's finding — it just doesn't currently manifest for v2 because v2 apparently doesn't fire an unsolicited early tool call). Mitigation: design the fix to be engine-agnostic and applied to the shared idiom (or explicitly scope it to `_SupervisorV3.new_session` only, if a v3-only fix is judged lower-risk) — a `/qplan`-level decision.
- **R3 — `commands_options`/`commands_execute`'s correct v3 replacement is unknown** (SC-8 has no confirmed answer, only a confirmed failure mode). Mitigation: dedicate an explicit Phase-0-style probe (mirroring the original spike's own methodology) before implementing, rather than guessing.
- **R4 — `session/request_permission`'s interactive-UI design (SC-9) is entirely new surface** — new WS frame type in both directions, new pending-request state tracked server-side, new UI component. Mitigation: since it's not reachable in production `kiro_default` usage today (per this session's testing), it can be built and tested via the same standalone-probe technique (spec mode) without needing to be exercised through the live PowerAtlas instance for initial verification — only final integration needs a live restart+click-through.
- **R5 — Every fix requires a user-timed restart to verify live**, and `AGENTS.md:5` forbids requesting one autonomously mid-session more than the minimum needed. Mitigation: batch phases to minimize restart count (see Testing strategy / QA environment below); verify everything restart-independent (pytest, standalone protocol probes) exhaustively before ever asking for one.
- **R6 — Browser-based testing of the delete feature (SC-2) is unsafe via automation**: this session directly hit a Chrome-extension-crashing native `confirm()` dialog when clicking "Delete session," requiring the user to manually recover Chrome. Mitigation: verify SC-2 via pytest/direct API calls (`curl`/`httpx` against `/api/acp-v3/sessions/delete`), not via clicking the UI button in an automated browser session; a manual user click-through remains fine.
- **R7 — Deleting a v3 session directory tree that includes `sub-executions/`** (subagent execution logs) needs `shutil.rmtree`-equivalent recursive deletion, not v2's fixed-suffix file list — a naive port of v2's delete logic would miss this subdirectory.

### Recommended approach

Phase the work to respect the restart constraint (R5): group all Python-level changes (SC-1 through SC-11, excluding the pure-test-file SC-11 additions which need no restart to author, only to run against a restarted instance for full confidence) so they land together and get verified in as few user-approved restarts as possible — likely one restart after the `_on_notification`/shared-helper/liveness/delete cluster, and a second after the `session/request_permission` UI + `commands_options`/`execute` replacement (since SC-8's fix depends on an unresolved probe finding). Within each cluster, order by risk: SC-6 (presence.py attribution) and SC-10 (log-level bump) are lowest-risk, do first; SC-1 (the race fix) and SC-9 (new interaction pattern) are highest-risk/highest-novelty, do with the most test coverage before touching the live instance.
