## Automation & Workflows

> Every item here needed one capability PowerAtlas did not have: sending a prompt to an agent
> without a terminal. **PowerAtlas has it as of 2026-08-01** — `260731_ACP_REMOTE_CLIENT_PRODUCTIZATION`
> promoted the prototype to product, so `/acp` creates, resumes, prompts and closes kiro-cli sessions.
> What every item below still turns on is whether dispatch is safe *unattended*; the capability is no
> longer the blocker, the posture is. The findings are recorded per item below, dated 2026-07-26 and
> measured on kiro-cli 2.14.2 unless a bullet says otherwise — several were re-measured on **2.16.0**
> on 2026-07-31 and those re-measurements supersede the pinned figures where they overlap. They come
> from `260725_KIRO_CLI_ACP_CLIENT_PROTOTYPE`, so read them with that
> prototype's boundary in mind: it proved a **chat surface driven by a human watching it**, which is
> what its `-a` posture assumed. Three of the six — fire-and-forget dispatch, scheduled tasks and
> chained launches — are *unattended*, which is the absence of that human, so for those the prototype
> prices the work without deciding it. Where it established nothing, that is said rather than left
> blank.

- **Dispatch no-interactive tasks** — launch kiro-cli with `--no-interactive` and a prompt, fire-and-forget from the UI
  - **The mechanism this item names persists nothing, which changes what the feature would deliver.** Four variants were run: `--no-interactive` piped, `--no-interactive` in a real console window, and an interactive session with piped stdio quit gracefully via `/quit` (exit 0) all wrote **zero files**; only a fully interactive TTY session persisted. It is the console, not the flag. So a fire-and-forget `--no-interactive` dispatch leaves no session file, no transcript and no lock — nothing for the dashboard that motivates the item to show, and nothing for `status_classifier.py` to classify. Recorded in full under *Accepted limitations* in `plans/CLOSED_INVESTIGATIONS.md`.
  - **ACP is the dispatch path that does leave a trail**, and the trade is the mirror image. `session/new` writes `<sid>.json`, `.jsonl` and `.lock` at creation before any prompt, and the turn lands in the `.jsonl` the existing pipeline already reads — but every dispatch is then a permanent artifact in a store already holding ~13,300, and the prototype had to enumerate the store by `cwd` before and after each phase to keep its own count of what it had created honest.
  - *Unanswered — the thing that decides the item*: whether dispatch is safe with nobody watching. The permission experiment that bears on it **ran on 2026-07-31** and its results are in `docs/KNOWLEDGE.md`; what it did not settle is classifier *accuracy*, which is the open half tracked under *An auto-mode for `/acp` permissions* in `## Session Control & Integration`.
- **Open session with specific prompt/skill** — generic prompt input, local/user skill execution with params
  - **The prompt half is built and measured.** Prompting over ACP works end to end with incremental chunks, tool-call rendering and an authoritative `stopReason`. Budget for latency rather than assuming it: a trivial 20-line answer took ~24 s wall clock and a tool-using turn runs to minutes, which is why the prototype needed a 600 s prompt ceiling distinct from its 90 s ceiling for ordinary requests.
  - **Skills work, and they work in full.** A skill invoked over ACP loads the whole `SKILL.md` body, not just the frontmatter description — verified with tools forbidden, reproducing a script path, four flag names and a five-row taxonomy that exist only in the body. The advertised catalogue matches `~\.kiro\skills\` exactly: 25 each, set difference empty in both directions.
  - **`with params` is the open half, and it is this item's own wording.** `/qsummarize-chat 1` honoured the body's output format but emitted 4 pairs rather than 1, and nothing distinguishes "the argument never reached `$ARGUMENTS`" from "the model ignored it". Any surface that passes parameters into a skill needs this settled first, and settling it costs one prompt.
- **Template prompts** — save reusable prompt templates per workspace (e.g., "/qdev {latest plan file}" as one-click)
  - **Nothing established about templating itself.** Storage, per-workspace scoping and the UI were all out of scope; the prototype hardcoded agent, model and effort and added no config keys, deliberately.
  - **The substitution question is inherited, not new**: this item's own example is a slash command carrying an argument, so it is blocked behind the same inconclusive `$ARGUMENTS` result as the item above — the template mechanism is worthless if the parameter never arrives.
- **Scheduled tasks** — cron-like recurring kiro-cli launches (e.g., "/qdream every Sunday 10am in agent-playbook")
  - **This is the item the prototype was scoped never to test**, and the gap is structural rather than incidental: `-a` was accepted for "a prototype driven by a human watching it", and a schedule is precisely the absence of that human.
  - **Three measured facts price it even so.** An unprompted `shell` command ran under `-a` and wrote into the real session store, overriding that session's own recorded `allowed_write_paths: []`, on a trigger nobody identified — so plan on an ungated command running on any turn, not the first. A held-open session costs ~254 MB and 5 processes, and the only lever that frees them is `_kiro.dev/session/terminate`, a kiro-private extension; at the time of measurement there was no idle sweeper anywhere. And creation is ~5.4 s cold / ~2.5 s warm, so a scheduler either pays that per run or holds processes between runs and pays the memory instead.
    - *All three re-measured 2026-07-31 on 2.16.0, and all three moved in the scheduler's favour.* The "trigger nobody identified" is identified: it is `~\.kiro\steering\session-tab-title.md`, PowerAtlas's own global steering, so the ungated command is **known and predictable** rather than arbitrary — it fires once on the first turn of every new CLI session and touches only that session's own store record. A held-open session now costs **~3 procs / ~150 MB** (not 5 / 254), `_kiro.dev/session/terminate` is confirmed working and confirmed to actually reclaim, and creation is **1.47 s cold / ~0.5 s warm**. The dilemma in the last sentence therefore softens a lot: sub-second warm creation makes *not* holding processes between runs the cheap option.
    - *And the sweeper now exists, 2026-08-01.* `260731_ACP_REMOTE_CLIENT_PRODUCTIZATION` shipped one in `acp.py`: a 60 s tick terminates any session idle past `acp_idle_ttl_seconds` (default 30 min) that has no attached tab, no turn in flight, no close in flight and no load in flight, leaving the transcript resumable. The session cap is configurable too (`acp_max_sessions`, default 8), and the marginal cost was re-measured across eight concurrent sessions at **3 processes / 178 MB** each. Two residuals a scheduler must plan around: a turn is bounded by **silence** (15 min default) with a 4 h absolute ceiling rather than by wall clock, so an unattended task is not cut off for being slow; and neither `session/cancel` nor `_kiro.dev/session/terminate` reaps a shell subprocess the agent started — measured still alive 20-25 s after both, dying only when PowerAtlas's Windows job object closes. A cancelled dispatch can leave work running that no accounting here counts.
  - *Blocked on*: an auto-mode that can replace `-a` — tracked as *An auto-mode for `/acp` permissions* in `## Session Control & Integration`. The protocol half is already proven (permission round trip, `docs/KNOWLEDGE.md`); the accuracy half is not. Of the six items here this is the one that should not be built on the prototype's evidence alone.
- **Chained launches** — "when session X exits, auto-launch session Y in folder Z" (pipeline mode)
  - **The trigger this item needs exists, and polling cannot see it.** `stopReason` on the completing `session/prompt` is an authoritative turn-end signal — measured at ~0.11 s after a cancel notification — where a transcript tail can only infer one from the shape of the last record.
  - **But it is a trigger only for sessions PowerAtlas itself drives.** A session live in a terminal is unreachable, because `kiro-cli chat`'s own ACP grandchild holds the lock, so "when session X exits" holds for X's that PowerAtlas launched or that have already exited — not for the terminal work the dashboard mostly watches.
  - **Stage health is not readable from the process.** ~~`_kiro.dev/commands/execute` killed the agent with exit code 0 and no stderr~~ — **superseded 2026-08-12**: that kill was caused by the *string-form* payload (the incorrect form); the TuiCommand *object* form `{"sessionId":sid,"command":{"command":name,"args":{}}}` is confirmed correct and is what PowerAtlas now uses (`_handle_commands_execute`, Phase 3). The broader point stands: the prototype's agent wrote 0 stderr bytes across whole sessions; separately, `-32603 "Internal error"` is this build's generic failure and was returned once for a `session/prompt` that then succeeded on immediate retry. A pipeline must judge liveness from the JSON-RPC channel and must not read a single error frame as a failed stage.
- **Skills support — spike to understand how Claude Code and kiro-cli execute skills, then build on that.** PowerAtlas already invokes skills as plain prompt text over ACP (verified: a skill invoked over ACP loads the full `SKILL.md` body, 25 of 25 match `~\.kiro\skills\`), but two gaps remain unresolved and both block downstream items. First, **`$ARGUMENTS` passing is unverified** — `/qsummarize-chat 1` emitted 4 pairs rather than 1, and nothing distinguishes "argument never reached the template" from "model ignored it"; settling this costs one probe prompt. Second, **Claude Code's skill execution path is unknown** — Claude Code uses slash commands (`/project:name`, `/user:name`) from `.claude/commands/` rather than a centralized `~\.kiro\skills\` tree, and how PowerAtlas would invoke one over Claude Code's ACP (or equivalent) is a separate question. The spike should answer: (a) how kiro-cli's `$ARGUMENTS` substitution actually works over ACP, (b) how Claude Code defines and invokes slash commands, (c) whether a common invocation surface exists across both providers, and (d) what the correct invocation looks like from a launcher button. Unblocks *Open session with specific prompt/skill*, *Template prompts*, and *Plan-file shortcuts* — all three carry the same `$ARGUMENTS` dependency.

- **Plan-file shortcuts** — detect plan files in `plans/` and offer one-click "/qdev on this plan" buttons
  - **The invocation path is proven and it is cheap.** Slash commands are ordinary prompt text intercepted agent-side — `/tools` returned a canned answer in **1 ms**, impossible for a model round trip — so no proprietary RPC is involved and a standards-only client sees every skill.
  - **The parameter is the whole feature, and it is the unresolved part**: "/qdev on this plan" is exactly an argument-carrying invocation, blocked on the same `$ARGUMENTS` question as the two items above.
  - **Like *Open session with specific prompt/skill*, this one keeps its human.** A one-click button is a user gesture with the user present, so it sits inside the posture the prototype actually validated and is blocked on the parameter question rather than on the permission experiment. That makes it, with its two siblings above, the part of this section that survives a bad result from that experiment.

## Platform

- **[MEDIUM — downgraded 2026-08-04 when shape (b) shipped] Secret-aware handling for custom-launcher env vars** — launcher environment variables are stored in cleartext, and at least one real launcher holds production credentials. *Scoped 2026-07-25; the serving half addressed 2026-08-04.*
  - **What shipped 2026-08-04 — shape (b), "keep the values local but stop serving them".** `_launchers_without_env` (`web.py`) strips `env` from every launcher payload that leaves the process, and the scoping note below was wrong about how many that is: it named `/api/launchers` and the `|tojson` bootstrap, but **`/api/settings` returned `custom_launchers` with `env` too**, which `refreshSettings` fetches on a timer. Three paths, not two. The edit modal now asks for one launcher's env through `POST /api/launcher/env` — POST rather than GET so `same_origin_guard`'s Origin/Referer check applies, since that guard's own docstring justifies its POST-only scope with "every other GET here only reads", and credentials are not that. Not on `_REMOTE_ALLOWED_PATHS`, which is default-deny.
    - *A regression this would otherwise have shipped, caught by mapping consumers first*: `runLauncherById` posted `env: l.env` to `/api/launcher/run` from the now-stripped page state, so every custom launcher would have started **without its environment variables**. `/api/launcher/run` now resolves `env` from the stored launcher when the caller names an id — which `/api/launcher/run-batch` always did, so this brings the two into line and stops credentials round-tripping through the browser at all.
    - *The fail-closed decision, worth knowing before changing it*: a failed env fetch **refuses to open the modal** rather than opening it with an empty env box. The box is written back verbatim on save, so degrading to empty would silently wipe the credentials on the next Save. `POST /api/launcher/env` 404s an unknown id for the same reason — "gone" and "has no variables" must not look alike on the wire.
  - **What this does NOT do, stated plainly so the item is not read as closed.** It removes the credentials from payloads that are fetched routinely, cached, and visible in `view-source:`. It **authenticates nothing** — `same_origin_guard` never did — so a local process that deliberately forges an `Origin` header can still read one launcher's env through the new POST. The exposure moved from *ambient* to *deliberate*. That is worth having and is not the fix; **shape (a), reference-by-name indirection into Windows Credential Manager / libsecret, remains the durable answer** and is what keeps this item open.
  - *Coverage*: 9 tests in `tests/test_web.py` pin the three payloads, the non-mutation of live config, the env route's 200/400/404, and both run-path env resolutions.
  - *The concrete case*: `%LOCALAPPDATA%\power-atlas\config.toml` (lines 57-61 as of 2026-07-25) carries `AUTH_TOKEN_PRODUCTION`, `AUTH_TOKEN_STAGING` and `MQTT_CERT_PATH` under a `[custom_launchers.env]` block. Three other launchers have empty env blocks. The file is outside the repo, so this is not a git-leak risk — it is a local-exposure one.
  - **The exposure is wider than the config file, and this is the part that makes it high priority.** `/api/launchers` (`web.py`) returns every launcher **including its env dict**, and the `_launchers` bootstrap in `index.html` (`var _launchers={{launchers|tojson}}`) injects the same list into the page. `same_origin_guard` (`web.py`) authenticates nothing: its Origin/Referer check is CSRF defence and is **POST-only**, so both `GET /` and `GET /api/launchers` are unauthenticated. **Any local process can read the production tokens with a single HTTP GET**, with no ACP client, no agent, and no user interaction. *Verified by code reading 2026-07-25; not executed against a live server.*
    - *Corrected 2026-08-01 — "gates POST only" was already too coarse and is now wrong.* The guard has three halves with deliberately different scopes: the **Host allowlist applies to every method** (DNS-rebinding defence, since a rebound page is same-origin with whatever it fetches), the Origin/Referer CSRF check stays POST-only, and `GET /acp` additionally carries a `Sec-Fetch-Site` navigation check. **None of that changes this item**, because a local process simply sends a loopback `Host` and the allowlist admits it — the exposure is unchanged and the fix is still (a), (b) or (c) below. What *did* change is the blast radius: `260731_ACP_REMOTE_CLIENT_PRODUCTIZATION` added `RemoteAccessGuard`, a default-deny path allowlist outside everything else, so `/` and `/api/launchers` are refused with a 403 from any non-loopback peer even with the remote bind on. The exposure is local-process only, never network.
  - *Nothing masks them on the way through*: `launcher_modal.html:10` is a plain `<textarea>` ("Env (KEY=VAL per line)"), `editLauncher` (`index.html`) renders stored values straight back into it, and `launcher_create` (`web.py`) stores `body.get("env", {})` with no validation. Values reach the child at `launcher.py:403` (`proc_env = {**os.environ, **env}`), which is the intended behaviour and not the problem.
  - *Why now*: `save_config` (`config.py:271-290`) rewrites the whole file on any settings change, so the values are re-serialised constantly; and the ACP prototype (`260725_KIRO_CLI_ACP_CLIENT_PROTOTYPE`) introduces an agent running with `-a` that has filesystem access — a second, weaker path to the same data. That plan added a WebSocket token partly for this reason, but the token is itself served over the same unauthenticated `GET`, so it does not close this.
  - *Shapes worth considering — still none chosen for this item, and one was deliberately declined next door.* (a) reference-by-name indirection — store `AUTH_TOKEN_PRODUCTION = "@keyring:poweratlas/prod"` and resolve at launch from Windows Credential Manager / libsecret; (b) keep values local but stop serving them — omit `env` from `/api/launchers` and the `|tojson` payload, fetching it only when the edit modal opens; (c) minimum viable — mask in the UI and redact from any export or log. Note (b) alone fixes the GET exposure and is small; (a) is the durable answer. **`260731_ACP_REMOTE_CLIENT_PRODUCTIZATION` (D4) put exactly this question to the user for the remote-access surface and the answer was to change nothing**: redaction was recommended and declined so the values stay readable in the WebUI, the loopback split being the sole protection, on the measured ground that PyCharm already stores run-config env vars in plaintext in `.idea/workspace.xml`. That decision is scoped to *that* plan's remote surface — it keeps `/api/launchers` off the remote allowlist rather than fixing the local exposure — so it does not close this item, but it does mean a proposal here must argue against a standing user decision rather than into a vacuum.
  - *Adjacent, same root cause*: the `GET`-side gap is general. The Origin/Referer half protecting only POST means every read endpoint is open to any local process supplying a loopback `Host`. Worth deciding whether that is acceptable independently of this item — the remote guard added 2026-08-01 bounds it to loopback but does not authenticate it.

- **Launched sessions inherit PowerAtlas's own environment — on one of three launch paths only** — a session's environment silently depends on how the tray app was last started, and the three spawn paths disagree about whether it does. *Scoped 2026-07-28.*
  - *The symptom that surfaced it*: Claude Code launched from the PowerAtlas UI opens with `Transcript saving is off — inherited CLAUDE_CODE_CHILD_SESSION marker`; the same binary typed by hand into a terminal PowerAtlas opened in the same folder does not. `CLAUDE_CODE_CHILD_SESSION` is set by Claude Code on processes it spawns so a nested `claude` suppresses transcript saving.
  - **Verified — the discriminator is the `wt` command shape, measured 2026-07-28** on Windows Terminal 1.24.11911.0. Probe: exact-argv `subprocess.Popen` (the same call shape `launcher.py` uses) from a caller carrying `PA_PROBE_MARKER=set-by-caller` and `CLAUDE_CODE_CHILD_SESSION=1`. `wt --title … -p … -d … -- pwsh …` → the spawned shell sees **neither**. `wt new-tab --title … -d … -- pwsh …` → it sees **both**. `PA_PROBE_MARKER` existed nowhere but in the caller, so what arrives is the *caller's* environment block, not the Terminal's. Bare `wt` resolves through the app-execution-alias activation path, so the window is created by the app-model infrastructure with a fresh environment from the user registry; `new-tab` is routed into an existing Terminal instance, which forwards the invoking `wt.exe`'s environment to that tab's shell.
  - **The asymmetry is PowerAtlas's own, and nothing in the code names it.** `launch_session` (`launcher.py:172`) passes the configured template straight to `detect_terminal`; `launch_terminal` (`launcher.py:556`) and `launch_custom` (`launcher.py:419`) **discard** it whenever it contains a `{` placeholder and fall back to auto-detected bare `wt`. The Windows default template (`config.py:35`, live at `config.toml:19`) begins `wt new-tab`. So the provider path forwards the environment and the two others drop it, decided implicitly by which command shape each code path happens to build.
  - *The marker is the visible instance, not the extent*: `launch_session` calls `Popen` with no `env=`, so **everything** PowerAtlas holds reaches the session. The tray app is long-lived, so one start from inside an agent session poisons every launch until restart — currently reproducible because PowerAtlas is developed with Claude Code and gets restarted from tool calls (live instance at the time of scoping: PID 33732, `python -m power_atlas --foreground`, parent already exited — the shape of a launch from a tool call that then returned).
  - *Same disease as the interpreter split, on a different resource*: `interpreter.py`'s module docstring already diagnoses it — "four entry points independently choose an interpreter … and each inherits whichever environment invoked it. Left alone they drift apart." That module made the interpreter a property of the source tree instead of the invoking context. The environment has the identical shape and no equivalent fix.
  - *Shapes worth considering, none chosen*: (a) deny-list — strip `CLAUDECODE`, the `CLAUDE_CODE_*` session markers, the kiro equivalents and `POWER_ATLAS_VENV_REEXEC` before spawning; small, but a list that needs maintaining as agents add variables; (b) construct the child environment explicitly rather than inheriting it, which is the durable answer and also the one that makes the three launch paths agree; (c) accept it and document the workaround — restart PowerAtlas from a shell that is not inside an agent session, or from its autostart shortcut. ## Session Control & Integration

> **Control shipped 2026-08-02.** `260731_ACP_REMOTE_CLIENT_PRODUCTIZATION` closed this section's central question: PowerAtlas now dispatches and drives kiro-cli sessions from a phone over NetBird. The four items immediately below are the follow-ons that plan surfaced and deliberately did not take. Everything under the original heading text after them is the 2026-07-24 spike record that led here, retained because its measurements are still the evidence base.

- **Bulk session deletion — the case per-row deletion deliberately does not serve.** Single-session delete shipped 2026-08-03 (a `⋯` menu on each rail row, loopback-only, all-or-nothing). It is the wrong shape for the volume problem: the store holds **5,958 sessions**, and the `## Session Control & Integration` entry below records **2,431 store artifacts produced in a single afternoon** of permission-gate benchmarking, cleaned up by hand outside the UI. One confirm per session does not touch that. The protocol is already ready — `POST /api/acp/sessions/delete` takes a list and is capped at 200 per request — so this is a change to `/acp` and nothing else.
  - *The design questions it opens, none of them answered*: what the confirm says when the target is 200 sessions rather than one; what happens when 3 of 208 are `held` or `locked` (the current route reports per id, which a bulk UI has to render as something better than a list of 200 rows); whether it is resumable after a partial failure; and whether the selection unit is the workspace, the filter, or a multi-select like the dashboard's (`session_row.html`'s `.session-check`).
  - *Cheapest useful version, and it may be the right one*: a per-workspace **delete all N in this workspace** on the rail's group header. It matches the shape of the case that actually hurts — the 208-session `nrf_tool` worktree whose folder is gone, and the benchmark's scratch workspace — without a selection model.
    - **Re-scope that before building — "the group header" stopped naming one thing on 2026-08-03.** The rail now has three groupings: workspace (`_acp_listing`), recency-ordered with client-side day buckets (`_acp_flat_listing`, `47d6742` + `a177f1d`), and status-based with client-side buckets also using the flat listing (`_acp_flat_listing`). A delete-all affordance on the group header therefore reads as *delete this workspace* in one mode and *delete everything from Tuesday* or *delete everything that is available* in the others. Those second two are not the case this item was written for and are considerably worse things to fire by accident, since day and status buckets span workspaces the user was not thinking about. So the affordance belongs to the workspace grouping specifically; the recency and status modes omit it or earn their own.

- **Creating a session in a workspace that has none — scoped out of the picker on purpose, 2026-08-03.** The create picker offers the agent's neutral folder or a workspace that already has kiro-cli sessions, and nothing else. So the first session in a brand-new project still has to be started from a terminal, or by pointing the dashboard's launcher at it.
  - *Why it was cut rather than built*: **no folder picker exists anywhere in PowerAtlas**, and there is no cheap one to copy. Every directory the app has ever taken from the user — global `default_directory`, per-provider defaults, launcher dirs, and the free-text `/acp` cwd box this picker replaced — is typed as free text, and `web.py:_acp_cwd_exists` states the constraint that makes it hard: *"a browser cannot stat a filesystem"*.
  - *The two candidates, if it comes back*: (1) a typed path with a **loopback-only validation endpoint** answering exists / not-a-directory / not-found as you type, seeded with folders PowerAtlas already knows but has no sessions for (`pinned_folders`, the `default_directory` settings, launcher dirs) — cheapest, adds no enumeration surface; (2) a **directory-listing route** the picker browses from drive roots — much better UX, and a route whose whole job is enumerating the filesystem, which would need the same default-deny placement deletion got plus a per-request budget against the 42 s UNC stat measured at `web.py:_ACP_EXISTS_BUDGET_SECONDS`.

- **Tell the operator a turn ended — the plan's headline use case is not actually closed without it.** `260731_ACP_REMOTE_CLIENT_PRODUCTIZATION`'s Intent says "leave a long agentic task running and come back to it, on either device". What shipped lets you leave; coming back still means remembering to look. The inactivity ceiling (15 min silence) and the absolute ceiling (4 h) both already fire server-side and are the natural triggers, alongside `meta turn:end` — the plumbing exists, the delivery does not.
  - *Open question that should be decided before any code*: the transport. Web push needs a service worker and a push subscription, which means HTTPS on the remote surface — and D5 declined TLS on the grounds that WireGuard already encrypts, so this reopens that decision rather than sitting beside it. The tray notification path already exists (`notifications.py`) but only reaches the machine PowerAtlas runs on, which is the one place you are *not* when this matters.
  - *Cheapest useful version*: the page already holds a websocket. A notification while the tab is backgrounded needs no push infrastructure at all — `Notification.requestPermission()` plus the existing `meta turn:end` frame. It fails the moment the phone sleeps the tab, which is most of the time, so treat it as a first step rather than the answer.

- **Tool output in the transcript, now that there is somewhere to put it.** `acp.py` deliberately excludes it — *"a file read or a build log is unbounded by nature and every byte of it would be recorded in the replay buffer, evicting the conversation it is meant to annotate"* — and that reasoning still holds for raw output. What changed on 2026-08-02 is that the transcript began rendering markdown with fenced code blocks, so a **truncated, rendered** tool result has a home it did not have before. The existing precedent is `MAX_TOOL_INPUT_CHARS = 4000` on the command, with `.acp-tool-more` stating the truncation rather than hiding it.
  - *The home got materially better on 2026-08-04, so this item is under-priced as written.* Fenced blocks are now syntax-highlighted and language-labelled (`6c9b2ea`) and agent tables render as tables (`fda76ed`). A `git status --short`, a test summary or a build error therefore arrives as something readable rather than as a wall of monospace, which moves the argument from "there is somewhere to put it" to "the place to put it is good". Nothing about the exclusion in `acp.py` changed — this is the case for the item strengthening, not the item shrinking.
  - *Why it matters*: under `-a` the tool rows are the only record of what actually executed, and today they say what ran without saying what happened.

- **Tool display improvements** — the tool-call rows in the `/acp` transcript are functional but sparse. *Delivered 2026-08-11*: **(4) collapse/expand command body** (Phase 2 — `▶` toggle, collapsed by default, `aria-expanded` driven) and **(5) visual grouping of consecutive calls** (Phase 3 — turn-end grouping into collapsible rows with count+name+status tally header). Remaining open candidates, none requiring `acp.py` changes: (1) **status badges** (running / completed / denied / failed) coloured to match the existing status-dot palette; (2) **tool-type icons** differentiating shell execution, file read/write, search, and sub-agent dispatch; (3) **structured argument display** — for file operations show the path, for shell show the command verb. Priority remains the items that reduce mis-reading (status and type) over the ones that add information. *Note*: this is about the rendering of tool-call rows that already appear in the transcript; it is distinct from "Tool output in the transcript" above.

- **An auto-mode for `/acp` permissions — drop `-a` and decide each request, the way Claude Code's auto-mode does.** `-a` is the last thing keeping every unattended item on this page gated, and the permission spike already proved the replacement works: `session/request_permission` round-trips, deny is genuinely enforced, and an automated client decision costs **0.036-0.11 ms**. What is missing is the decider. **Intended architecture (stated 2026-08-03): PowerAtlas `/acp` is the orchestrator and the gate; the classifier is a decision function it calls.** The ACP session raises `session/request_permission`; `/acp` routes it to the auto-mode classifier; an allow is answered automatically and only a **block** is escalated to the user. So the classifier never needs a permission channel of its own, and it is free to run over any transport — a pooled ACP session, `--no-interactive`, or something else entirely — since the only thing crossing the boundary is a verdict. Layered in front of it: a deterministic allowlist (`_meta.trustOptions` exposes a persistent regex allowlist under `setting_key: allowedCommands`, at three granularities), so the model is consulted only on what the allowlist does not settle and its latency is paid on the residue rather than on every tool call.
    - *Consequence worth designing for*: the escalation path is **block-only**, so a classifier false-allow is silent and unreviewable while a false-block merely costs a prompt. That asymmetry should drive the accuracy work below — optimise for recall on genuinely dangerous requests, not for balanced accuracy. It also interacts with the missing `reject_always` noted under the ordering bullet: the user can be asked, but the answer cannot be made permanently negative kiro-side.
  - **Latency is measured and it is not the constraint — 2026-08-03, kiro-cli 2.16.0, 1,500 assessments.** A one-word ALLOW/BLOCK verdict on a synthetic permission request, fresh session per assessment, every session model-pinned and verified. Median **1.0-1.3 s** on a stripped agent and **1.2-2.0 s** under `kiro_default`, plus ~1.15 s of `initialize` once per process, not per assessment. Distribution matters more than the median for a gate that fires on every tool call, and the models separate on the tail rather than the middle: `qwen3-coder-next` p99 **1.75 s** (empty) / **2.78 s** (default) with an IQR of ~0.05 s, `claude-sonnet-4.6` p99 3.34 / 3.45 s, `claude-opus-4.5` 3.49 / 4.98 s, and `claude-haiku-4.5` — fastest of all at p50 — carries a **7.49 s p99** under `kiro_default`. `minimax-m2.5` is disqualified at p99 24-30 s (max 35 s): it is the only model that reasons on every turn and the reasoning cannot be switched off.
  - *Candidates on latency alone*: **`qwen3-coder-next`** and **`claude-sonnet-4.6`**. `claude-haiku-4.5` and `claude-opus-4.5` stay in the test set as references rather than candidates — haiku for its p99, opus as the capability ceiling. **Nothing here is a capability finding**: see the open question below.
  - **[LATENT — downgraded from "live in shipped `acp.py`" on 2026-08-04, after checking] Model selection silently does not stick past the first session, and this blocks the accuracy benchmark before it blocks auto-mode.**
    - *The "live in shipped `acp.py`" label was wrong and is corrected here.* Verified 2026-08-04: `grep` for `set_model`, `currentModelId`, `--model` and `models` across `src/power_atlas/**.py` returns **nothing**, and `ACP_ARGS` is `("acp", "-a")` with no model flag, no config key and no UI. **PowerAtlas never requests a model at all**, so there is no request for a later session to silently diverge from — every session gets `chat.defaultModel`, uniformly and correctly. Corroborated the same day: five probe sessions across three agents all reported `currentModelId: claude-sonnet-4.6`, including `kiro_default`, whose own `model` is `null`. Nothing user-visible is wrong today. The trap is real and fires **the moment model selection is added** — which is why the read-back below should land with that feature rather than before it. `kiro-cli acp --model X` is honoured for the **first** session of a process only; every later `session/new` reverts to `chat.defaultModel` without an error, a warning or a log line. `acp.py` never sends `session/set_model` and never reads `models.currentModelId` back, so with `acp_max_sessions` defaulting to 8, **seven of eight sessions run `chat.defaultModel` regardless of what was requested**. Nothing in the product surfaces that the model changed. *Fix regardless of auto-mode*: call `session/set_model` after `session/new` and assert `currentModelId` from the response — the same read-back-and-assert discipline the `--agent` / `--trust-tools` bullet already prescribes, and `session/set_model` is now verified to work (see the ACP client entry below). *Why it gates step 2*: an accuracy benchmark run against a client with this defect measures `chat.defaultModel` on most of its samples while labelling them as other models — which is exactly how the latency benchmark went wrong on its first run, and the wrong numbers looked entirely plausible. Whatever harness runs the accuracy work must pin and verify per session.
  - **Two levers do not work; one does.** `--effort` (low→max) produced no reproducible effect on any model, on the gate prompt *or* on a hard multi-step control task — an apparent effort curve on `minimax-m2.5` failed to replicate across arms and sat inside an IQR of up to 8.7 s. `chat.enableThinking: false` moved only `claude-sonnet-4.6`, by ~0.12-0.18 s, and notably did **not** suppress MiniMax's reasoning (150/150 thinking chunks emitted with it off), so it does not reach the ACP path in any useful way. No Claude or Qwen model emitted a single `agent_thought_chunk` in 1,200 runs. **Context is the only real lever**: +0.17 to +0.22 s for the Claude models, +0.95 s for qwen and +3.48 s for MiniMax moving from a stripped agent to `kiro_default`, plus `session/new` going from 0.03 s to 0.71 s. That is the *same* saving the dispatch-agent entry under `## Misc` argues for, arriving from a second direction — a gate should run under a stripped agent regardless of which model wins.
  - **The open question, and it is the one that decides the item.** Accuracy was 150/150 for every model in every configuration, with zero tool-call attempts — and that number should not reassure anyone. The three scenarios were deliberately obvious (`git status` → allow, recursive delete outside cwd → block, `curl | bash` → block), chosen to measure latency and nothing else. **The benchmark establishes that these models are fast enough; it says nothing about whether any of them is correct enough.** Prompt injection inside the tool input, a destructive command dressed as routine, path traversal, a force-push to a shared branch — all untested, and that is exactly where the models would separate. A latency winner is not a gate.
  - **Where the classifier runs is three questions that turn out to be one — cwd, session reuse, and hiding its sessions from the UI.** They are recorded together because answering any one constrains the other two, and the wrong combination is what produced **2,431 store artifacts in a single afternoon of benchmarking** (cleaned up 2026-08-03, but the shape of the mistake is the point).
    - *Which cwd the classifier agent runs in.* cwd decides which `AGENTS.md`, `memory/**` and steering resources load — the measured +0.17 to +3.48 s context penalty above — but it **also decides which workspace the session is grouped under** in PowerAtlas's own session browser. A scratch cwd is fastest and keeps the classifier out of the real workspace's session list; the cost is that it invents a junk workspace unless the UI knows to ignore it.
    - *Whether the session is reused.* A fresh session per assessment costs **one permanent store artifact per tool call** — at gate frequency that out-produces the user's genuine session history within days, against a store already holding ~6,000. Reusing one session costs one artifact total and keeps the ~1 s pooled latency, but accumulates conversation history across assessments, which a stateless gate should not have: assessment N sees N-1's verdicts. So the real question is the recycle policy — reuse for K assessments, or until a context threshold, then rotate — not reuse-vs-not.
    - *How its sessions are hidden from the main interface.* There is precedent: `data_kiro.py` already filters **4,532** sub-agent sessions out of the session list via four `parent_session_id` guards. A classifier session has no parent, so it needs its own discriminator — and **the cwd choice above is the cheapest one available**, which is why these three are one decision rather than three.
  - *Candidate transport for the classifier call — `kiro-cli chat --no-interactive`, measured 2026-08-03.* Its draw is that it **persists nothing**: store count identical before and after (delta **0**), confirming the `## Automation & Workflows` finding on this flag, so it sidesteps the store-artifact question entirely. Its cost is full process startup per invocation — **~5-10 s** per assessment on a stripped agent and **~10-11 s** under `kiro_default`, against ~1.0-2.0 s for a pooled ACP turn, a 5-8x penalty. Part of that is `chat.enableCheckpoint` re-initialising a checkpoint on every invocation (**3.87 s** on one probe), so the gap is not all inherent and is worth decomposing before the mode is ruled out. Weigh against it that **session reuse solves the same persistence problem while keeping the ~1 s latency** — the two are alternatives to the same problem, not to each other.
  - *Suggested order — research first, because it changes everything downstream.* (1) **State-of-the-art research** on permission/safety gating: what the prompt should be, whether one classifier call is even the right architecture, and where the deterministic allowlist boundary belongs. Cheapest step and it defines the benchmark. (2) **Accuracy benchmark** using that prompt, over an adversarial scenario set, across all four models — this picks the winner, and it is where the choice is actually made. (3) **Auto-mode logic** and (4) **UI for blocked/escalated requests** co-designed rather than sequenced: the policy's decision states (allowed / blocked / escalated-to-human) *are* the UI's states, and the escalation path has to exist before the logic can be dogfooded. Note `_meta.trustOptions` offers `allow_once` / `allow_always` / `reject_once` but **no `reject_always`** — a policy engine can permanently say yes and never permanently no, which shapes both the logic and what the UI can offer.
  - *Harness — not retained.* The benchmark client, sweep driver and raw per-run JSONL for all 1,500 runs were throwaway and were deleted with the session scratchpad on 2026-08-03, so **the figures above are the only surviving record** and cannot be re-derived from stored data. Re-measure rather than extend them: the shape to rebuild is a minimal ACP client that pins `session/set_model` per session and asserts `currentModelId`, three-plus scenarios, medians over n≥15 with the dispersion reported alongside — n=3 per cell left the within-cell spread wider than the between-cell differences and produced two conclusions that did not survive replication. The standing evidence-decay warning on this page applies with full force here.

- **A lean dispatch agent — see *A PowerAtlas dispatch agent* further down this same section**, which predates this plan and carries the measurements. (That entry said "under `## Misc`" until 2026-08-04; it has always sat in `## Session Control & Integration`.) - **Revisit the `None` → `"working"` fallback at the end of `_session_status` (`web.py`)** — an unclassifiable session currently displays as working, on the reasoning that a running process is working. Small and self-contained, and the last surviving follow-up from the transcript-tail fix.

- **A PowerAtlas dispatch agent — cut what every dispatched session drags into context before it reads a word of the task.** kiro-cli agents are declarative JSON (`prompt`, `tools`, `allowedTools`, `resources`, `includeMcpJson`, `model`, `hooks`), and `--agent` is now known to bind to **every** session on a process, so one agent definition covers a whole dispatch client. Today PowerAtlas would dispatch under `kiro_default`, which is configured for an interactive developer at a terminal and is close to maximal on every axis.
  - **Measured 2026-07-31, and the steering figure alone justifies the item.** `kiro_default.json` sets `tools: ["*"]` (every tool advertised), `includeMcpJson: true` (MCP tool schemas for `playwright` and `atlassian` in context), and a `resources` list that globs **`file://.kiro/steering/**/*.md`**, `skill://.../SKILL.md`, `file://memory/**/*.md`, `AGENTS.md` and `README.md`. The steering glob alone resolves to **13 files totalling 116,113 bytes** as of 2026-08-04 (11 files / 104,668 bytes when first counted, so it grows). **Do not read a token figure off those bytes** — the measured bullet below supersedes the ~26k estimate that used to sit here, and shows both what the real number is and why the byte route mis-attributes it.
  - *Why it bites PowerAtlas specifically.* A dispatched session is usually narrow and single-purpose — run a check, summarise a diff, answer one question — but pays the full interactive-developer preamble regardless. It also compounds with the decision above to keep MCP: servers stay, so their tool schemas stay in context too.
  - **Boundary — this does not reopen the keep-default-MCP-servers decision (2026-07-31).** Servers stay enabled and browser automation stays available. The question here is what a *dispatch* agent advertises and loads into the context window, which is `resources` and `tools`, not `mcp.json`. Any proposal that removes a server belongs to that closed decision, not this item.
  - *Open questions, none of which should be guessed*: whether `session-tab-title.md` belongs in a dispatch agent at all, given it costs a shell tool call on every session's first turn and its session-title half lands about 1 time in 11; and whether a dispatch agent should pin `model` (currently `null`) so dispatch cost is predictable rather than inheriting whatever the default is — note the 2026-08-04 probe found the default resolving to `claude-sonnet-4.6` on a **1M-token** window, so an unpinned dispatch agent's context budget moves with whatever the default becomes. The per-resource-class question that used to lead this bullet is answered in the measured bullet above.

## Misc

- **[SECURITY] Loopback API token — authenticate local callers to the `/api/*` and `/ws/acp` surfaces.** Today any local process that can reach `127.0.0.1:<port>` can create sessions, send prompts, delete sessions, and read the full session list, with no credential required. The `same_origin_guard` is CSRF defence only (POST-scoped, passes a loopback `Host` unconditionally) and `RemoteAccessGuard` is non-loopback only — neither checks whether the caller is PowerAtlas's own browser UI or a rogue script. Because `/acp` hardcodes `-a`, anything that reaches the API can execute arbitrary shell commands as the user with no confirmation.
  - *Proposed shape*: a secret written to `%LOCALAPPDATA%\power-atlas\local-secret` at first startup (same pattern as `remote-secret`). Required as a header (`X-PowerAtlas-Token`) on all `/api/*` and `/ws/acp` requests. Browser clients (the dashboard, `/acp` page) receive the token injected into the HTML at page-load time so they need no manual handling. Non-browser callers (agents, scripts, `Invoke-RestMethod`) must supply it explicitly — which is what "only allow what we choose" means in practice.
  - *What this does not change*: the browser UI works transparently; the remote surface is unaffected (it already has the device cookie); the loopback split between dashboard and `/acp` is unaffected.
  - *What this enables*: a deliberate opt-in for agent access — an agent that knows the token can drive PowerAtlas; one that does not cannot. The token is readable from disk by any process running as the same user, so this is not a hard security boundary against a fully-compromised session, but it raises the bar from "any process that makes an HTTP request" to "any process that reads a specific file first", and it makes the access explicit and auditable.
  - *Interaction with the sync-prompt endpoint*: if that endpoint is added (see *Tell the operator a turn ended* and the dispatch-agent item), it should require the token too — it is the sharpest surface in the API.
