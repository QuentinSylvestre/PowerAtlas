## Intent

### Problem statement & desired outcomes

PowerAtlas shows and launches sessions for three providers: Claude Code (`claude-code`), kiro-cli v3 (`kiro-cli-v3`) and Kiro IDE (`kiro-ide`). OpenAI's Codex is installed on the user's machine and keeps its sessions under `~/.codex`, but PowerAtlas cannot list, read, launch or show the live state of them.

The outcome is a fourth built-in provider, id `codex`, display name "Codex", behaving like Claude Code and kiro-cli in the dashboard. Three tiers were chosen by the user (Q1, "iso kiro-cli and claude code, A+B+C"):

- **A.** Launch, discovery and transcripts: Codex in the filter chips, "New AI session" menu, launcher tile and provider settings; sessions in the workspace rail; full transcript view; New and Resume launch.
- **B.** Live dot and Resume state.
- **C.** Overview: live tiles and the usage section.

A documentation deliverable rides with it: improve the stored knowledge about Codex in `docs/KNOWLEDGE.md`, the way the Claude Code and kiro-cli findings are already stored there.

### Success criteria

- SC-1: **Provider surfaces.** `codex` appears in `/api/available-providers` (so the filter chip, "New AI session" menu and launcher tile), with display name "Codex", default colour white (`#ffffff`), and the tinted terminal glyph as icon (`codex.exe` has no embedded icon, see § 1). A "White" swatch is added to the Card color swatch group in `launcher_modal.html`. A provider-settings entry for `codex` works (enabled, colour, default args, default directory). The provider colour stays legible everywhere it is drawn.
- SC-2: **Sessions in the rail.** Codex top-level sessions are listed per workspace. Sub-agent threads are excluded. Sessions that originate from the VS Code extension and the desktop app are included. Workspace identity goes through `data._normalize_path`, so the same folder written with an upper-case and a lower-case drive letter groups as one workspace. Title, first prompt, last prompt and reply tail are shown, taken from real user prompts, not from injected context.
- SC-3: **Transcript.** The full-transcript view renders user and assistant text and tool calls for a Codex session, with tool success taken from the tool's own exit code where Codex records one. A rollout of tens of MB opens without hanging the dashboard, bounded by an unconditional read and event cap. A session whose writer lock is held stays openable (transcript and Overview tile).
- SC-4: **Launch and Resume.** New session and Resume run `codex` and `codex resume <id>` in a terminal in the workspace, with no baked flags (Q3). Per-provider `default_args` apply. Only the Resume button is hidden while the thread's writer lock is held; the row stays enabled.
- SC-5: **Live dot (Claude rule, Q5).** A terminal `codex.exe` process marks a session live by id when `resume <id>` is on its argv, or by workspace plus a rollout record newer than 300 s. The daemon and helper `codex.exe` processes (`app-server`, `exec-server`, and similar subcommands) never mark anything live. As with the Claude rule, a session held by the desktop app or the VS Code extension has no terminal process and shows no dot.
- SC-6: **Overview.** Live tiles show Codex events from rollout tails and rank by real activity. The usage section shows Codex agent time, per-day session counts and token totals with the cache-hit ratio. The three "any other provider falls through to the Claude or kiro parser" sites are replaced by explicit per-provider dispatch, and tests pin that an unknown provider is not parsed as another provider's format.
- SC-7: **Parser hardening.** The Codex reader caches by (mtime_ns, size) and never assumes a file only grows. It tolerates torn or partial lines, in-place rewrites (compaction), unknown record shapes, wrong-typed fields and unknown `cli_version`; one bad file never blanks discovery and no public function of the adapter raises. Reads are bounded: head, tail and transcript windows for lists, tails, status and transcripts. Legacy rollouts without the `payload` wrapper and `archived_sessions/` are ignored without error.
- SC-8: **Tests.** Existing test files are updated (`tests/test_data.py`, `tests/test_launcher.py`, `tests/test_web.py`, `tests/test_transcript_translator.py`, `tests/acp_page.test.mjs` for the Resume gate and usage chart). Adapter tests patch module-level Codex roots (sessions, session index, lock folder) in autouse fixtures of both `tests/test_data.py` and `tests/test_web.py`, and a guard test fails if any root still points at the real home. Fixtures are synthetic, built from the record skeletons in § 1: no real session content or ids from a developer's store enter this public repository. `pytest` (with `--timeout=300`) and `node tests/acp_page.test.mjs` pass.
- SC-9: **Docs.** README lists Codex (providers, features, config example, usage notes). `docs/KNOWLEDGE.md` gains a dated, measured Codex section: store layout, writer lock, process shape, record shapes across versions, hardening evidence with upstream issue references, and the explicit statement that OpenAI publishes no stability guarantee for the rollout files.
- SC-10: **Probe cleanup.** At the end of execution, the Codex probe artifacts listed in Phase 5 are removed, with the user's approval of each.

### Scope boundaries & non-goals

- No driving of Codex from `/acp`. The ACP layer is kiro-cli only, and the roadmap already treats a second ACP provider as a driver-abstraction spike (`plans/ROADMAP.md`, "Spike: drive Claude Code over ACP through an adapter").
- No Working/Waiting/Errored verdict for Codex rows. Only held kiro-cli v3 sessions get one today.
- No notifications for terminal Codex sessions. Notifications are ACP-only today.
- No context-pressure metric for Codex (kiro-cli only), and no cost estimate.
- No SQLite accelerator, no `codex app-server` integration. Both are deferred with reopen triggers (Follow-up Work).
- No bundled Codex logo (Q6). No baked launch flags (Q3).
- No append-only fast path for the Codex reader (it would break SC-7's "never assume a file only grows").
- Linux is best-effort: lock and process behaviour were measured on Windows only.

## 1) Current State

Claims marked "measured" were taken on 2026-10-01 with codex-cli 0.159.2 on Windows 11, on the developer's own `~/.codex`, by read-only scripts that print counts, key names and record types only. `auth.json`, `config.toml`, `secrets/` and message text were never read. They carry an expiry that a `file:line` citation does not: re-run them if this plan is executed much later or against a newer Codex. Code citations name a function or unique string, with a line number beside it where it helps; line numbers in `index.html`, `style.css` and `launcher_modal.html` moved during this session (commits `4348d4c`, `8abd4a3`), so re-find them by the named anchor.

### Provider mechanics in the code

- **Registry.** `data.PROVIDERS` (`src/power_atlas/data.py` ~176) maps a provider id to a module with eight duck-typed functions: `is_available`, `discover_workspaces`, `load_sessions`, `refresh_stale_entries_for_cwd`, `find_session_workspace`, `get_session_tail`, `get_first_prompt`, `get_full_transcript` (reference implementation `data_claude.py`). "Installed provider" means its session data exists on disk, not that the binary is on PATH (`data.available_providers`); `/api/available-providers`, `/partials/launchers`, the "New AI session" menu and the filter chips all derive from it. `Session.extra_fields` must stay the last field of `data.Session`. `data._normalize_path` casefolds and expands 8.3 names on Windows; caches key on the normalised cwd and keep the original spelling separately. Not every entry point is guarded against a raising adapter: `available_providers`, `_find_pinned_session_workspace` and `warmup_pinned` (which catches only `OSError`) are not, and one raise in `warmup_pinned` skips `warmup_done.set()`.
- **Reader model.** The Claude adapter is the model: bounded head scan (500 lines) and tail scan (256 KB), parse cache keyed by (mtime, size) (`data_claude._parse_session_cached`) in `data.BoundedCache` (LRU; a cache smaller than the file count thrashes on a sequential scan). Its head cache assumes append-only files (`_head_cache`); Codex does not allow that assumption, and its transcript reader uses `readlines()`, which must not be copied. `data.get_session_tail` and `data.get_first_prompt` have no callers in `src/` (grep) but remain part of the contract.
- **Launch.** `launcher.py` has `_PROVIDER_DISPLAY`, `_PROVIDER_BINARY`, `_PROVIDER_TERMINAL` and `_build_provider_args`, which raises `ValueError("Unknown provider")` for an unregistered id (launch then fails with a toast); `launch_session` appends `default_args` after the provider args. The binary lookup falls back to the id itself, so `codex` resolves without a table entry. The launcher's id regex (`launcher._SESSION_ID_RE`, `^[\w\-]+$`) accepts a leading `-`, so an id like `--flag` would reach `codex resume` as an option. `launcher._build_child_env` scrubs only `CLAUDE*` markers.
- **Web tables.** `web.py` has `PROVIDER_COLORS`, `PROVIDER_DISPLAY_NAMES`, `_PROVIDER_BINARY_DISPLAY` (`PROVIDER_BADGES` has no readers). Resolved colour: the user's provider setting, else `PROVIDER_COLORS`, else `#888` (`_get_provider_color`). The icon route `/api/launcher-icon/provider--<id>` extracts the icon embedded in the provider binary and caches it, else serves the 24x24 outline terminal SVG (`icons._TERMINAL_ICON`) stroked with the provider colour. `claude.exe` has 2 icon resources, `kiro-cli.exe` 0, `codex.exe` 0 (measured), so Codex gets the tinted glyph. `/api/session-transcript` runs only `get_full_transcript` in a thread; `translate_transcript` (a markdown parse per message) runs on the event loop.
- **Front end (`index.html`, `style.css`, `launcher_modal.html`).** Anchors: `DASH_OV_PROVIDERS` (tile icon); `DASH_OV_USAGE_PROVIDERS` (fixed array that silently drops any other provider from the usage bars, legend and tooltip); the Resume button whitelist in `dashRailRowNode` (`session.provider === 'kiro-ide'` and siblings; a Codex row would get no Resume button); `_providerBinaryDisplay` and `_providerTerminal` (must mirror the Python dicts; missing the JS map was a shipped bug for Kiro IDE); `dashOvUsageTokens` (hard-coded "Claude Code only") and its call `dashOvUsageTokens(usage.claude_tokens)`, with the "Still counting sub-agent transcripts" note appended in the partial case; the Card color swatch group in `launcher_modal.html` (`id="launcherColorPicker"`, 13 entries including "No color", no white; `.launcher-appearance .color-picker-swatches` is a 7-column grid, so 14 fills two rows); `.dash-ov-bar-seg.is-claude/is-kiro-cli/is-kiro-ide` in `style.css`. The UI is dark-only (single `:root`). **Availability `locked` is not a Resume-only state:** in `dashRailRowNode` it sets `row.disabled = true` (the transcript cannot be opened), blocks the row click, files the row under the "Locked elsewhere" status bucket (`DASH_STATUS_BUCKET_ORDER`, `dashRailAvailability`), and the Overview tile refuses a click when `tile.availability === 'locked'`. This plan therefore never uses it for Codex.
- **Live state.** `presence._PROVIDER_SPECS` covers `claude-code` and `kiro-cli-v3` (binary names plus an id flag). `_match_provider` matches on process name or argv0 basename and rejects `--type=` argv. `_extract_session_id` takes the token after the flag, position-agnostic. A provider absent from the specs is never live. `Snapshot.is_live(provider, cwd, session_id)` is id-based; the workspace-plus-recency branch lives in `web._session_is_live` (`snapshot.is_live` or a provider process in the cwd and the transcript recency within 300 s, via `status_classifier._resolve_jsonl_path`). `_resolve_jsonl_path_uncached` returns None for an unknown provider; only kiro has a path cache. `_acp_availability` returns `available` for any id not starting with `sess_`; the two row builders (`_row_dict` in the session listings) read `availability.get(...)`, and the Overview tile takes availability from `deps.acp_availability`.
- **Overview.** `overview._line_events` sends `claude-code` to `_claude_events` and every other provider to `_v3_events`; `_transcript_cwd` treats every non-kiro provider as Claude (and reads only `_CWDLESS_HEAD_BYTES`, 64 KiB, of the head); `_parse_usage_file` treats every non-kiro provider as Claude, and `_summarize` expects it to return a dict. `live_sessions` ranks tiles by `st_mtime` of the transcript. `_usage_roots()` returns a 3-tuple unpacked in `_usage_files` and indexed in `_ide_daily`, and is patched with 3-tuples by existing tests (`tests/test_web.py`, the autouse `isolated_config` fixture and `TestOverviewUsage.stores`), so its arity must not change. `_usage_files` lists files modified since the window start and the warm pass routes only `_CLAUDE_SUB` files to stage 2 (`stages[provider == _CLAUDE_SUB]`), because Claude sub-agent files were 548 of 682 in-window files and about half of a cold pass; stage 1 alone measured 3.4 s, 6.9-19 s under dashboard load. A glob error in the shared `_usage_files` loop fails the whole pass (state `error`) for every provider. The per-file usage summary is `{"provider","session_id","cwd","model","subagent","days"}` with per-day `{"active","agent_seconds","tools","tokens":{"input","output","cache_read","cache_creation"},"context_peak"}`; `_USAGE_SCHEMA = 1` must be bumped when a parser's output shape changes. `usage_summary` accumulates tokens for `provider == _CLAUDE` only and returns them as `claude_tokens` with `cache_hit_ratio`. Tile events are `{"kind":"text","role","text"}`, `{"kind":"tool","name","arg"}`, `{"kind":"result","ok"}`.
- **Translator.** `transcript_translator._TOOL_KIND_BY_NAME` / `_TOOL_TITLE_BY_NAME` know `shell`; other names fall back to kind `other`. It drops a `tool_result` whose `success is None`, leaving the call at "started"; `_derive_tool_display` falls back to `json.dumps(tool_args)` with no cap.
- **Tests and rules (`AGENTS.md`).** Provider adapter tests live inside `tests/test_data.py` (`TestClaude*`, `TestKiroIde*`, an autouse `_clear_cache` fixture); classifier and Overview tests inside `tests/test_web.py`. Nothing enumerates `PROVIDERS` by equality. `tests/acp_page.test.mjs` (~`for (const provider of [...])`) already lists `"codex"` as an unknown-provider canary and keeps passing. Python changes need a PowerAtlas restart and an agent must not restart without a per-task grant; template, CSS and static JS changes need only a hard reload; the node test is not part of pytest or CI (there is no CI); no new test files unless requested; README only for user-visible surface; `--timeout=300` for the full pytest run; `PYTHONPATH=src` in a worktree; `_check_test_names.py` pre-commit hook rejects duplicate test or fixture names. A live QA of the dashboard needs the `pa_local` cookie (see `AGENTS.md`).
- **Precedents.** `plans/done/260706-1653_KIRO_IDE_PROVIDER.md` and `plans/done/260701-2250_PROVIDER_LAUNCHER_UNIFICATION.md`; recorded lessons: browser-side maps must mirror the Python dicts, the README config example must list the new provider, `_group_workspaces` must dedupe and sort providers deterministically.

### Codex facts (measured; sources on the web are marked)

- **Binary.** `shutil.which("codex")` resolves to a native `codex.exe` (0.159.2); an npm shim (0.124.0) is shadowed by PATH order. `codex --help` lists no `acp` command; the programmatic surface is `codex app-server`.
- **Store.** `~/.codex/sessions/YYYY/MM/DD/rollout-<local timestamp>-<uuid>.jsonl`, one thread per file; 613 files, about 575 MB, largest about 28 MB. The first line is a `session_meta` record whose payload has `id`, `cwd`, `source`, `originator`, `cli_version`, `model_provider`, `parent_thread_id`, `history_mode`, `subagent_history_start_ordinal` and a large `base_instructions` (first line p50 about 17 KB, max about 42 KB).
- **Population.** 93 top-level sessions (65 VS Code extension, 4 desktop app, 24 CLI) and 509 sub-agent threads (`source` is an object with a `subagent` key; 244 are `guardian` reviewers). `source == "subagent"` is a wrong test because the value is an object. 11 oldest files (2025-08/09) lack the `payload` wrapper (Codex itself lists them as skipped in its rollout migration). 40 threads are archived under `archived_sessions/`. No top-level session has a `parent_thread_id`.
- **Catalogue.** `state_5.sqlite` `threads` agrees with the files on the top-level set (93 = 93). `thread_history_1.sqlite` is a projection of the rollouts (it stores a byte offset into each file). `has_user_event` is 0 on all 93 rows. `session_index.jsonl` (`id`, `thread_name`, `updated_at`) covers 47 of 93 top-level sessions and differs from the `threads.title` column for 44 of those 47.
- **cwd forms.** Plain backslash drive paths only (no `\\?\`). The VS Code extension writes a lower-case drive letter, the CLI an upper-case one; `_normalize_path` collapses 22 raw cwds into 18 workspaces.
- **Record key paths (measured, key names only; the skeleton fixtures are built from this list).**
  - Every line: `{ordinal, timestamp, type, payload}`; `type` is one of `session_meta`, `response_item`, `event_msg`, `turn_context`, `token_usage_record`, `world_state`, `inter_agent_communication_metadata`.
  - `session_meta.payload`: `id`, `cwd`, `source` (a string, or an object with a `subagent` key), `originator`, `cli_version`, `model_provider`, `parent_thread_id`, `history_mode`, `subagent_history_start_ordinal` (int, or null on 63 of 509 sub-agent rollouts), `timestamp`, `git`, `base_instructions`.
  - `event_msg.payload.type` and keys: `task_started` (`turn_id`, `started_at`, `model_context_window`); `task_complete` (`turn_id`, `started_at`, `completed_at`, `duration_ms` from 0.139 only, `last_agent_message`); `token_count` (`info.total_token_usage`, `info.last_token_usage`, `info.model_context_window`, `rate_limits`); `item_completed` (`item`, `thread_id`, `turn_id`, `started_at_ms`, `completed_at_ms`); `turn_aborted`; `thread_settings_applied`.
  - `item_completed.payload.item.type` and keys: `UserMessage` (`id`, `client_id`, `content`); `AgentMessage` (`id`, `content`, `phase`); `CommandExecution` (`command`, `cwd`, `exit_code`, `status`, `stdout`, `stderr`; newer versions only); `Reasoning`; `SubAgentActivity` (`agent_path`, `agent_thread_id`, `kind`). `content` is a list of objects with a `text` key; the element `type` values are not yet recorded (Phase 0).
  - `response_item.payload.type` and keys: `message` (`role`, `content`, `id`); `function_call` (`name`, `arguments` as a JSON string, `call_id`, `namespace`); `function_call_output` (`call_id`, `output` as a string or a list); `custom_tool_call` (`name`, `input` as a string, `call_id`, `status`); `custom_tool_call_output` (`call_id`, `output`); `reasoning` (encrypted); `compaction`.
  - `turn_context.payload`: `model`, `cwd`, `approval_policy`, `sandbox_policy`, `effort`, `turn_id`.
  - Token usage objects (`total_token_usage`, `last_token_usage`, `token_usage_record.usage`): `input_tokens`, `cached_input_tokens`, `output_tokens`, `reasoning_output_tokens`, `total_tokens`, and `cache_write_input_tokens` in newer versions.
  - Whether every record carries the top-level `ordinal`, and the `phase` values, are recorded in Phase 0.
- **Record shapes across 23 `cli_version`s (0.35 to 0.159).** Every era carries `task_started`, `UserMessage`, `AgentMessage`, `token_count`, `task_complete`, and `response_item` `function_call` / `custom_tool_call` with matching `*_output` records. `response_item` user-role messages include injected context (a `# AGENTS.md instructions` block of about 44 KB) in every era; across 738 `UserMessage` items none looked injected. `task_complete.duration_ms` exists only from 0.139. `token_count.info` exists in every era; `token_usage_record` only in the newest. Cumulative `total_token_usage` never decreased across 759 events in 60 sessions. `total_tokens = input_tokens + output_tokens` in 749 of 759 events, so cached tokens are a subset of input and reasoning tokens a subset of output. `turn_context.model` exists in every era.
- **Tool shapes.** Tool names seen: `shell_command` (dominant), `shell`, `apply_patch` (custom tool), `exec` (custom tool, 0.139 and later), `update_plan`, `view_image`, `wait`, `spawn_agent` and other multi-agent tools. A `shell_command` output is a string starting `Exit code: <n>`; older `shell` and `apply_patch` outputs are JSON with `metadata.exit_code`; `exec` outputs are lists with no exit code.
- **Sub-agent rollouts embed the parent's history.** 446 of 509 sub-agent rollouts carry an integer `subagent_history_start_ordinal`; in five sampled children every `token_count` event lay before that ordinal. Summing sub-agent rollouts naively multiplies the parent's tokens (a parent's cumulative total of 43.8 M sat beside children whose cumulative totals summed to 329.8 M).
- **Live session shape.** An interactive TUI is its own `codex.exe` whose cwd is the workspace. A new session has no id on argv; `codex resume <id>` carries it right after the `resume` token. A bare `codex` with no prompt wrote no rollout and no lock in 30 s. Every `codex.exe` that was running before the probes was infrastructure (`app-server` daemon, `exec-server`, `daemon pid-update-loop`). The rollout appeared about 15 s after launch with the first prompt, was readable while Codex held it open, and its Windows mtime stayed frozen while its size grew from about 23 KB to 166 KB. Every record carries a top-level ISO `timestamp`.
- **Writer lock.** `~/.codex/thread-writer-locks/<thread-id>.lock`, 0 bytes. A live session holds a byte lock: a non-blocking lock attempt failed while the session lived and succeeded once the owner was dead. Opening the lock file for read-write succeeded while it was held. Clean exits remove the file. A TUI also creates a second lock for a helper thread with no rollout. Resuming a locked thread fails inside Codex ("thread already has an active writer").
- **Upstream (web, no maintainer guarantees).** No documented stability guarantee for the rollout files ([openai/codex #45251](https://github.com/openai/codex/issues/45251), open, unanswered). The rollout is canonical and the SQLite projection desyncs ([#41079](https://github.com/openai/codex/issues/41079), [#38792](https://github.com/openai/codex/issues/38792), [#40342](https://github.com/openai/codex/issues/40342)). Compaction rewrote rollouts in place ([#45350](https://github.com/openai/codex/issues/45350)); an upgrade corrupted one ([#45150](https://github.com/openai/codex/issues/45150)); logs reach 0.7 to 2 GB ([#24948](https://github.com/openai/codex/issues/24948)). The desktop app holds the writer lock for every thread opened in a run until it exits ([#37450](https://github.com/openai/codex/issues/37450), Windows); an SSH-orphaned TUI keeps it ([#44063](https://github.com/openai/codex/issues/44063)). The documented stable interface is the app-server's `thread/list` and `thread/read` ([docs](https://learn.chatgpt.com/docs/app-server)). A third-party tool's issue titled "read-only lock probe can make a concurrent Codex writer acquisition fail" (abruption/codex-unlock #55) was seen as a search result only, not read: treat the hazard as unverified until Phase 0 reads it.

## 2) Goal

Register `codex` as a fourth provider that is discovered from the rollout files, launched through the existing launcher, shown live by the Claude-style process rule, and counted by the Overview, with Codex's on-disk behaviour recorded in `docs/KNOWLEDGE.md`.

## 3) Design Decisions

Decisions D1-D7 were settled by the user in `/qexplore` and confirmed again in `/qplan`; the rest are planner decisions that follow from them, from measurements, or from the plan review (Review Log).

| # | Decision | Choice | Alternatives considered | Rationale |
|---|---|---|---|---|
| D1 | Tiers (user, Q1) | A + B + C at parity with Claude Code and kiro-cli, plus a KNOWLEDGE.md section | Launcher only; add `/acp` driving (tier D) | The roadmap's value is machine-wide visibility. `/acp` needs a driver abstraction and a permission model that exist only for kiro. |
| D2 | Provider id, display name (user, confirmed in `/qplan`) | `codex` / "Codex" | `codex-cli` / "Codex CLI" | Id equals the binary name, so the launcher resolves it without a table entry. The provider also lists VS Code and desktop sessions of one store. The id is persisted in config, pins and the icon cache, so it is costly to rename later. |
| D3 | Launch flags (user, Q3) | None baked in: `codex`, `codex resume <id>` | Baked approval preset; full bypass | Matches Claude Code. The user's `config.toml` governs; flags go in Provider Settings default args (verified with `resume` in Phase 2 QA). |
| D4 | Discovery source (user, Q4, after an online check) | Rollout JSONL is the source of truth, read with the hardening rules of SC-7 | SQLite `threads` (42 ms, private versioned schema, `has_user_event` unreliable); hybrid; app-server (`thread/list`, official but needs a Codex process and the PATH `codex` version) | The rollout is canonical and the same parser serves transcripts, tails and usage. Cold scan measured 0.8 s for 613 files and runs in the startup warm-up. SQLite and app-server are deferred. |
| D5 | Live dot (user, Q5) | The Claude rule: terminal `codex.exe` by `resume <id>` or by workspace plus recent activity. The lock is used only for the Resume button | Lock held means live; lock plus terminal process in the cwd; lock-owner lookup | The lock-plus-process variant failed a break test (a desktop-held idle thread in the same folder would light up). The lock means "loaded in a running process" (desktop and VS Code hold it for opened threads), wider than "a terminal session is running". Consequence, accepted: desktop-held and VS Code-held threads show no dot (Risk Assessment, README). |
| D6 | Session set (user, confirmed) | All top-level sessions (CLI, VS Code, desktop). `source` an object with a `subagent` key means sub-agent and is excluded | CLI only (24 of 93) | Same approach as Claude Code. Hiding VS Code sessions would hide most of the history here. |
| D7 | Usage and sub-agents (user, confirmed) | Count sub-agent rollouts toward tokens and tool calls, only for records at or after `subagent_history_start_ordinal`; never as sessions or agent time. A sub-agent rollout whose start ordinal is `None` or not a non-negative int counts nothing (fail safe). Phase 0 verifies per kind; a kind that fails is excluded; if none validates, exclude all sub-agent rollouts | Exclude all sub-agent rollouts; naive sum; count-all for `None` | Naive summing multiplies the parent's tokens (measured). Excluding undercounts real work, and Claude's sub-agent transcripts are counted. A silent multiply is worse than an undercount. |
| D8 | Colour and icon (user, Q6) | `PROVIDER_COLORS["codex"] = "#ffffff"`; tinted terminal glyph; add a 14th "White" swatch (`#ffffff`) to the Card color group; usage bar colour `#e5e7eb` | Bundled logo; brand green | `codex.exe` has no icon resource. The UI is dark-only, so white is visible; Phase 2 QA checks every place the provider colour is drawn. A 14th swatch fills the 7-column grid exactly.
